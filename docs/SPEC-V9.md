# 目標利益 仕様 — SPEC-V9

記録 1 件ごとに「この取引でいくら残したいか」を持てるようにする。
持たせた記録では、**目標に届く最低販売価格**と、そこまでの**値下げ可能額**が計算できる。

**本書は SPEC.md / SPEC-V2〜V8 より後発**で、記録の列・記録フォーム・CSV に関する記述が
衝突する場合は本書が優先する。計算式（SPEC §2）には**足すだけ**で、既存の 7 関数はどれも変えない。

**分析画面は §9、記録詳細からの入口は §10**（どちらも 2026-08-14 に追加）。§4 の関数は
その画面の材料として先に用意したもので、§9 が最初の呼び手になる（記録フォームが使うのは
§2 の入力だけ、という関係は変わらない）。
§9 を書いた時点で **§4.6 の範囲の決め方だけを改訂**した ── 赤字の記録で使えなかったため。
§10 は §9 の関数（`recordDetailConclusion` など）を記録詳細の帯グラフに繋いだだけで、
新しい計算式は増やしていない。

**触っていないもの**: 集計（SQL の `netProfitSql` / `totalExpensesSql`）・絞り込み・
確定申告用 CSV（11 列）・記録詳細画面。目標は**計算式に一切入らない**（§1.4）。

| | 手数料率（SPEC §2.2） | 目標利益（本書） |
|---|---|---|
| 何か | 販売価格から引かれる実額の元 | **こうしたいという値。実際の金額ではない** |
| 未設定 | 無い（0〜50 の整数が必ず入る） | **ある。`null` =「決めていません」**（§1.2） |
| 0 の意味 | 手数料がかからない | **「利益ゼロを目標にする」という有効な目標**（§1.2） |
| アプリ全体の既定値 | ある（`DEFAULT_COMMISSION = 10`） | **無い。設定に置かない**（§1.3） |
| 計算式への影響 | 入る | **入らない**（§1.4） |

---

## 0. 背景

### 0.1 逆算はあったが、記録に残らなかった

計算タブには「目標から逆算」（UI-SPEC §1.1-3b）が既にある。目標額を入れると必要販売価格が出る。
だが**計算タブは記録を作らない**（SPEC-V2 §1.3「レコードではなくシミュレーション」）ので、
入れた目標はその場限りで消える。

出品したあとに「値下げ交渉が来たが、どこまで下げてよいか」を知りたい場面では、
出品時に決めた目標がもう手元に無い。同じ数字を毎回入れ直すことになる。
**記録が目標を覚えていれば、あとから何度でも同じ判断ができる。**

### 0.2 既定値を持たせるほうが自然に見えるが、採らなかった

「設定に既定の目標利益を置き、新規記録はそれで始まる」形（＝既定種別 `defaultRecordKind`
と同じ作り。SPEC-V2 §3.1）を検討して**退けた**。理由は §1.3。

## 1. データ

### 1.1 列（マイグレーション 0009）

`sale_records` に 2 列を**1 つのマイグレーションで**足す。

| 列 | 型 | NULL | 既定値 |
|---|---|---|---|
| `target_profit` | `integer` | **許容** | **置かない** |
| `listed_at` | `text` | **許容** | **置かない** |

```sql
ALTER TABLE `sale_records` ADD `target_profit` integer;--> statement-breakpoint
ALTER TABLE `sale_records` ADD `listed_at` text;
```

`DEFAULT 0` を置かない理由は §1.2 そのもの ── 置くと既存の全行が「目標 0 円」になり、
決めていない状態と区別できなくなる。既存行はすべて `NULL` で始まる。

**`real` ではなく `integer`。** 目標は人が決める切りのいい額で、端数を持つ意味がない
（他の金額列が `real` なのは、計算の途中で端数が出るため。SPEC §2.6）。

**`listed_at` は将来の出品日のために列だけ確保したもの**（§3.4）。今回は読み書きしない。

### 1.2 `null` は「決めていない」。0 とは別のもの

**`target_profit = null` =「目標を決めていない」。**
**`target_profit = 0` =「利益ゼロを目標にする（＝赤字にならなければよい）」。**

0 は有効な目標であって、未設定の代用ではない。**0 を「決めていない」の意味で使わない。**

区別が必要になるのは値下げ可能額（§4.3）で:

- 決めていない → **下げ幅を言えない**（`null` を返す）
- 目標 0 円 → **損益分岐点までは下げられる**（分岐点との差を返す）

どちらも 0 を返すと「もう下げられない」と読め、**決めていない人に根拠のない下げ止まりを見せる**。
金額の列でありながら NULL 許容にするのはこのため ── 他の金額列が
「未入力＝0 円」で意味が通るのに対し、目標だけは 0 に別の意味がある。
値が無いことを NULL で表す先例は `photo_file_name`（SPEC-V5 §2.1）。

### 1.3 アプリ全体の既定値は持たない（設定に置かない）

**設定タブに目標利益の欄を作らない。新規記録の `target_profit` は常に `null`。**

`defaultRecordKind`（SPEC-V2 §3.1）と同じ作りにしなかった理由:

1. **既定種別は「どちらか」だが、目標は「決めるか決めないか」から始まる。**
   種別は不用品か仕入品のどちらかで必ず決まるので、よく使うほうを既定にすると打鍵が減る。
   目標は**決めないのが正しい選択でもある**（値段だけ見て出すことのほうが多い）。
   既定値を置くと、決めていない記録に「決めた覚えのない目標」が入る。
2. **金額の目標は商品ごとに違う。** 500 円の不用品と 8,000 円の仕入品に同じ目標額は乗らない。
   種別のように「たいてい同じ」ものではないので、既定値の当たる率が低い。
   率（「原価の 30%」など）なら共通の既定値もあり得るが、それは別の機能になる（§7）。
3. **既定値があると `null` が作れなくなる。** 既定 1,000 円で始まる欄から
   「決めていない」に戻す操作は、空欄にすることでしか表せない。
   §1.2 の区別を守るなら、始まりが `null` であるほうが素直。

その帰結として、**大半の記録は目標が未設定のまま**になる。目標が無い状態が例外ではなく標準。

### 1.4 目標は計算式に入らない

`netProfit` / `totalExpenses` / `commissionCost`（SPEC §2.2〜§2.4）と、
SQL 側の集計（`src/db/repository.ts` の `netProfitSql` / `totalExpensesSql`）は**変えない**。

目標は「こうしたい」であって、支払った金額でも受け取った金額でもない。
経費に混ぜると収支が実態と合わなくなる。目標を読むのは §4 の関数だけで、
そのどれも既存の集計から呼ばれない。

### 1.5 保存時の正規化はしない

`repository.toRow()` は `target_profit` を**素通しで書く**。
不用品の仕入価格を 0 に落とす（SPEC-V2 §2.4）ような矯正はかけない ──
0 も `null` も、どちらも利用者が選んだ状態そのもの。

`SaveRecordInput.targetProfit` は**省略可にしない**（`siteName` / `photoFileName` / `tagIds` と
同じ理由。SPEC-V4 §1.4）。`update` は行を丸ごと書き換えるので、省略できると
「渡し忘れて静かに目標が消える」経路ができる。

## 2. 記録フォーム

### 2.1 入力欄

伝票カードの**外**に、折りたたみの節を 1 つ置く。畳んだままでも見出しの右に値が出る。

**伝票カードに入れない理由**: 伝票は販売価格から経費を縦に引いていく面（UI-SPEC §1.3）で、
そこに並ぶのは実際に動いた金額。目標を混ぜると、縦の引き算に入る額に見える。

欄のラベルは `targetProfitLabel(kind)` ── 不用品は「目標の純利益」、仕入品は「目標利益」。
**計算タブの逆算と同じ関数**を使う（§5.2）。

### 2.2 「決めていません」と書く。「¥0」とは書かない

未設定の表示語は **`TARGET_PROFIT_UNSET_LABEL = '決めていません'`**。

- `UNSET_INPUT_LABEL`（「未入力」）とも分ける ── 目標は入れ忘れではなく、
  決めないのが正しい選択でもある。「未入力」だと直すべき空欄に見える
- 空欄のときの placeholder も「決めていません」。薄い `0` を置くと消し忘れの 0 円に見える

畳んだ見出しの右に出す値は `targetProfitSummary(targetProfit)`:
`null` なら語、それ以外は金額（**0 なら「¥0」と出る** ── そう決めた目標なので正しい）。

### 2.3 空欄 ↔ `null` の変換

`RecordFormValues.targetProfit` は他の金額欄と同じ**入力中の文字列**で持つが、
**空欄の扱いだけが違う**。

| | 他の金額欄（SPEC §5.1） | 目標利益 |
|---|---|---|
| `''` | `0` | **`null`** |
| `'.'` | `0` | **`null`** |
| `'0'` | `0` | `0` |
| `'1500.6'` | `1500.6` | **`1501`**（整数に丸める。§1.1） |

- `parseTargetProfitInput(value): number | null` … 入力欄 → 保存値
- `targetProfitToInput(value: number | null): string` … 保存値 → 入力欄

**`amountToInput` は使えない。** あれは 0 以下を空欄に落とすので、
目標 0 円の記録を開いて保存し直すだけで目標が消える。空欄になるのは `null` のときだけ。

`'.'` を `null` にするのは、他の欄と違って 0 が別の意味を持つため ──
打ちかけの記号を「利益ゼロを目標にする」として保存してしまう。

### 2.4 必須にしない

`canSave()` は変えない。**必須は商品名のみ**（SPEC §5.2）。
目標が空でも保存でき、保存された記録の目標は `null` になる。

## 3. CSV とバックアップ

### 3.1 書き出し（データ保存用）は 18 列 → 19 列

`CSV_BACKUP_COLUMNS` に **`目標利益`** を 1 列足す。位置は**収支の直後**。

```
販売日, 商品名, 販売価格, 仕入価格, 送料, 販売手数料, 梱包材, その他,
経費合計, 収支, 目標利益, 手数料率, 販売サイト, 種別, タグ, 状態, 出品日, メモ, 記録ID
```

収支の隣に置くのは、表計算で「目標に対して実際いくらだったか」を横に並べて読むため。
属性の側（種別・タグの並び）へ流すと 2 つが離れる。

**決めていない記録は空欄**（`0` とは書かない）。日付の `null` と同じ扱い（SPEC-V3 §5.4）。
既に整数で保存されているので丸めない。

**確定申告用（11 列）は変更しない。** 帳簿に「目標」の欄は無い。

**SPEC-V8 の本文にある「18 列」はすべてこの 19 列を指す**（冒頭の対照表・§0.2 など）。
あちらは本書より前に書かれたもので、列数以外の記述は変わらない。

### 3.2 バックアップの `records.csv` は 17 列 → 19 列

`target_profit` と `listed_at` を**末尾に足す**。列名は DB のカラム名そのまま（SPEC-V8 §2.1）。

| 列 | 型（`ColumnSpec`） | 空欄 |
|---|---|---|
| `target_profit` | **`numberOrEmpty`**（新設） | 許す＝`null` |
| `listed_at` | `dateOrEmpty` | 許す＝`null` |

**`numberOrEmpty` を新設した理由**: 既存の `number` は空を弾く。
目標を決めていない記録が 1 件でもあるバックアップを、**自分で書いて自分で弾く**ことになる。
`0` と書いてあれば `0` として通る（空欄との書き分けが列の要点）。

**末尾に足す**のは `backup-info.csv` の `photo_count`（SPEC-V8 §4.1）と同じ理由 ──
途中に挿すと、古いファイルを「先頭 n 列が一致するか」で読む道が塞がる。

### 3.3 形式バージョン 3。17 列の旧ファイルは受け入れる

`BACKUP_FORMAT_VERSION` を **2 → 3**。列が増えたので上げる（SPEC-V8 §1.2.1）。
`BACKUP_MIN_SUPPORTED_VERSION` は **1 のまま**。

**版 2 以前の `records.csv`（17 列）はエラーにせず、足りない 2 列を `null` として読む。**

これは **SPEC-V8 §3.2「1 件でもエラーがあれば一切読み込まない」の例外**。
例外にする理由は写真の欠落（SPEC-V8 §4.3）と同じ考え方 ──
**列が 2 つ増えたというアプリ側の都合で、利用者が既に持っているバックアップを
読めなくする理由がない。** 目標利益は後から足した任意項目で、無くても記録の意味は変わらない。

読み分けの手順:

1. `records.csv` のヘッダが**現在の 19 列と一致する**か → 通常どおり読む
2. **旧 17 列と一致する**か → 旧の表で検証し、足りない 2 列を**空文字で埋める**
3. どちらでもない → 今までどおり「列の数が違います / 列名が違います」で止める

**見るのはヘッダの形であって `backup-info.csv` の版ではない。**
版の数字は手で書き換えられるし、書き換えられていても中身が読めるならそれで足りる。

**例外はこの 2 列だけ。** 17 列ぶんの値に不正があれば今までどおり全体が止まる
（旧ファイルの `sales_price` が `abc` なら「販売価格が正しい数値ではありません」で停止）。

空文字で埋めるのは、それが書き出し側が `null` に対して書く値そのものだから ──
読み込み側（`db/backup.ts`）は新旧どちらのファイルも同じ 1 本の経路で `null` に落とせる。
`Number('')` は `0` になるので、目標だけは素で通さず `null` に落とす分岐を持つ。

### 3.4 `listed_at` は列だけ確保する

**現在このアプリは `listed_at` を読み書きしない。** 常に `null` で、CSV では常に空欄。

- **出品日は既存の `sale_start_date` を使う。** 一覧・詳細・経過日数・CSV の「出品日」列は
  すべて今までどおりこの列を見る。「8/1 出品 → 8/14 販売」「出品中 14日目」の表示も変わらない
- `sale_start_date` は記録を作った日で埋まることが多い。将来「実際に出品した日」を
  別に持ちたくなったときの置き場として、**`ALTER TABLE` を 1 回で済ませられるうちに**足した
- UI も計算式も無い。通るのはバックアップの往復だけ（列を落とすと
  「`records.csv` = DB の全カラム」の対応が崩れるため、書き出しには出す）
- `SaveRecordInput` にも入れない。`repository.create` が新規行に `null` を置くだけで、
  `update` はこの列に触らない（`toRow` に入れると、将来値が入ったとき編集のたびに消える）

## 4. 計算（`src/logic/profit.ts`）

すべて純粋関数。**端数処理は既存に合わせる**（SPEC §2.6 / 決定 §7-3）:

- **「この価格なら届く」を返すもの** … `Math.ceil`。切り捨てると 1 円足りずに目標を割る価格を返す
- **差額を返すもの** … 丸めない（中間値なので、丸めるのは表示の瞬間だけ）
- **目標が `null` のとき、目標に関わる関数は `0` ではなく `null` を返す**（§1.2）

### 共通の入力 — `TargetCostInput`（率と固定額の両方を取る）

```ts
type TargetCostInput = Omit<CostInput, 'salesPrice'> & { fixedFee?: number };
```

今のアプリの手数料は**率のみ**（`commission` は %）だが、
販売価格に比例しない固定額を取る販売先もあるので、式の側では両方を受ける。

**固定額が無い構成では `0` を渡す。そのとき結果は率だけの式と完全に一致する** ──
`fixedFee` は割り算の外側にそのまま足されるだけなので、0 なら消える。
省略も 0 と同じ扱いにしてあるので、既存の `CostInput` をそのまま渡せる。

式は 1 本だけ。既存の `exactRequiredSalesPrice`（SPEC §2.5）を借りて、
固定額は「率のかからない支出」として目標側に寄せる:

```
必要販売価格 = ceil( (目標 + 経費4項目 + 固定額) / (1 − 率/100) )
```

### 4.1 `breakEvenSalesPrice(costs): number`

損益分岐点の販売価格。**その価格で売ると純利益がちょうど 0 になる額。切り上げ。**

上の式の目標 0 円の場合そのもの。**目標が無くても常に出せる**ので、返り値に `null` は無い。

### 4.2 `targetSalesPrice(targetProfit, costs): number | null`

目標利益を達成できる最低販売価格。**切り上げ。目標が `null` なら `null`。**

**目標 0 円は `null` ではなく、§4.1 と同じ価格を返す。**

`requiredSalesPrice`（計算タブの逆算。SPEC §2.5）との違いは、
固定額を受けることと、「決めていない」を型で表せること。式は同じ 1 本を通る。

### 4.3 `discountRoom(currentPrice, targetProfit, costs): number | null`

値下げ可能額 ＝ 現在価格 − §4.2。**負なら 0。目標が `null` なら `null`。**

負を 0 に丸めるのは、下げ幅としてマイナスが意味を持たないため ──
「−300 円下げられる」ではなく「もう下げられない」が言いたいこと。
目標に既に届いていないことは、この値ではなく §4.2 との比較で分かる。

### 4.4 `lossMargin(currentPrice, costs): number`

赤字までの余裕 ＝ 現在価格 − §4.1。**負なら 0。**

目標と無関係なので**常に数値**。0 は「余裕がない」であって「決めていない」ではないので、
`null` を返す道がない。

### 4.5 `simulateAtPrice(price, costs): PriceSimulation`

指定価格での純利益と利益率。シミュレーターの 1 点ぶん。**丸めない。**

```ts
type PriceSimulation = { price: number; netProfit: number; profitRate: number | null };
```

- `netProfit` … `price − (経費4項目 + price × 率 + 固定額)`。赤字なら負
- `profitRate` … 純利益 ÷ 販売価格 × 100。**販売価格が 0 のときは `null`**

**価格 0 で `0` を返さない。** 0 で割れないため。`0` を返すと「利益率 0%（とんとん）」に読めるが、
価格 0 で経費が出ていれば実際は丸ごと赤字。計算できないことは計算できないと返す
（目標が `null` のときと同じ考え方）。

固定額を `netProfit`（SPEC §2.3）の式に混ぜず、ここで引くのは、
既存の式・SQL・CSV がすべて率だけを前提にしているため。

### 4.6 `simulationPriceRange(currentPrice, costs): PriceRange`

シミュレーターが動かす価格の範囲。両端とも含む。
**現在価格が分岐点（§4.1）のどちら側かで、伸ばす向きが変わる。**

| | 最小 | 最大 |
|---|---|---|
| 現在価格 **>= 分岐点**（黒字） | (分岐点 − 500) を **100 円単位で切り下げ**・0 未満は 0 | **現在価格**（丸めない） |
| 現在価格 **< 分岐点**（赤字） | **現在価格** | (分岐点 ＋ 分岐点と現在価格の差) を **100 円単位で切り上げ**。ただし最低でも分岐点 + 500 を超える |

分岐点ちょうどを端にしない（外側に 500 円ぶん残す）のは、
「ここから赤字」の線が範囲の端に張り付くと、その先の様子が見えないため。
下端と上端で同じ 500 円を使うので、定数は 1 つ（`SIMULATION_BREAK_EVEN_MARGIN`）。

**2026-08-14 の改訂。** 元は向きが 1 つだけ（最小 = 分岐点 − 500 / 最大 = 現在価格）で、
「最大が最小を下回ることがある。黙って直さず、そのまま返す」と書いていた。
**赤字の記録でこれが使えないことが §9 の画面で分かったので、向きを分ける。**

- 範囲の上端が分岐点に届かず、**この画面でいちばんしたいこと（黒字になる価格を探す）が
  操作としてできない**。潰れた範囲が「今の価格では赤字」を伝えるという当初の考えは、
  伝える相手（画面）が赤字を別に知っている以上、範囲を潰す理由にならなかった
- 赤字側の下端を現在価格にするのは、そこから下は「もっと赤字」しか無いため ──
  下げる幅に意味が無い場面で、範囲の半分をそこへ使わない
- 上端を「分岐点 ＋ 今の不足額」にするのは、値上げ幅を今の不足と同じだけ先まで見せる形。
  不足がわずかなときに分岐点のすぐ上で頭打ちにならないよう、下限として分岐点 + 500 を置く

**どちらの向きでも最小 <= 最大**が成り立つ（現在価格 = 分岐点 = 0 の記録では 0〜0）。

### 4.7 `elapsedDays(record, today): number`

経過日数。売却済みは 記録日 → 販売日、出品中は 記録日 → 今日。

**数え方は `src/logic/listingDays.ts` が持つ**（暦日差・当日は 0 日。UI-SPEC §5-2）。
この関数はその 1 本をそのまま通すだけで、日付の引き算を書き直さない ──
目標の面でも一覧・詳細と同じ日数が出るようにするため。

**日付が逆転している記録（販売日 < 記録日）は負の値をそのまま返す。0 に丸めない** ──
逆転は入力の誤りなので、「0 日で売れた」と見せると直すきっかけごと消えてしまう。

## 5. 逆算（計算タブ）とは統合しない

### 5.1 統合できない理由

計算タブの「目標から逆算」（UI-SPEC §1.1-3b）の目標額は
`CalcFormValues.targetProfit` ── **画面ローカルの state**で、DB に一切触らない。

**計算タブは記録を持たない**（SPEC-V2 §1.3）。あの画面に対応する行が
`sale_records` に無いので、「1 つの state を両方が参照する」形にする土台がない。
同じ値にするには、計算タブが「編集中の記録」を持つ設計に変える必要がある。

### 5.2 語彙だけは統一する

**`targetProfitLabel(kind)` を両方で使う**（「目標の純利益」/「目標利益」）。
同じものを指す欄なので、画面ごとに呼び名が変わると別の値に見える。

### 5.3 計算タブの目標は記録フォームの初期値として引き継ぐ

`toInitialAmounts()` / `InitialAmounts` に `targetProfit` を**足す**。
「この内容で記録する」で渡るのは金額・種別・サイト名と、逆算の目標額。

**ただし記録時に黙って保存されるのではなく、フォーム上で編集可能な状態で渡す。**
入るのは目標の欄の初期値で、開いた人はそのまま保存することも、書き換えることも、
消すこともできる。保存されるのは「保存」を押した時点で欄に入っている値だけ ──
これが「記録に紐づかない試算が、いつの間にかこの記録の目標になっている」を避ける線。

**逆算モードで入力しているときだけ渡す。** `CalcFormValues.targetProfit` は
モードを「利益を出す」に戻しても残るので、そのまま渡すと画面のどこにも出ていない
目標が付いてしまう。モードの解決は呼び出し側（計算タブの画面）が行い、
逆算モード以外では空文字を渡す ── 販売価格（逆算結果 or 入力値）と同じ作法で、
`toInitialAmounts` の**省略できない引数**にしてある。

目標を入力していなければ空文字が渡り、フォームの目標は
`null`（＝決めていない）のまま（§1.2 の区別を壊さない）。

## 7. 決定の記録

### §7-1 アプリ全体の既定値を持たない
§1.3 の 3 点。**既定値があると `null` が作れなくなる**のが決め手で、
§1.2 の区別（決めていない / 目標 0 円）を守るには始まりが `null` である必要がある。

### §7-2 `0` を「決めていない」の代用にしない
0 は「赤字にならなければよい」という目標として成立する。
代用にすると、値下げ可能額が「もう下げられない」と「下げ幅を言えない」を取り違える（§4.3）。
NULL 許容列を 2 本目に増やしてでも区別を持つのはこのため。

### §7-3 目標関連の関数は `null` を返す（`0` ではない）
呼び出し側が「未設定」と「目標ゼロ」を区別できる必要がある。
`0` を返すと意味が反転して読める（§4.3）。同じ考え方で、
利益率も価格 0 のときは `0` ではなく `null`（§4.5）。

### §7-4 端数は「届く価格は切り上げ / 差額は丸めない」
既存の逆算（決定 §7-3）と同じ。切り捨てると目標を 1 円割る価格を返すことがあり、
それは答えとして嘘になる。差額は中間値なので、丸めるのは表示の瞬間だけ（SPEC §2.6）。

### §7-5 手数料の固定額を式の側だけ用意する
今のアプリに固定額は無い。それでも引数に持つのは、
**あとから足すと 7 関数すべての形が変わる**ため。0 を渡せば率だけの式と完全に一致するので、
持っていても現在の結果は 1 円も動かない（§4「共通の入力」）。

### §7-6 旧 17 列のバックアップを例外として受け入れる
SPEC-V8 §3.2 の「全か無か」を崩す唯一の例外。
**アプリ側の都合（列を 2 つ足した）で、利用者が既に持っているファイルを読めなくしない。**
例外の範囲は末尾 2 列だけで、17 列ぶんの値の検証は今までどおり全体を止める（§3.3）。

### §7-7 `listed_at` を使う予定が無いまま足す
`ALTER TABLE` を 2 回に分けるより 1 回で済ませたい、という理由だけの列。
**使わない列を持つことの害**（CSV に空欄が 1 列増える）より、
**将来もう一度マイグレーションを増やす害**のほうが大きいと判断した。
出品日は既存の `sale_start_date` のままで、置き換える計画も現時点では無い（§3.4）。

### §7-8 目標を伝票カードの外に置く
伝票は実際に動いた金額を縦に引いていく面（UI-SPEC §1.3）。
「こうしたい」という値をそこに混ぜると、引き算に入る額に見える（§2.1）。

## 9. 分析画面「いくらで売る？」（2026-08-14 追加）

記録詳細から push する **1 商品の分析画面**。データタブが販売全体の傾向（何が売れているか）を
扱うのに対し、この画面は「**この 1 つをいくらで売るか**」だけを扱う。だから合計も推移も出さない。

**今回は出品中のみ。売却済みの扱いは次回のまま。**
入口（記録詳細のどこから開くか）は §10 で足した ── 記録詳細の帯グラフの直下に出る
結論行（`PricingEntryRow`）を押すとここへ push する。ルートを直接叩いての確認も引き続きできる:

```
npx uri-scheme open "apprn://records/record/<記録ID>/pricing" --ios
```

### 9.1 この画面が守ること

1. **サービス名は一切出さない。** 出品先は「出品しているサイト」「あちら」としか呼ばない
2. **「¥0」を「目標を決めていない」の意味で使わない**（§1.2）
3. **目標が `null` のとき、目標関連の値は 0 ではなく `null` として扱う**（§7-3）
4. **計算は §4 の純粋関数を使い、画面側に式を書かない**（`src/logic/pricing.ts` が中継する）
5. **帯グラフを複製しない。** 費用の内訳は記録詳細のレシートへ戻す（§9.13）
6. **「手取り」は使わない**（SPEC-V2 §7-8）。同じことを言う語は「手元に残る」

### 9.2 骨格（上から 6 段）

| 段 | 中身 |
|---|---|
| 1 | 商品名 ＋ バッジ（「出品中 14日目」） |
| 2 | 「今の価格 ¥5,000 で売れたら」＋ 主役の数字（見込み純利益）＋「手元に残る見込み・利益率 34.0%」 |
| 3 | 結論の帯（色は状態による） |
| 4 | 価格ライン（横。目盛りは 2〜3 点） |
| 5 | シミュレーターのカード |
| 6 | 最下段 2 行「費用の内訳 ›」「目標利益 ›」 |

**目標の有無で段の数を変えない。** とくに最下段は常に 2 行で、目標を決めていない記録でも
「目標利益　決めていません ›」が出る（決める口がそこにしかないため）。

**目標なしが標準ケース**（§1.3）。目標ありを基本形にしてそこから引き算する作りにはしない ──
目標が無いときに空の目盛りや「¥0」が残る。

### 9.3 状態（目標の有無 × 赤字かどうか ＋ 価格未設定）

`src/logic/pricing.ts` の `PricingState` は **3 つ**（`unpriced` / `loss` / `profit`）。
目標の有無は状態に入れない ── 目標は「どの線が基準になるか」を変えるだけで、
画面の骨格（主役の数字が出るか・向きが反転するか）を変えるのは価格のほう。

- **価格 0 は「赤字」ではなく「未設定」。** 0 円は必ず分岐点を割るが、それは値付けの失敗ではない
- バッジは出品中なら「出品中 N日目」（日数は §4.7 の暦日差 + 1。出品当日が 1 日目）。
  **出品日が未来（日数が負）の記録では日数を出さず「出品中」だけ** ──「0日目」には読み方がない

### 9.4 A. 目標なし・黒字（標準）

- 結論の帯（青）:「¥3,112 までなら赤字になりません。」＋「交渉されても、あと ¥1,888 は下げられます。」
- 価格ライン: **2 点のみ**（利益ゼロ / 今の価格）。**目標ラインの区間は作らない**（空の目盛りを残さない）
- シミュレーター: 見出し「値下げしてみる」。判定は「まだ ¥1,388 の余裕があります」（分岐点までの残り）。
  **「達成」という語は使わない** ── 決めていない人に「達成」と言うと、
  決めた覚えのない基準に受かったように読める
- 最下段:「目標利益　決めていません ›」

### 9.5 C. 目標なし・赤字（現在価格 < 分岐点）

- 主役の数字は「−¥550」＋「赤字」バッジ（赤）。補足は「売っても、手元のお金は ¥550 減ります」
- 結論の帯（赤）:「あと ¥612 の値上げで、赤字から抜けます。」
  ＋「¥3,112 で利益ゼロ。それより上なら手元にお金が残ります。」
- 価格ライン: **横のまま**。2 点の順序が逆転する（今の価格が左・分岐点が右）。
  2 点の間に「あと ¥612」を渡し、右端に「上げるほど残る →」を添える
  ── 赤字時は動かす向きの意味が反転するため
- シミュレーター: 見出しを「**価格を動かしてみる**」に変える（「値下げ」ではない）。
  範囲は §4.6 の赤字側（上へ伸ばす）
- ボタン:「価格を ¥3,112 以上に直す」

### 9.6 B / D（目標あり）と、5 つ目の状態

**目標を決めると基準線が分岐点から目標ラインへ上がる。** それが B と A の唯一の違い。

`pricing.ts` の `PricingConclusion` は **5 つ**（結論の帯の種類そのもの）:
`safe` / `safeWithTarget` / `belowTarget` / `loss` / `lossWithTarget`
（A＝`safe`、B＝`safeWithTarget`、C＝`loss`、D＝`lossWithTarget`）。
判定は `pricingConclusion()`：`state === 'unpriced'` なら `null`、
`state === 'loss'` なら目標の有無で `loss` / `lossWithTarget`、
それ以外は目標が無ければ `safe`、あれば `meetsTarget` の真偽で `safeWithTarget` / `belowTarget`。
文言は `pricingConclusionText()` が組む（色は `CONCLUSION_TONES`：good＝青 / warn＝オレンジ / bad＝赤）。

| 状態 | 帯 | 価格ライン |
|---|---|---|
| B. 目標あり・黒字（`safeWithTarget`） | 「¥4,223 までなら、目標利益 ¥1,000 を保てます。」＋「交渉されても、あと ¥777 は下げられます。」 | 3 点 |
| D. 目標あり・赤字（`lossWithTarget`） | C と同じ 1 行目 ＋「目標利益 ¥1,000 まで戻すなら ¥4,223（今より ¥1,723 上）」 | 3 点 |
| **`belowTarget`** | 「目標利益 ¥1,000 まで、あと ¥723 です。」＋「¥3,112 までなら赤字にはなりません。」（オレンジ） | 3 点 |

**余裕がちょうど 0 のとき（今の価格 ＝ 基準線）は「あと ¥0 は下げられます」と言わない。**
2 行目を「今の価格がその下限です。これ以上は下げられません。」に差し替える ──
0 円ぶん下げられるという文は、下げられないことを回りくどく言っているだけになる。
シミュレーターの判定も同じで、余裕 0 なら「ここが下限です」（「まだ ¥0 の余裕があります」とは言わない）。

**`belowTarget` はモックに無い 5 つ目の状態で、目標を決めた記録では必ず通る道。**
今の価格が分岐点と目標ラインの間にあるとき、B の文（「あと ¥777 は下げられます」）は
0 円の余裕を「下げられます」と言うことになる。だから帯を 1 つ増やした。

### 9.7 E. 価格が未設定（`sales_price === 0`）

- バッジは「**価格 未設定**」（「未入力」ではない ── 空欄も 0 円も同じ値で保存されるため）
- 主役の数字と利益率は「ーー」で置く
- 「売る価格を入力する」ボタン → **記録の編集フォーム**（この画面に価格の入力欄は作らない）
- 「価格がなくても分かっていること」…目標なしなら 2 行（すでにかかった費用 / 赤字にならない価格
  ¥3,112 以上）、目標ありなら 3 行目に「目標が出る価格」。**目標が無いときに空の行を残さない**
- シミュレーターは薄く出して不活性。「価格を入れると、ここで値下げを試せます」

### 9.8 価格ライン

**点の並びは値の昇順**（`priceLineTicks`）。赤字での逆転（今の価格が左）はこの規則から
自然に出るので、「赤字のときは逆に描く」という第 2 の規則を持たない。

- 点は 2〜3 個。**目標が無いときは目標の点を作らない**
- 今の価格だけ塗りつぶした丸、他は角丸の四角の枠 ──
  「今どこに居るか」と「どこに線があるか」は種類の違う情報なので、色だけで分けない
- 金額と説明の列は**それぞれの点の真下**。近すぎる隣とは押し合って離す（`labelLefts`）──
  両端寄せにしていた初期の実装は、書き換えたあとに灰色の点が右端へ来ると
  「今の価格」の列がその点の下に並び、別の点の説明に読めた
- 「あと ¥612」と「上げるほど残る →」は**赤字のときだけ**。
  向きの説明は**金額の列とは別の行**に置く（目盛りが 3 点あると場所を取り合うため）
- **書き換える前の価格（灰色の点）も値域に入れる。** 入れないと、値下げした直後に
  前の価格が右端の外へ出て、残すはずの点が線から消える

### 9.9 シミュレーター

- 範囲は §4.6。**初期値**は黒字なら今の価格（開いた時点では何も変えていない）、
  赤字なら**分岐点**（この画面で探しているのはその価格）
- つまみは 10 円刻み。分岐点・目標達成価格には**吸い付く**（答えがたいていその点そのものなので）
- 判定は 5 種（`SimulationVerdictKey`）。「達成」は目標があるときだけ
- **外部ライブラリを足していない。** つまみは RN の responder プロパティで書く（`PriceSlider`）

### 9.10 ボタンの語と押せる条件

| | 語 | 押せる条件 |
|---|---|---|
| 黒字 | 「この価格でこのアプリに記録する」 | 今の価格と違うこと |
| 赤字 | 「価格を ¥3,112 以上に直す」 | 今の価格と違い、**かつ分岐点以上** |

赤字で分岐点未満のときに押せると、ボタンの語が嘘になる（`canApplyPrice`）。
**黒字の記録は分岐点を割る価格でも書き戻せる** ── そこは利用者の判断。

### 9.11 記録への書き戻し

1. 確認シートを出す:「この価格に書き換えます」。
   いまの記録 / 書き換えたあと / 見込みの利益（¥1,700 → ¥1,250）を並べる
2. シートの注意文:「出品しているサイトの価格は変わりません。あちらはご自分で変更してください。」
   （**サービス名は書かない**）
3. 書き込みは `repository.setSalesPrice`（**1 列だけ**）。`update` は行を丸ごと書き換えるので、
   この画面が持っていない列（タグ・写真・目標）を渡し忘れて消すことになる
4. 反映後、上の数字は再計算される。**前の価格は価格ライン上に灰色の小さな点として残す**
   （画面を出るまで。保存しない）。この画面にいる間に何度も書き換えた場合は、
   `previousPrices`（配列）が古いものも含めて全部残す ── 「取り消す」は直前の 1 回だけを
   戻し、対応する点だけを配列の末尾から取り除く（§9.12 のバーと寿命が同じなのも直前の 1 回分）

### 9.12 反映後のバー

「このアプリの記録を ¥4,500 にしました」＋「取り消す」。**5 秒で消え、そのとき取り消しもできなくなる。
画面を出たときも同じ**（戻す先の価格をバーと同じ寿命で持つ）。
「売れた」の合図（4 秒）より長いのは、こちらが金額の書き換えで、読んで確かめるものが 1 つ多いため。

### 9.13 最下段の 2 行

- 「目標利益 ›」の右は `targetProfitRowValue`:
  決めていなければ「決めていません」、決めてあれば「¥1,000（この記録だけ）」
  ── アプリ全体の既定値は無い（§1.3）ので、この額が他の記録に及ばないことを言う

### 9.14 目標利益を決めるシート

  **0 を入れて消す道は作らない** ── 0 は「利益ゼロを目標にする」という有効な値（§1.2）

## 10. 記録詳細の帯グラフと入口（2026-08-14 追加）

記録詳細のレシート（`RecordDetailSections.ReceiptCard`）の上に、同じ 1 件を横の割合で見せる
積み上げ帯を足す。**新しい計算式は増やしていない** ── 数字は `src/logic/recordBreakdown.ts` が
既存のレシートの数字を並べ替えるだけ、帯の直下の結論行は §9 の `analyzePricing` /
`recordDetailConclusion`（`src/logic/pricing.ts`）をそのまま呼ぶ。この結論行が、
§9 の画面（「いくらで売る？」）への唯一の入口になる。

### 10.1 帯とレシートの関係

- レシートは「販売価格から順に引いて結果に至る」縦の流れ、帯は同じ 1 件を横の割合で見せる。
  **レシート側は変えない** ── 帯はレシートカードの先頭に足すもの
- **凡例は独立させない。** 色と項目名の対応は、帯の直下ではなく**レシートの各行に付けた
  同じ色のドット**が引き受ける（`RecordDetailSections.ReceiptCard` の `dotColor`）。
  独立した凡例を試したところ、同じ項目名がレシートと 2 列に分かれて並び、
  どちらを読む列なのか決まらなかった
- 色は `components/CostProportionBar.partColor` をそのまま呼ぶ（計算タブの逆算の帯と同じ配色）。
  新しい色はここでは定義しない
- 数字の丸め方は計算タブの `costBreakdown`（`logic/calcForm.ts`）に合わせる。
  **各項を先に丸めてから足し引きする**ので、帯・レシートに出る額が互いに 1 円もずれない

### 10.2 黒字の 1 本バー（`SurplusBreakdown`）

帯は 1 本、全長 ＝ 販売価格。区画は `RecordBarPart`（`key` / `label` / `amount` / `inBar` / `ratio`）
の並びで、**常に計算タブの帯と同じ順**（利益 → 販売手数料 → 仕入 → 送料 → 梱包材・その他。
`costBreakdown` と同じ並び）。額の大きい順には詰めない ── 記録をまたいで色が別の項目を
指すように見えてしまうため。

- **不用品は仕入の区画自体を作らない**（SPEC-V2 §1.3）。レシートも行ごと出していないのと対応する
- **0 円の項目は区画を作らない**（`inBar: false`）。幅 0 の区画は色だけが残って意味を持たない
- 区画の幅に文字（項目名・割合）が入るかは `showsBarLabel`（後述の §10.4 と同じ下限）

### 10.3 赤字の「案C」（`DeficitBreakdown`）

```
██仕入██│送料│手数料│▨▨足りない -¥550▨▨
```

**黒字と同じ費用の積み上げ ＋ 右端の 1 区画だけが違う。** 黒字で緑の「手元に残る」が伸びる
位置に、赤字では**斜線の「足りない」**（`shortfall = costTotal − salesPrice`）が入る。
帯の全長は「かかった費用の合計 ＋ 足りなかった額」（`total = costTotal + shortfall`）── 
販売価格を分母にすると費用の合計だけで 100% を超え、不足分の置き場が無くなるため。
**`kept`（手元に残る額）の区画は常に `inBar: false`**（その位置は `shortfall` の斜線が占める）。

以前試した「売った / かかった」の 2 本立てと、それを改めた単色 1 本はどちらも廃止した
（帯グラフのコメント参照）。2 本立ては桁違いの記録で片方の塗りが 1% 未満になり空の器に見え、
単色 1 本はそれを避けたが今度は赤字の記録だけ内訳が読めなくなった。積み上げ 1 本 ＋
下限を守った区画（§10.4 の `MIN_SEGMENT_WIDTH`）ならどちらも避けられる。

- **`COLLAPSE_COST_RATIO = 0.9`。** 費用側の 1 項目がこの帯の 90% を超えたら、費用側は
  1 色にまとめて内訳をレシートに任せる（`collapsedCosts`）。残りの費用が合わせて 1 割未満に
  潰れると、区画も引き出し線も互いに重なって読めなくなるため。まとめた区画は右端を
  `TornEdge`（三角形 `TORN_TOOTH_COUNT = 4` 個）でギザギザにし、「内訳を途中で打ち切った」
  ことを形でも示す。**このとき費用側の `parts` はどれも `inBar: false`**（描くのは 1 区画だけ）
- **斜線は `DiagonalStripes`。** 語（「足りない」）は模様とは別の手がかりで、模様だけで
  「足りていない」と伝えない。斜線の区画の中に額を入れる下限は
  **`SHORTFALL_AMOUNT_MIN_RATIO = 0.25`**（`showsShortfallAmount` が判定する）。
  費用の区画の下限（15%）より広く取るのは、こちらに入る文字が金額
  （「−¥399,100」＝ 9 文字）で割合（「30%」＝ 3 文字）より長いため。下限に届かないときは
  帯の外の引き出し線へ回す（§10.4）。**額そのものは必ずどこかに出す**（区画内 or 引き出し線）

### 10.4 引き出し線（15% 未満の下限と段違い）

`BAR_LABEL_MIN_RATIO = 0.15` 未満の区画は、帯の中に項目名・割合を入れず**帯の外へ引き出す**
（`leaderLines`）。対象は「帯に区画があり（`inBar: true`）、かつ文字が入らない
（`!showsBarLabel`）」区画だけ。0 円の項目・不用品の仕入・赤字の `kept` は元から `inBar: false`
なので対象に入らず、**費用側をまとめた赤字（`collapsedCosts`）の結果は必ず空**になる。
閾値は帯の中に文字を入れる判定（`showsBarLabel`）と同じ 1 つを使う ── 別の値にすると、
文字も線も付かない区画や、両方付く区画ができてしまう。

**段違いは `LEADER_TIERS = 2` の 2 段。** 対象を左から数えて `index % 2` で交互に段を振る
だけで、隣り合う区画は必ず別の段になる（線の長さ＝`LEADER_LINE_HEIGHTS`）。細い区画が
隣り合うと、線の先のラベルどうしが幅では避けられず必ず重なる ── 高さをずらすことで避ける。
赤字で額を区画内に入れられなかったときの引き出し線（`shortfallLeader`）も、
直前の費用側の引き出し線と段を揃えないように 1 つずらす。

### 10.5 分析画面への入口行（`PricingEntryRow`）

帯（黒字・赤字どちらも）の直下に、**出品中（`!record.isSold`）かつ価格設定済み**のときだけ
1 行を足す。売却済みでは出さない ── 売れたあとは「動かせる価格」という概念自体が無いため。
価格未設定でも出さない（§10.6）。押すと `router.push` で `/records/record/[id]/pricing`
（§9 の画面）へ入る。

行の状態は `recordDetailConclusion(analyzePricing(record))` が持つ **4 状態**
（`RecordDetailConclusion`）で、§9 全画面の結論（`PricingConclusion` の 5 状態）とは別の型。
`state === 'unpriced'` なら `null`（行を出さない）、`loss` なら目標の有無で `loss` /
`lossWithTarget`、それ以外は目標の有無で `safe` / `safeWithTarget` ──
**`belowTarget`（黒字だが目標未達）は `safeWithTarget` に合流させる。** どちらも
「`floorPrice`（＝目標があれば目標ライン、無ければ分岐点）まで下げられる」としか言わない
1 行で、目標に届いているかどうかはこの行の主題ではない（届いているかはレシートの結果行の
色が言う）。全画面の帯は 2 行使って「行き先」と「余裕」を分けて言えるが、こちらは 1 行しか
無いので額 1 つで用件が伝わる短い言い方にする（`recordDetailConclusionHeadline`）。

| 状態 | 見出し（1 行目・太字） | 詳細（2 行目・グレー、末尾に ›） |
|---|---|---|
| `safe` | 「あと ¥1,888 下げても赤字になりません」 | 「値下げを試す・赤字にならない価格を見る」 |
| `safeWithTarget` | 「¥4,223までなら、目標利益¥1,000を保てます」 | 「値下げを試す・目標を保てる価格を見る」 |
| `loss` | 「あと¥612の値上げで、赤字から抜けます」 | 「値上げを試す・赤字から抜ける価格を見る」 |
| `lossWithTarget` | 「目標利益¥1,000まで戻すなら¥4,223」 | 「値上げを試す・目標を保てる価格を見る」 |

行は薄い青（`colors.highlightBackground`）の角丸の面に乗せる ── レシートの他の行と同じ地の色
に置くと、この行だけが持つ「押せる・pricing 画面への入口」という役割が埋もれる。帯の区画から
引く括弧線は試作段階で廃止した ── 特定の区画だけを指すのに対しこの面は帯の全幅に広がる箱で、
対応関係よりノイズのほうが目立っていた。面自体が「押せる結論」として十分目立つので、
区画との対応づけは無くても迷わず読める。

### 10.6 価格未設定時 ── 帯もレシートの利益行も未確定表示

`showsPricedAmounts(record)`（`salesPrice !== 0`）が `false` の記録では:

- **帯グラフ**は区画を持たない灰色 1 本（`UnpricedBar`）＋不活性文
  `BREAKDOWN_BAR_UNPRICED_NOTE`（「価格を入れると内訳が計算できます」)。割合も金額も出さない
- **入口行（`PricingEntryRow`）は出さない**（`RecordBreakdownBar` が `showsPricedAmounts` を
  先に見て `UnpricedBar` に分岐するので、結論行の判定にすら進まない）
- **レシートの利益行**（`ReceiptCard` の結果行）も金額の代わりに `AMOUNT_PLACEHOLDER`
  （「ーー」）を出す。0 円で売れた体の損失額をそのまま出すと、まだ価格を入れていないだけの
  記録を確定した赤字であるかのように見せてしまうため
- 帯とレシートの利益行は**同じ `showsPricedAmounts` を共有**して判定する。2 か所が別々の
  条件（例えば片方だけ `salesPrice === 0`、もう片方だけ `salesPrice <= 0`）を持つと、
  片方だけ未確定表示のまま数字が出るような食い違いが起こり得る
- 「いくらで売る?」画面の未設定時（E。§9.7）と同じ考え方 ── 3 か所（帯・レシート・分析画面）
  が同じ「価格が無いことは確定した赤字ではない」という前提を共有する

**費用側（仕入・送料・手数料・梱包）は対象外** ── これらは販売価格に依存しない値なので、
価格未設定の記録でもレシートはこれまでどおり金額を出す。

### 10.8 決定の記録

#### §10-1 帯グラフを 2 本立て・単色 1 本から積み上げ 1 本に落ち着けた
桁違いの記録（販売 1,000 円・仕入 400,000 円）で「売った」バーの塗りが 0.25% になり
空の器に見えた（2 本立て）。それを避けた単色 1 本は、今度は赤字の記録だけ内訳が読めなくなった。
区画の下限（`MIN_SEGMENT_WIDTH`）を守った積み上げならどちらも避けられる（§10.3）。

#### §10-2 入口行の状態を 4 つに畳んだ（`belowTarget` を合流させた）
§9 全画面の帯は 5 状態（`belowTarget` が独立）だが、記録詳細の 1 行にその区別を持たせると
「目標に届いているか」を短い見出しで言い切ることになり、レシートの結果行の色と役割が
重複する。1 行の主題は「floorPrice まで下げられる」だけで足りるので、
`safeWithTarget` に合流させた（§10.5）。

#### §10-3 帯の区画から引く括弧線を廃止し、面全体を押せる結論にした
括弧は特定の区画だけを指すのに対し、入口行は帯の全幅に広がる箱で、対応関係よりノイズの
ほうが目立っていた。面自体が薄い青の地で十分目立つので、区画との対応づけは無くても迷わず
読める（§10.5）。

#### §10-4 帯とレシートの利益行の未確定判定を 1 つの関数に共有させた
2 か所に同じ趣旨の条件を別々に書くと、将来どちらかだけ直して食い違う経路ができる。
`showsPricedAmounts` を両方が呼ぶことで、価格未設定の見え方が帯とレシートで必ず揃う（§10.6）。
