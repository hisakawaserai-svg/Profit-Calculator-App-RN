# 商品写真 仕様 — SPEC-V5

出典: Claude Design プロジェクト「フリマアプリUI設計の見直し」の採用案 `41a`。
記録 1 件に商品の写真を 1 枚だけ添えられるようにする。

**本書は SPEC.md / SPEC-V2.md / SPEC-V3.md / SPEC-V4.md より後発**で、
写真に関する記述が衝突する場合は本書が優先する。
UI の配置は `docs/UI-SPEC.md`（§1.2 / §1.3 / §1.4）にも反映してある。

**別書を立てた理由**: 写真は既存のどの機能にも属さない独立した追加で、
新しい列・新しい保存先（ファイル）・新しい依存（`expo-image-picker` /
`expo-image-manipulator`）・新しい後始末（実体の削除）を一度に持ち込む。
既存の書に混ぜると「DB の外に実体がある」という本機能だけの前提が分散して読めなくなる。

**触っていないもの**: 計算式（`src/logic/profit.ts`）・集計・絞り込み・CSV の列。
写真は計算にも `buildWhere` にも入らない（§5）。

---

## 0. 前提と方針

### 0.1 1 件 1 枚（決定 §6-1）

**複数枚は持たない。** 用途は次の 2 つで、どちらも代表の 1 枚で足りる:

- **値付けのときに現物を思い出す**（同じような品を何度も出していると、記録の商品名だけでは
  どれのことか分からなくなる）
- **一覧で見分ける**（「白いマグカップ」が 3 件並んだときに、写真があれば区別が付く）

複数枚にすると**カルーセル・並べ替え・1 枚ずつの削除**が要り、
記録フォーム（金額を入れる面）にその操作を載せることになる。
**1 枚 → 複数枚は後から広げられるが、逆は縮められない**（既に 3 枚入っている記録の
2 枚目以降をどうするか、という移行の問題が出る）ので、狭い側から始める。

この決定の帰結として、**写真は記録に 1 対 1 で属し、記録間で共有されない**。
記録を消せばその写真を指すものは他に無い（§1.5 の削除がそれで成り立つ）。

### 0.2 必須にしない

タグ（SPEC-V4 §0）と同じ。写真の無い記録の方が**多数派になる前提**で画面を組む
（§2.2 / §2.3 の判断はすべてここから出ている）。

## 1. データの持ち方

### 1.1 列（`sale_records.photo_file_name`）

| 列 | 型 | NULL | 既定 | 内容 |
|---|---|---|---|---|
| `photo_file_name` | text | **許容** | なし（NULL） | 写真置き場の中のファイル名（`"<uuid>.jpg"`）。NULL = 写真なし |

- **この列だけ NULL 許容**にする。他の追加列（`kind` / `site_name`）は「空文字・既定値」で
  未設定を表しているが、写真は「無い」と「空の写真」の区別が意味を持たない。
  既存行を書き換えないマイグレーション（§2.1）にもそのまま乗る。
- 型の上では `string | null`。空文字が入ってきたら保存時に NULL へ倒す
  （`repository.toRow`）── 空文字のまま入ると、表示側が壊れた URI を組み立てる。
- **インデックスは張らない。** 絞り込みにも並べ替えにも使わない（§5）。

### 1.2 画像そのものは DB に入れない（決定 §6-6）

**BLOB で持たない。** 理由:

- 1 枚 100〜300KB（§1.4）が数百件ぶん DB に入ると、**ファイル 1 個が数百 MB** になる
- SQLite は行を読むときに BLOB を跨ぐので、**写真を出さない一覧のクエリまで重くなる**
- バックアップ・書き出しのたびに全画像が動く

DB が持つのは**名前だけ**で、実体はファイルとして別に置く。
その代償が「DB とファイルの整合を自分で保つ」責任で、それを引き受けるのが §1.5。

### 1.3 保存先と名前

| 項目 | 決定 | 理由 |
|---|---|---|
| 置き場所 | **ドキュメントディレクトリ配下の `photos/`**（`expo-file-system` の `Paths.document`） | アプリ専用の領域で、OS に勝手に消されない。キャッシュディレクトリ（`Paths.cache`）は端末の空きが減ると消されるので、記録から参照するものを置けない |
| カメラロール | **書き戻さない** | 利用者のアルバムに勝手に増えるのは筋が違う。元の写真はカメラロールに残っているので、複製を作る意味もない |
| 列に入れる値 | **ファイル名だけ**（パスもディレクトリも持たない） | サンドボックスの絶対パスは再インストール・OS 更新で変わり得る。パスを保存すると、ある日を境に全部の写真が表示できなくなる |
| 名前 | **写真ごとの新しい UUID ＋ `.jpg`**（記録の id は使わない） | 記録 id を名前にすると差し替えのたびに同じ名前へ上書きすることになり、`expo-image` の（URI をキーにした）キャッシュが古い写真を出し続ける |
| ディレクトリを作る時機 | **最初の保存の直前**（idempotent） | 写真を 1 枚も使わない人に空の階層を作らない |

### 1.4 縮小と圧縮（必ず通す）

カメラロールの原寸は数 MB・長辺 4000px 級で、**そのまま置くと 1 件ごとに数 MB 積み上がる**。
使い道はサムネイル（56pt）と詳細（幅 338pt）の 2 つだけなので、次の値まで落とす:

| 項目 | 値 | 理由 |
|---|---|---|
| 長辺 | **1000px**（`PHOTO_MAX_EDGE`） | 3 倍密度でも 338 × 3 = 1014px。詳細に全幅で出しても等倍に届く |
| 品質 | **JPEG 0.7**（`PHOTO_JPEG_QUALITY`） | 拡大しなければ劣化が見えない。1000px と合わせて 1 枚 100〜300KB |
| 形式 | **JPEG に揃える** | 用途が写真（連続階調）。PNG のままだと透過も使わないのにファイルだけ数倍になる |

- **縦横比は保つ。** 長辺の側だけを指定し、もう一方は比率から決める（`resizeTarget`）。
- **長辺が上限以下なら縮小しない。** 小さい画像を上限まで引き伸ばすと、容量だけ増えて画質は上がらない。
- 大きさが取れなかった（0 以下）ときは縮小そのものを飛ばす ── 比率が出せない値で
  resize すると、縦横のどちらかが 0 の画像を作りかねない。
- `expo-image-picker` の `quality` でも一度落とし、その後 `expo-image-manipulator` で
  縮小と再圧縮を通す（保存の経路は 1 本だけなので、必ず両方を通る）。
- **切り抜き（`allowsEditing`）は使わない。** 一覧のサムネは正方形・詳細は横長で、
  どちらか一方に合わせて切ると他方が破綻する。切り抜きは表示側（`contentFit`）の仕事にする。

### 1.5 実体の後始末（この機能でいちばん壊れやすいところ）

**DB の列と実体の寿命を一致させる。** 消し忘れたファイルは画面のどこにも出ないので、
不具合として気付けないまま容量だけが増える。消す責任を次の 2 か所に分けて持つ:

| 誰が | いつ | 何を |
|---|---|---|
| **repository** | 記録を削除したとき | その記録の写真（`remove`） |
| **repository** | 更新の前後で列が変わったとき | **更新前**の写真（`update`。差し替え・写真を外す の両方） |
| **記録フォーム** | 保存・取り消し・シートを閉じたとき | **開いている間に作ったのに、列に載らなかった**ファイル |

- **repository は `expo-file-system` を知らない。** 消す口（`deletePhotoFile`）を
  外から受け取る（`db/client.ts` が渡す）── この層は Node のテストからも動かすので、
  端末に触る処理を直接持てない。おかげで「消えること」を端末なしで確かめられる（§7）。
- **実体を消すのはトランザクションを抜けてから。** 中で消すと、後続の SQL が失敗して
  巻き戻ったときに「行は残っているのにファイルだけ無い」状態になる ──
  逆（ファイルだけ残る）と違い、画面から直せない。
- **フォームの片づけが要るのは、実体と列で時機がずれるから**（§3.1）──
  実体はカメラロールから選んだ瞬間に置かれ、列に載るのは「保存」を押した瞬間。
  選び直し・取り消しの間にできる「どこからも指されないファイル」は、
  フォームが自分で控えて（`createdPhotos`）閉じるときに消す。
  **アンマウントを最後の関所にする** ── シートを下へ払って閉じたときは「キャンセル」を通らない。
- **フォームの「削除」は実体を消さない。** 保存を押すまでは元の写真に戻せなければならない。
  実体が消えるのは、保存されて列が実際に書き換わったとき（= repository の担当）。

## 2. レコード詳細（案 `41a`）

### 2.1 写真の位置

**商品名の左に正方形（88pt）。レシートカードの外側**（UI-SPEC §1.4）。

```
[ 状態バッジ  不用品 ・ 8/2 出品 → 8/9 販売（7日） ]   メタ行
[ ┌──────┐  商品名（26px 太字）        🖼 ]   ← 🖼 は写真が無いときだけ（§2.2）
[ │ 写真 │  ● タグ                        ]
[ └──────┘                                ]
[ 写真を押すと全画面で見られます                 ]
[ ┌ レシートカード（販売価格 − 内訳 = 結果）─┐ ]
```

- **レシートカードの中に入れない。** カードは金額の面（UI-SPEC §1.4）で、写真は金額ではない
  ── タグをカードの外に置いたのと同じ理由（SPEC-V4 §3.4）。
- 押すと**全画面**（地は黒で固定・`contentFit: contain` で全体を見せる）。
  画像そのものを押しても閉じる（「✕」だけだと指が届かない場合がある）。
- 写真の下（塊の下）に「**写真を押すと全画面で見られます**」の 1 行。画像には押せる印が
  付かないので、押せることは語で言う。**写真が無いときは出さない**（押す対象がない）。
- **タグはこの塊の中・商品名の下**（SPEC-V4 §3.4 の再改訂）。写真が隣で 88pt の高さを
  作るので、チップ 1 段ぶんは**縦を増やさずに収まる**。0 件なら行ごと出さない。

**全幅 196pt の帯にしない（決定 §6-9）。** 最初の実装は商品名の下に全幅の帯を置いていたが、
正方形に改めた:

| 理由 | 中身 |
|---|---|
| 写真はこの画面の主役ではない | 詳細を開く目的はふつう金額の確認。帯にするとレシートカードが毎回 1 画面ぶん下へ落ちる |
| 画面の形を写真の有無で変えない | 帯は「ある/ない」で見た目が大きく変わる。正方形なら、無いときに出さなくても**商品名の位置が動かない** |
| **3 つの画面で並びが揃う** | 一覧の行（左に 56pt の枠）・フォーム（左に 72pt の枠）・詳細（左に 88pt）。同じ記録を 3 面で見るので、写真と名前の位置関係が画面ごとに入れ替わらない |
| 大きく見る口は別にある | 押せば全画面（等倍まで見える）。常時大きく出す必要がない |

**大きさは 3 面で少しずつ変える**（56 / 72 / 88pt）。詳細がいちばん「1 件を見る」面なので最大にする。

**ピンチでの拡大は入れない（決定 §6-5）。** 保存する画像は長辺 1000px（§1.4）で、
全画面に広げた時点でほぼ等倍まで見えている ── 拡大しても増える情報がない。
入れるとしたら「保存する画素数を増やす」方が先で、その判断が済むまでは持たない。

### 2.2 写真が無いときの足す口（決定 §6-4）

**節そのものを出さず、商品名の行の右端に写真アイコンだけを置く。** 押すと編集フォームが開く。

| 案 | 形 | 採否 |
|---|---|---|
| A | 写真と同じ大きさの枠に「写真を追加」 | **却下**。写真の無い記録の方が多い前提なので、開くたびに空の枠が出て「追加を急かされている」画面になる |
| B | 同じ位置に青いリンク 1 行（高さ 30pt） | 却下。A よりは軽いが、多数派の記録で常に 1 行を消費する |
| **C（採用）** | **商品名の行の右端に写真アイコン**（`image-outline`・青・24px） | **縦を 1pt も使わない**。写真が出る位置（商品名の左）と同じ行にあるので、押した結果が現れる場所とも近い |

- 何も出さない案は採らない ── 「どこから写真を足すのか」が分からなくなる
  （編集フォームの中にはあるが、そこに気付くとは限らない）。
- **語が出ないぶんは読み上げ語で補う**（`accessibilityLabel = "写真を追加"`）。
  これが C の唯一の弱点で、アイコンだけで意味が伝わることに賭けている。
- 写真があるときはアイコンを出さない（写真そのものが出ているので、足す口は要らない）。
  差し替え・削除は編集フォームから（タグ・販売サイト名と同じ扱い）。

### 2.3 一覧の行（採用案 `41a` の本体）

**記録タブ・データタブの行の左に、写真の有無にかかわらず常に 56pt の枠を置く。**

| 状態 | 枠の中身 |
|---|---|
| 写真あり | サムネイル（`contentFit: cover`・角丸 8pt） |
| 写真なし | **薄い枠**（ヘアラインの角丸＋薄い画像アイコン）。押せる印は付けない |

**これが `41a` を採った理由そのもの**（決定 §6-3）:

> 写真のある行だけサムネを出すと、**商品名の左端が行ごとに揺れる**。
> 写真の無い記録の方が多い前提なので、揺れる側が多数派になる。

- 行の高さは **56pt ＋ 上下 13pt = 82pt**。タグの付いた行だけ 3 段目ぶん伸びる（従来どおり）。
- 一覧から写真は足せない（枠は押せない）。足すのは編集フォーム（§3）。
- **データタブの「選択日の一覧」も同じ `RecordRow`** なので同時に反映される（UI-SPEC §6-11）。
  同じレコードが画面によって違う形で出ないための共用なので、片方だけ変えない。

## 3. 記録フォーム（案 `41a`）

### 3.1 写真の欄の位置

**商品名の左に正方形（72pt）。** 見出しの行は持たない。

```
[ 売れた記録                        出品中にする ]  見出し行
[ ┌──────┐  商品名                        ]
[ │ 写真 │  商品名（必須）                 ]
[ └──────┘                                ]
[ タグ  ◯洋服 ✕   ＋                        ]
[ 種別セレクタ                               ]
[ 販売価格 … 以下、金額の積み上げ             ]
```

- **見出し「写真（任意）」＋ 88pt の欄を商品名の上に積む形（最初の実装）から改めた**
  （決定 §6-9）。写真は任意で、付けない記録の方が多い（§0.2）── 専用の 1 段を常に取ると、
  伝票（商品名 → タグ → 種別 → 金額）の読みの前に、多くの場合は空の欄が挟まる。
  商品名の横に畳めば**縦を 1pt も使わない**。
- **左に置くのは一覧・詳細と揃えるため**（§2.1 の表）。
- **金額の積み上げの中に入れない**（タグと同じ理由。SPEC-V4 §3.1）。
- **写真の有無で行の高さは変わらない** ── 枠の高さ（72pt）は商品名（22px）＋
  キャプション（12px）とほぼ同じで、行の高さを写真が決めない。
- **写真なし**: 破線の枠 ＋ 画像アイコン ＋「写真」（青）。**押せる場所であることを形で言う**
  ── 実線の枠だと「写真が出る場所」に見えて、押せることが読めない。
- **写真あり**: サムネイル ＋ **右上に「✕」**（濃いグレーの丸）。

### 3.2 選ぶ・差し替える・外す

- **カメラロールから選ぶ**（`expo-image-picker` の `launchImageLibraryAsync`）。
- **カメラは起動しない（決定 §6-2）。** 販売サイトにも載せる使い方を想定すると、
  写真は先にカメラロールへ撮ってある。カメラを足すと権限
  （`NSCameraUsageDescription`）も選択肢も増えるので、要るようになってから足す。
- 複数選択は付けない（§0.1。選ばせた後に 1 枚へ落とすことになる）。
- **差し替えは枠そのものを押す**（もう一度カメラロールが開く）。**外すのは枠の右上の「✕」**
  ── 口を 2 つ並べず、タグのチップと同じ作法にする。消えるのは**写真だけ**で、記録は消えない。
- 選んでから保存が終わるまでは枠を押せなくする（二重に開かせない）。

### 3.3 権限を拒否されたとき

**アプリの中では直せない**ので、行き先まで出す:

```
写真へのアクセスが許可されていません。  設定を開く
```

- 「設定を開く」は `Linking.openSettings()`。
- 利用者がシートを閉じただけ（`canceled`）のときは**何も出さない** ── 選んだ結果なので伝えることがない。
- 縮小・保存に失敗したときは「写真を保存できませんでした。」だけ。原因は端末側で、言えることがここまで。
- `app.json` の `expo-image-picker` プラグインで `photosPermission` を渡す
  （`cameraPermission: false` でカメラの権限文言は生成させない。§3.2）。

### 3.4 計算タブには置かない

**タグと同じ**（SPEC-V4 §3.4 / 決定 §9-4）。計算タブは金額を試算する面で、
まだどの品のことかも決まっていない。`siteName` のように state で引き継ぐこともしない
（`InitialAmounts` は写真を持たない）。

## 4. マイグレーション

`drizzle/0005_dry_ted_forrester.sql`:

```sql
ALTER TABLE `sale_records` ADD `photo_file_name` text;
```

- **バックフィルをしない。** 既存の記録に写真は無いので、埋める値がない（NULL のままが正しい）。
- 既存の行は 1 列増えるだけで、他の値は一切動かない（§7 で検証する）。
- `kind` の追加（SPEC-V2 §2.2）と違って `DEFAULT` も要らない ── NULL 許容なので、
  既存行は自動的に NULL になる。

## 5. CSV には出さない（決定 §6-7）

**書き出しの列は 1 つも増やさない**（SPEC-V3 §5.3 / §5.3.1 のまま）。

- 表計算で開くものに画像を入れる場所がない。
- **ファイル名を書いても意味がない** ── そのファイルは端末の中にあり、他所では開けない。
  「`a1b2c3.jpg`」という列が増えるだけで、読む人には何の情報にもならない。

**ただしバックアップとしては不完全になる。** CSV を読み込んでも写真は戻らない ──
`sale_records` の他の列と違って、CSV に**書き出せていない情報がある**のはこの列が初めて。
写真が入ったことで「CSV だけで完全に復元できる」が成り立たなくなったので、
**ZIP でのバックアップ**（CSV ＋ 画像フォルダを 1 ファイルにまとめる）を
`docs/IMPROVEMENTS.md`「ZIP でのバックアップ」に記録した。

同じ理由で、**絞り込みにも並べ替えにも使わない**（「写真のある記録だけ」は作らない）。
条件を増やすほど絞り込みの面が重くなり、写真の有無は分類ではないため。

## 6. 要確認への決定

### 6-1. 1 枚か複数枚か
**決定: 1 件 1 枚。** 用途（値付けのときに思い出す / 一覧で見分ける）は代表の 1 枚で足りる。
複数枚はカルーセル・並べ替え・1 枚ずつの削除が要り、金額を入れる面が一段重くなる。
**1 枚 → 複数枚は後から広げられるが、逆は縮められない。**（§0.1）

### 6-2. カメラを入れるか
**決定: 今回は入れない。** 販売サイトにも載せる使い方では、写真は先にカメラロールにある。
権限と選択肢が増えるので、要るようになってから足す。（§3.2）

### 6-3. 一覧に写真の枠を常設するか（案 `41a` vs 出す・出さない）
**決定: 常設する（案 `41a`）。** 写真のある行だけサムネを出すと商品名の左端が行ごとに揺れ、
**写真の無い記録の方が多い前提なので揺れる側が多数派になる。**（§2.3）

### 6-4. 詳細で写真が無いときに何を出すか
**決定: 商品名の行の右端に写真アイコンだけ（案 C）。**
196pt の枠（案 A）も 1 行のリンク（案 B）も、多数派である写真の無い記録で
毎回「追加を急かされている」画面を作る。何も出さないと足す口が分からない。
**縦を使わずに押せることだけが分かる**形に落とし、語は読み上げ語で補う。（§2.2）

### 6-5. 全画面でピンチ拡大できるようにするか
**決定: 入れない。** 保存する画像は長辺 1000px なので、全画面に広げた時点で
ほぼ等倍まで見えており、拡大しても増える情報がない。
先に検討すべきは「保存する画素数を増やすか」の方。（§2.1）

### 6-9. 詳細・フォームで写真をどれくらい大きく出すか（実装時に改訂）
~~**決定: 詳細は全幅 196pt の帯／フォームは見出し ＋ 88pt の欄を商品名の上。**~~

> **改訂（実装済み）。決定: どちらも「商品名の左の正方形」にする**（詳細 88pt / フォーム 72pt）。
>
> 実機で見て、**帯も専用の欄も「写真がこの画面の主役だ」と言い過ぎている**と判断した。
> 詳細を開く目的はふつう金額の確認で、帯にするとレシートカードが毎回 1 画面ぶん下へ落ちる。
> フォームは金額を入れる面で、多数派である写真なしの記録では空の欄が 1 段挟まる。
> 商品名の横に畳めば**縦を 1pt も使わず**、大きく見たいときは押して全画面（§2.1）。
>
> 併せて**一覧（56pt）・フォーム（72pt）・詳細（88pt）で「写真が左」に揃えた** ──
> 同じ記録を 3 つの画面で見るので、写真と名前の位置関係が画面ごとに入れ替わらないようにする。
> 大きさだけを変えるのは、面ごとに「1 件をどれくらい見る場所か」が違うため。
>
> **タグ（SPEC-V4 §3.4）も詳細では商品名の下に戻した** ── 写真が隣で 88pt の高さを作るので、
> チップ 1 段ぶんは縦を増やさずに収まる。レシートカードの下へ逃がしていた理由
> （可変長で金額の面を押し下げる）が、この形では薄くなる。

### 6-6. 画像を DB に入れるか、ファイルにするか
**決定: ファイル。DB には名前だけ。** BLOB は DB を数百 MB に膨らませ、
写真を出さない一覧のクエリまで重くする。代償（DB とファイルの整合を自分で保つ）は
§1.5 の分担で引き受ける。（§1.2）

### 6-7. CSV に出すか
**決定: 出さない。** 表計算に画像の置き場がなく、ファイル名を書いても端末の外では開けない。
**代わりにバックアップが片道でなくなった（不完全になった）ことを IMPROVEMENTS に記録する。**（§5）

### 6-8. 列を NULL 許容にするか、空文字にするか
**決定: NULL 許容。** 既存列は空文字・0 で未設定を表しているが、写真は
「無い」と「空の写真」の区別が意味を持たない。バックフィルの要らない
マイグレーション（§4）にもそのまま乗る。空文字が来たら保存時に NULL へ倒す。（§1.1）
