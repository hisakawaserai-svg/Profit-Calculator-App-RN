# タグによる分類と絞り込み 仕様 — SPEC v4

記録に「洋服」「食器」などの**タグ**を付け、後から絞り込めるようにするための仕様。
`docs/IMPROVEMENTS.md`「タグによる分類」（未着手）と「絞り込みの拡張 / 販売サイトでの絞り込み」
（同項が「実装するなら絞り込み UI をまとめて設計する必要がある」と書いていた）を、
**1 つの絞り込み UI にまとめて**確定させる。
実装前に確定させるための文書であり、この時点ではコードは変更しない。

## 0. 前提と方針

- **タグは「入力を楽にする」機能ではなく「記録の中身を増やす」機能**（IMPROVEMENTS の分類そのまま）。
  プリセット（SPEC-V3）は選ぶと**欄に数値が入るだけ**で記録には残らないが、
  タグは**記録に残り、後から絞り込みの対象になる**。この違いがデータモデル（§1）と
  設定画面の置き場所（§2）の両方を決める。
- **タグは記録を参照される側になる。** プリセットが物理削除で済んだのは
  「レコードが id を参照しない」（SPEC-V3 §1.1 / §1.5）からで、タグにはその前提がない。
  よって**プリセットと同じテーブルには入れない**（§1.1）。
- **絞り込みは 1 か所にまとめる。** 種別（SPEC-V2 §4.2）・販売サイト（SPEC-V3 §1.5.1 で先送り）・
  タグの 3 つを、合計行のチップを増やすのではなく**1 枚のシート**に入れる（案 `30b`）。
  IMPROVEMENTS が「合計行に 3 つ目のチップが増えると窮屈」と書いた懸念は、
  チップを増やさないことで解消する。
- **計算式（`src/logic/profit.ts`）と `sale_records` の列は一切変更しない。**
  追加するのは新テーブル 2 本（`tags` / `record_tags`）だけ。既存の列は増やさない
  ── タグは 1 記録に複数付くので、列では表せない。
- **タグは付けなくても保存できる。** 必須にしない。入力の手間が増えて続かなくなるのが
  IMPROVEMENTS が挙げていた唯一の懸念で、必須化はその懸念をそのまま実現してしまう。

### 0.1 プリセットとタグの対比（形が違う理由）

| | プリセット（SPEC-V3） | タグ（本書） |
|---|---|---|
| 目的 | 入力を減らす | 記録を分類して後から絞り込む |
| 記録との関係 | **紐付かない**（値が欄に入るだけ） | **紐付く**（多対多） |
| 見た目 | 色 ＋ 1〜2 文字の頭文字バッジ | **色の点 ＋ 名前**のチップ |
| 数値 | 持つ（% / 円） | 持たない |
| 削除 | 物理削除で完結 | 中間テーブルの後始末が要る（§1.4） |
| 初期値 | 17 件を seed（§SPEC-V3 §2） | **seed しない**（§1.2） |

**見た目を分ける理由**（設計で確定済み）: プリセットは金額の行と 1 対 1 で位置が決まっているので
2 文字のバッジで足りる（どの行にあるかで意味が読める）。タグは**名前そのものを読む**必要があり、
長さも可変なので、色は識別の補助（点）に落とし、名前を本体にする。
**この違いは部品を分ける根拠でもある**（`PresetBadge` を流用せず `TagChip` を新設する。§2.3）。

## 1. データモデル

### 1.1 なぜ `presets` に同居させないか

| 案 | 内容 | 判断 |
|---|---|---|
| **A（採用）** | `tags` を独立したテーブルにする | **参照される側だから。** 中間テーブルの外部キーが `presets.id` を指すと、「参照されない行（プリセット 3 種）」と「参照される行（タグ）」が 1 つのテーブルに混ざり、削除の作法が `type` によって変わる。SPEC-V3 §1.1 が「消えても壊れる先がない」と書けたのは 3 種すべてがそうだったから |
| B（不採用） | `presets` に `type = 'tag'` を足す | 上記に加えて、`value`（数値）と `initial`（頭文字）が常に無意味な行が増える。編集画面も選択シートも「タグのときだけ隠す」分岐だらけになる。SPEC-V3 §0 が 3 種を 1 テーブルにしたのは**構造が同じだったから**で、構造が違うものを足すのは同じ原則の否定になる |

**色パレットは共有する。** `PresetColorKey`（8 色）と `theme.ts` の `presetTones` を
そのまま使う（§2.3）。名前に "preset" が入るが、実体は「明暗どちらでも読める 8 色の見本帳」なので
**改名しない**（参照箇所が広く、意味も変わらないため）。

### 1.2 型

```ts
export type Tag = {
  id: string;
  /** 自由入力。前後の空白を落として 1〜12 文字。「・」を含められない（§1.3） */
  name: string;
  /** 色パレットのキー（SPEC-V3 §1.3 の PresetColorKey をそのまま使う） */
  colorKey: PresetColorKey;
  /** 一覧・選択シート・チップの並び順（§1.5） */
  sortOrder: number;
};
```

| 項目 | 決定 | 理由 |
|---|---|---|
| `initial`（頭文字） | **持たない** | 名前をそのまま出すので導出する対象がない（§0.1） |
| `value`（数値） | **持たない** | タグは金額に一切関与しない |
| 初期値（seed） | **投入しない。0 件から始める**（決定 §9-7） | タグの語は扱う商材で決まる（洋服 / 食器 / 本 / 部品…）。汎用の初期値を置いても「消す手間」しか生まない。プリセットが 17 件を seed したのは「入力の型」を示す必要があったからで（SPEC-V3 §2.5）、タグは**入力欄の中で作れる**（§3.2）ので 0 件でも詰まらない |
| 色の割り当て | **追加時に「使用済みの色を避けて」自動で割り当てる。編集で変えられる**（決定 §9-8） | タグは数が増えやすく、作るたびに色を選ばせると新規作成が 2 段階になる。検索欄から作る経路（§3.2）では色を選ぶ画面自体が出せない |
| 登録件数の上限 | **なし**（決定 §9-11） | 選択シートに検索欄がある（§3.2）ので、増えても選べる |

**色の自動割り当ての規則**（`src/logic/tag.ts` の純粋関数。決定 §9-8）

```ts
/** 既存タグが使っていない色を、パレットの並び順で最初に見つけたもの。
 *  8 色すべてが使われていたら先頭から一巡する（重複を許す） */
export function nextTagColor(existing: Tag[]): PresetColorKey;
```

- 8 色を使い切った後に重複を許すのは、**名前が本体で色は補助**だから（§0.1）。
  色が被っても「◯洋服」「◯食器」は読み分けられる。使い切ったら色を増やす、という方向は採らない
  （明暗どちらでも読める色に限定したのが 8 色の理由。SPEC-V3 §1.3）。

### 1.3 検証規則

`src/logic/tag.ts`（新規・純粋関数）に置く。SPEC-V3 §1.4 と**2 点だけ違う**。

| 項目 | 規則 | 無効時の文言 |
|---|---|---|
| `name` | 前後の空白を落として **1〜12 文字**（書記素単位で数える。決定 §9-5） | 「名前を入れてください」 |
| `name` に使えない文字 | **「・」を含められない**（決定 §9-6） | 「「・」は使えません」 |
| 名前の重複 | **弾く**（前後空白を落として完全一致で比較） | 「同じ名前のタグがあります」 |
| `colorKey` | 読み出し時に `normalizePresetColor()` で正規化（SPEC-V3 §1.6 と同じ） | — |

- **12 文字**にしたのは、チップが横に並ぶ（フォームのタグ行・絞り込みシート・解除バー）ため。
  プリセットの 20 文字は 1 行に 1 つしか出ないので長くてよかった。
- **この制限を「入力欄の打ち止め」で実装しない**（SPEC-V3 §1.2 の共通規則。2026-08-11 追記）。
  `maxLength` や `onChangeText` での切り詰めは、日本語入力の**変換前のひらがな**まで数えるので、
  上限の近くで漢字に変換できなくなる（React Native は変換中かどうかを JS に出さない。
  iOS の `markedTextRange` も Android の composing span もネイティブ内部で完結している）。
  上限を超えたら**保存を止めて上の文言を出す**だけにして、入力そのものは切らない ──
  変換途中で 12 文字を超えても、確定して縮めば有効に戻る。
  プリセットの頭文字（2 文字）だけは切り詰めが要るので、そちらは `onBlur`（確定後）で行う。
- **「・」を禁じるのは CSV のため**（§5.2）。1 セルに複数のタグを「洋服・春夏物」と並べるので、
  区切り文字が名前に入ると往復で意味が壊れる。名前の側で禁じるのが最も確実で、
  書き出し時にエスケープを考えるより説明も短い。
- **重複を弾くのは、プリセットと逆の判断**（SPEC-V3 §1.4 は許可した）。
  プリセットは「見分けは色と頭文字が担う」ので同名でも困らなかったが、
  タグは**絞り込みの意味そのもの**なので、同名が 2 つあると
  「『洋服』で絞り込み中」と出したときにどちらのことか言えなくなる（§4.5 の解除バー）。

### 1.4 削除したときの中間テーブルの扱い

| 操作 | 中間テーブル | 決定 |
|---|---|---|
| タグを削除 | そのタグの行をすべて削除 | **repository が明示的に 2 文を実行する**（トランザクション内） |
| 記録を削除 | その記録の行をすべて削除 | 同上（`repository.remove` に 1 文足す） |
| 記録のタグを付け替え | その記録の行を**全消し → 入れ直し** | 差分計算をしない。1 記録あたり数件なので、消して入れ直す方が経路が 1 本で済む |

- **`ON DELETE CASCADE` に頼らない。** SQLite の外部キー制約は `PRAGMA foreign_keys = ON` が
  接続ごとに必要で、既定は OFF。expo-sqlite / better-sqlite3 のどちらでも
  「有効になっているつもり」が最も危ない（孤児行は絞り込みの件数を静かに狂わせる）。
  スキーマには `references()` を**意図の表明として書く**が、**削除の保証は repository 側で持つ**。
- **タグ削除は取り消せる**（設定画面の `UndoBar`。SPEC-V3 §3.2 と同じ扱い）。
  取り消しでは**タグ本体と、消した中間行の `recordId` の一覧の両方を書き戻す**
  ── 本体だけ戻すと、付いていた記録から静かに剥がれたままになる。
  よって `remove` は消す前の `recordId[]` を返す。

```ts
/** タグ本体と、そのタグが付いていた記録の id を返す（Undo が両方を書き戻すため。§1.4） */
remove(id: string): { tag: Tag; recordIds: string[] };
restore(tag: Tag, recordIds: string[]): void;
```

- **孤児行の掃除は持たない。** 上記 3 経路がすべてトランザクションで閉じているので、
  起動時のクリーンアップは要らない（あると「なぜ要るのか」の説明が要る）。

### 1.5 並び順

- `sortOrder` の昇順で固定。追加は末尾（`max(sortOrder) + 1`）。
  手動並べ替え・使用頻度順は実装しない（SPEC-V3 §3.4 / SPEC-V2 §7-9 を踏襲）。
- **記録に付いたタグの表示順も `tags.sortOrder` に従う。**
  中間テーブルは順序を持たない ── 付けた順を保つと、同じ 2 つのタグが記録ごとに違う並びで出る。

### 1.6 schema への影響

`src/db/schema.ts` に 2 テーブルを追加する。**既存のテーブル・列は一切変更しない。**

```ts
export const tags = sqliteTable('tags', {
  id: text('id').primaryKey(),                       // UUID（seed がないので固定 ID は不要）
  name: text('name').notNull(),
  colorKey: text('color_key').notNull(),             // PresetColorKey（§1.1 で共有）
  sortOrder: integer('sort_order').notNull().default(0),
}, (table) => [
  index('idx_tags_order').on(table.sortOrder),
]);

export const recordTags = sqliteTable('record_tags', {
  recordId: text('record_id').notNull().references(() => saleRecords.id),
  tagId: text('tag_id').notNull().references(() => tags.id),
}, (table) => [
  primaryKey({ columns: [table.recordId, table.tagId] }),   // 同じ組み合わせは 1 行だけ
  index('idx_record_tags_tag').on(table.tagId),             // タグ → 記録（絞り込み・使用件数）
]);
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 中間テーブルの主キー | **複合主キー `(record_id, tag_id)`** | 代理キー（`id`）を持たせても使い道がない。複合 PK なら「同じタグを二重に付ける」が DB の側で起きなくなり、`record_id` 先頭のインデックスも自動で手に入る（記録 → タグの引き方） |
| `idx_record_tags_tag` | **足す** | 絞り込み（§4）と使用件数（§3.3）は「タグ → 記録」の向きに引く。複合 PK は `record_id` が先頭なのでこの向きには効かない |
| 追加の列（付けた日時など） | **持たない** | 使う画面がない。中間テーブルは関係だけを持つ |
| 保存先 DB | 既存の `profit-calculator.db` | プリセットと同じ判断（SPEC-V3 §1.6） |

**マイグレーション**は `drizzle/0003_*.sql` を生成する。**手での追記は不要**（seed がないため。
SPEC-V3 §1.6 が `INSERT` を手で足したのとはここが違う）。既存行への影響もない
（`sale_records` を触らないので、バックフィルという概念自体がない）。

## 2. タグの管理画面（設定タブ）

### 2.1 どの群に置くか

**決定: 「入力を減らす」群には入れない。新しい群「記録を分類する」を作り、その下に 1 枚置く。**

| # | 群 | 項目 | 本書での変更 |
|---|---|---|---|
| 1 | （見出しなし） | 使いかた ▸ | — |
| 2 | 記録 | 新規作成時の種別 | — |
| 3 | 入力を減らす | 販売サイト / 送料 / 梱包材（`PresetSummaryCard` 3 枚） | — |
| 4 | **記録を分類する** | **タグ ▸**（カード 1 枚。登録件数と、色の点のプレビュー） | **新設** |
| 5 | データ | 書き出し（CSV）/ 記録の件数 | — |
| 6 | フッタ | バージョン表記 | — |

- **群を分けるのは目的が違うから**（§0.1）。「入力を減らす」の 3 つは
  *選ぶと欄に値が入る*もので、タグは*記録に残って後から効く*もの。
  同じ群に 4 枚目として並べると、注記（「よく使う値を登録しておくと、記録するときに選ぶだけで入ります。」）が
  タグには当てはまらなくなる。
- 群 4 の注記 1 行: 「記録にタグを付けておくと、あとから『洋服だけ』のように絞り込めます。」
- 群 3 と 群 5 の間に置くのは、**設定を「入力 → 記録 → 出力」の順に読ませる**ため。

### 2.2 一覧画面

`app/(tabs)/settings/tags.tsx` → `src/screens/TagListScreen.tsx`（新規）。

**`PresetListScreen` は流用しない。** 理由は §1.1 と同じで、
あちらは `type` パラメータ・値の列（「210円」/「10%」）・頭文字を前提に組まれている。
`type` を 4 つ目に増やすと、値の列を出すかどうかの分岐が一覧・編集・プレビューの全部に入る。
**部品（`SwipeToDeleteRow` 相当・`UndoBar`・色の丸の横並び）は流用する。**

| # | 要素 | 内容 |
|---|---|---|
| 1 | ヘッダ | 「◀ 設定」／タイトル「タグ」 |
| 2 | 一覧カード | 1 行 = **色の点 ＋ 名前 ＋ 右端に使用件数（「12 件」）**。行タップで編集シート |
| 3 | 追加行 | カード末尾に「＋ 追加」 |
| 4 | 空表示 | 「タグがありません」＋「記録を追加するときにも作れます」＋「＋ 追加」 |
| 5 | 注記 | 「タグを消しても、記録そのものは消えません。」**要素 2（一覧カード）があるときだけ出す** |

- **注記は 0 件のときは出さない**（実装時に決定）。この 1 行の仕事は、タグが記録に**紐付く**
  （§0.1）ぶんプリセットより強く働く「消したら記録も消えるのでは」という誤読を、
  先回りして打ち消すことにある。**0 件では文の前提が成り立たない** ── 消せるタグが 1 つも
  無い画面で「消しても記録は消えません」と言うのは、まだ持ちようのない疑問に答えている。
  そのとき利用者の問いは**「どう作るのか」**で、それには要素 4（空表示）が既に答えている。
  - 見た目の上でも、中央寄せの空表示の 8pt 下に左寄せ・左余白 4pt の 1 行が貼り付き、
    揃っていない塊になっていた。ただし**位置を直す形は採らない** ── 一覧があるときの
    左寄せは設定タブの他の注記と揃っていて正しく、内容が当てはまらない状態のためだけに
    2 つ目のレイアウトを持つことになる。
  - **同じ規則を `PresetListScreen` にも適用する**（SPEC-V3 §3.1）。あちらは 17 件 seed
    されるので実際には空にならないが、**同じ形のものが別の規則で動いているほうが危険**
    ── seed を変えたときや利用者が全部消したときに、片方だけ古い挙動が残る。

- **削除は左スワイプ →「削除」＋ `UndoBar`**（SPEC-V3 §3.2 と同じ形）。確認アラートは挟まない。
- ただし**使用件数が 1 件以上のタグを消すときだけ**、`UndoBar` の文言を
  「『洋服』を削除しました（12 件の記録から外れました）」にする ── 記録から剥がれたことが
  取り消しの猶予の間に読めないと、`UndoBar` が消えてから気付くことになる。
- **使用件数は状態（売れた / 出品中）を問わない全記録で数える。**
  タグは記録の属性であって状態の属性ではない。

**例外: 絞り込み画面だけは、選択中のタグ以外のすべての条件で絞った件数にする**（§4.2.1 / §3.3）。

| 場所 | 数え方 | その数字が答えている問い |
|---|---|---|
| 設定タブの一覧（本節） | 状態を問わない全記録 | 「どのタグが生きているか」 |
| 記録フォームのタグ選択シート（§3.2） | 状態を問わない全記録 | 同上 |
| **絞り込み画面（§4.2.1）** | **選択中のタグ以外のすべての条件**（状態・期間・種別・販売サイト）**で絞った件数** | **「押したら何件出るか」** |

- 上の 2 か所は**タグそのものの様子**を見る場所なので、条件は関係ない。
- 絞り込み画面は用途が違う。あの画面の数字は**「押したら何件出るか」の予告**として読まれるので、
  **下部の「この条件に合う記録 N件」と同じ集合の上で数えないと嘘になる** ──
  嘘の現れが「1 と出ている行を押して 0 件になる」。

**この例外は 2 段階で決まった。経緯を残す:**

1. まず**状態（`isSoldMode`）だけ**を織り込むことにした。出品中を見ているのに売れた記録まで
   数えていたのを直すため。
2. しかしそれでは**条件を足した場合に同じ嘘が残った** ── 種別「仕入品」＋販売サイトを選ぶと、
   「1」と出ているタグを押して 0 件になる。予告として読まれる以上、
   **下部の件数と同じ条件で数える**しかない。よって期間・種別・販売サイトも織り込む。

**選択中のタグ（`tagIds`）だけは織り込まない。理由はタグが OR だから**（§4.4）──
「洋服」を選んだ状態で「春夏物」の数字に洋服の条件をかけると `洋服 AND 春夏物` の数になるが、
実際に押すと `洋服 OR 春夏物` で件数は**増える**方向に動く。予告としてまるで逆向きの嘘になる。
タグ以外の条件で絞った数なら、押したときの結果を OR の性質を壊さずに予告できる。

### 3.1 記録フォームのタグ行

### 3.3 使用件数の引き方

**1 本のクエリで全タグぶんまとめて数える**（タグごとに 1 本引くと N+1 になる）。

```ts
/** tagId -> 件数。0 件のタグはキーごと現れないので、呼び出し側で ?? 0 する */
countsByTag(): Map<string, number>;
```

```sql
SELECT tag_id, count(*) FROM record_tags GROUP BY tag_id;   -- idx_record_tags_tag が効く
```

**状態で絞る経路は別に持つ**（§2.2 の例外 / §4.2）。**`countsByTag` は変更しない** ──
設定画面と記録フォームがそのまま使い続けるので、引数で振る舞いを変えると
呼び出し側ごとに「どちらの数え方か」を追わないと読めなくなる。

```ts
/** tagId -> 件数を isSold で絞って数える（絞り込み画面。§4.2）。0 件のタグはキーごと現れない */
countsByTagForState(isSold: boolean): Map<string, number>;
```

```sql
SELECT rt.tag_id, count(*)
FROM record_tags rt
JOIN sale_records r ON r.id = rt.record_id
WHERE r.is_sold = ?
GROUP BY rt.tag_id;
```

- こちらも**1 本のクエリで全タグぶん**数える（タグごとに引くと N+1 になるのは同じ）。
- **期間・種別・販売サイト・他のタグは織り込まない**（理由は §4.2）。

### 3.4 計算タブとレコード詳細

| 画面 | 扱い |
|---|---|
| 計算タブ | **タグ行を置かない**（決定 §9-4）。計算タブは金額を試算する面で、記録の分類はまだ決まっていない。`siteName` のように state で引き継ぐこともしない |
| レコード詳細 | **商品名の下にチップを表示のみ**（「✕」なし。決定 §9-12・**実装時に 2 度改訂**）。**レシートカードの外側**であることは一貫している ── レシートカードは「販売価格 − 内訳 = 結果」の金額の面（UI-SPEC §1.4）で、タグは金額ではないため中に入れない。編集はフォーム経由（`SiteNameRow` と同じ扱い。SPEC-V3 §1.5.1） |
| 記録一覧の行 | **出さない。** 行の情報量を増やさない（UI-SPEC §6-1 / §6-2 の方針。SPEC-V3 §1.5.1 も同じ判断） |

> **実装時に 2 度改訂した（決定 §9-12 の改訂欄も参照）。現在は「商品名の下」。**
>
> **1 度目（2026-08-11）: 商品名の直後 → レシートカードの下。**
> 理由は**タグの行が可変長**だから ── 商品名の直後に置くと、チップが折り返して
> 2 段・3 段になるにつれてレシートカードが下がり、**タグを何個付けたかで金額が
> 画面のどこに出るかが変わる**。詳細画面を開く目的はふつう金額の確認なので、そこが動くのは分が悪い。
>
> **2 度目（2026-08-12・SPEC-V5）: レシートカードの下 → 商品名の下（元の位置に近い形）。**
> 商品名の左に**写真の正方形（88pt・固定）**が入った（SPEC-V5 §2.1 / 決定 §6-9）ため、
> 商品名とタグはその隣の列に収まる ── **チップ 1 段ぶんは縦を増やさずに入る**ので、
> 1 度目の理由（可変長で金額の面を押し下げる）が薄くなった。
> チップが何段にも折り返せば塊は伸びるが、それは**タグを大量に付けた記録だけ**で起きる。
>
> **「レシートカードの外側」という決定の中身は 2 度とも変わっていない**（金額の面に
> 金額でないものを入れない）。動かしたのは外側のどちら側か・どの塊に属するかだけ。
> **0 件のときは行ごと出さない**（メモと違い、空欄を埋める操作がこの画面に無い）。
>
> 現在の並びは **メタ行 → [写真 | 商品名・タグ] → レシートカード → 状態カード → メモ**
> （UI-SPEC §1.4）。

### 4.2 絞り込みページ（案 `33c` / `35a`〜`35f` で改訂）

> **案 `33c` で改訂（実装済み）。** 当初は**下から出るシート**で、販売サイトだけが 2 枚目に
> 分かれていた ── 3 条件のうち 1 つだけ操作の深さが違う。
> **記録タブの Stack に積む 1 枚のページ**に変えると、3 条件が同じ深さで縦に並び、
> タグが数十件になっても縦に伸ばせる。中身の詰めは案 `35a`〜`35f`（§4.2.1〜§4.2.3）。

| # | 要素 | 内容 |
|---|---|---|
| 1 | ヘッダ | 左「‹ 記録」（戻る）／中央「絞り込み」／右「すべて解除」。**「完了」は置かない** |
| 2 | 種別 | セグメント「すべて / 不用品 / 仕入品」（`KIND_FILTER_OPTIONS` をそのまま使う） |
| 3 | 販売サイト | **単一選択のカード**。先頭に「すべて」の行、以下に候補。同じページの中に開いたまま並べる（2 枚目に分けない）。**件数の上限は持たない**（決定 §9-10） |
| 4 | タグ | **複数選択の行**（§4.2.1）。1 行 = 色の点 ＋ 名前 ＋ 右端に使用件数。2 つ以上選ぶと **OR** |
| 5 | 下部 | 「この条件に合う記録」＋件数（§4.6）。0 件なら 2 行になる（§4.2.3） |

- **「完了」を置かない**のは、条件が選んだ瞬間から効くため ── 戻れば結果が見えるので、
  「完了」は閉じるだけのボタンになる。戻る導線はヘッダ左の「‹ 記録」1 つ。
- **「すべて解除」はヘッダの 1 つだけ。** 種別・販売サイト・タグの 3 つを初期値に戻す
  （**期間・検索・並び替えは動かさない**）。効いている条件が 0 件のときは非活性。
  解除の口を増やさない方針は §4.2.1（タグに「すべて」の行を置かない）と §4.2.3（0 件の帯に
  解除ボタンを足さない）でも同じ。
- **販売サイトに「すべて」の行があるのは、単一選択だから**（案 `35a`）── 選ばない状態を
  表す行が要る。複数選択のタグには要らない（§4.2.1）。
- **絞り込みの state はページが持たない。** **開いたタブの** Stack が持つ（`RecordFilterState`）──
  一覧／グラフとページが別ルートになったので、両方が同じ値を読む位置がそこになる。
  永続化しないのは決定 §9-9 のまま（置き場所が変わっただけ）。
  **データタブと共有しない**のも同じく §9-9 で、Provider を各タブに 1 つずつ置くことで守る（§6）。
- **販売サイトの候補は `presets(type='site')` ではなく、記録に実在する `site_name` の集合**から作る。

```sql
SELECT DISTINCT site_name FROM sale_records WHERE site_name <> '' ORDER BY site_name;
```

  ここは**候補の一覧を作るクエリなので `DISTINCT` が正しい**（§4.4 で `DISTINCT` を退けるのは
  レコードを引くクエリの話で、別物）。
- **上限も検索欄も置かずに始める**（決定 §9-10）。候補として並ぶのは
  「実際に使ったサイトの数」だけで、プリセットを何件登録しても増えない。
  実際に多くなってから対応する（`docs/IMPROVEMENTS.md` に記録する）。

**データタブから開いたときの違い**（§6。Step 5 で実装）

このページは**記録タブとデータタブで同じ 1 つの画面**を使う。違いは Stack の state から読む
`isSoldMode` と `scope` の 2 つだけで、画面には分岐を書かない:

| | 記録タブ | データタブ |
|---|---|---|
| 状態のセグメント | この面には無い（集計段にある） | **無い**（`isSold = true` 固定。SPEC §6.2） |
| 販売サイトの節 | 出品中では消える（下記） | **常に出る** ── 売却済みだけを見る面なので「選ぶと必ず 0 件になる」状態が起きない |
| 下部の見出し | 状態で変わる | 常に「この条件に合う記録」（`matchingRecordLabel(true)`。出品中の分岐が起きない） |
| 下部の件数・タグの使用件数 | `countRecords` / `countsByTagForFilter` | **データタブの集合で数え直す**（§6 の表） |

**出品中を選んだときの挙動**（記録タブだけの話）

| 状態 | シート |
|---|---|
| 売れた記録 | 種別 / 販売サイト / タグ の 3 節 |
| 出品中 | **販売サイトの節が消える**（種別 / タグ の 2 節） |
| 出品中 → 売れた記録 に戻す | **直前の販売サイトの指定を復元する** |

- 出品中の記録は `site_name` が空（まだ売れていないのでサイトが決まっていない。
  IMPROVEMENTS「販売サイトでの絞り込み」が挙げていた懸念そのもの）。
  節を残すと「選ぶと必ず 0 件になる欄」になる。
- 復元は**記録タブの Stack が生きている間だけ**保つ（`lastSiteName`）。
  アプリを立ち上げ直せば消える（決定 §9-9: 絞り込みは画面ローカルの state のまま。永続化しない）。
- **状態を切り替えても効いた条件は、SQL の側でも無視する**（画面で節を消すのと二重にする）。
  `isSoldMode === false` のときは `siteName` 条件を組み立てない ── 画面の見た目だけで
  条件を落とすと、復元した瞬間に「見えないのに効いている」状態を作り得る。
- **節が無い理由の説明文は置かない**（案 `35c`）。代わりに**下部の見出しを変える**:

| 状態 | 下部の見出し |
|---|---|
| 売れた記録 | 「この条件に合う記録」 |
| 出品中 | 「この条件に合う**出品中の**記録」 |

  無い欄の理由を読ませるより、無いまま短い方が迷わない ── 数えている対象が変わったことは、
  数の隣の語で言えば足りる（`matchingRecordLabel`）。

#### 4.2.1 タグの節（案 `35a` / `35b`）

- **「すべて」の行を置かない。** チェック 0 個が「絞らない」を意味するので、置くと
  ヘッダの「すべて解除」と**同じことをする口が 2 つ**になる。
  販売サイトに「すべて」があるのは**単一選択で、選ばない状態を表す行が要る**ためで、
  複数選択のタグには当てはまらない。
- **選択状態の要約（「0件選択中」など）も出さない。** 読む値が増えるだけで、
  チェックを見れば分かる。
- **選んでも行の位置を動かさない**（案 `35b`）。選択中は**名前を太字にするだけ**で、
  上へ移動させない ── 押した行が飛ぶと、次に押したい行の位置が変わる。
  探しやすさより「位置が動かないこと」を採る（探すのは検索欄の役目。§4.2.2）。
- **使用件数は「選択中のタグ以外のすべての条件」で絞った件数**（`countsByTagForFilter`。
  §2.2 の例外 / §3.3）。ここの数字は**「押したら何件出るか」の予告**なので、
  下部の件数（§4.6）と**同じ集合の上で**数えないと嘘になる。

| 条件 | 織り込むか | 理由 |
|---|---|---|
| 状態（`isSoldMode`） | ○ | 出品中を見ているのに売れた記録まで数えると予告が合わない |
| 期間（`monthKey`） | ○ | 8 月を見ているのに全期間の数だと下部の件数と食い違う |
| 種別（`kind`） | ○ | 押したら何件出るかの予告なので |
| 販売サイト（`siteName`） | ○ | 同上（`isSoldMode = false` では buildWhere の規則どおり無視される） |
| **選択中のタグ（`tagIds`）** | **×** | **織り込むと OR で逆向きの嘘になる**（下記） |

  **タグだけを外すのはタグが OR だから**（§4.4）── 「洋服」を選んだ状態で「春夏物」の数字に
  洋服の条件をかけると `洋服 AND 春夏物` の数になるが、実際に押すと `洋服 OR 春夏物` で
  件数は**増える**方向に動く。タグ以外の条件で絞った数なら、押したときの結果を
  OR の性質を壊さずに予告できる。
- 設定画面（§2.2）と記録フォームの選択シート（§3.2）は「どのタグが生きているか」を見る場所なので、
  あちらは従来どおり全記録のまま。
- **その状態に 1 件も無いタグ（「0」）も行としては出す。** 選べないタグを隠すと、
  なぜ消えたのか分からなくなる（0 と出ていれば、押しても意味がないことがその場で読める）。
- **選択の有無ではこの数字は変わらない**（選んだタグ自身の数も動かない）。
- 節の見出しは「タグ（32件）」＝**登録件数**で、選択数ではない。右に §4.4 の OR を
  「どれかが付いた記録が出ます」と言葉で置く（「OR」とは書かない。選ぶ前に読んで分かる語にする）。

**選択中の行の見た目（タグ・販売サイトの両方）**

```
[ ● 洋服                          14  ✓ ]   ← 地 rgba(0,122,255,.12) ＋ 青文字 ＋ 太字
```

- **薄い青の地 ＋ 青文字 ＋ 右端のチェック。** UI-SPEC §1.2 の期間シートが選択中に
  既にこの表し方を使っているので、アプリ内で選択中の表現が揃う。
- **地の色が主で、青文字と太字は補助。** 名前を太字にするだけでは差が弱かった。
- **タグの節と販売サイトの節に同じ扱いを入れる** ── 同じ画面で選択の表し方を 2 通りにしない。
- **タグの色の点は青地の上でもそのまま。** タグの識別色なので、選択状態で変えない
  （選択を示すのは地の色の役目）。
- チェックは**選択していなくても枠だけ確保する** ── 出し入れで幅が変わると、
  隣の使用件数が押すたびに横へ動く。行の位置を動かさない（案 `35b`）のは縦だけの話ではない。

#### 4.2.2 タグの検索欄（案 `35f`）

- タグが 1 件以上あるときは**常に出す**（0 件のときだけ出さない。§4.2.3）。
- **含む一致**（「服」で「洋服」も「こども服」も出る）。前方一致にしないのは、タグ名が
  後ろに意味の中心を置く形（「こども服」）を取り得るため。JS 側で絞る（数十件規模）。
  前後の空白は落とす（変換確定で末尾に空白が入っても見つかるように）。
- 入力中は欄の右端に ⊗、欄の外に「キャンセル」。一覧の下に「32件のうち2件が該当」。
- **検索は一覧の見え方だけを変え、絞り込みには効かせない。** 下部の件数は検索で動かない ──
  効かせると「条件は 3 つ」という決めごとが崩れ、下部の件数の意味も変わる
  （§4.6 が「下部の件数に検索語を含めない」と決めたのと同じ理屈）。
- **検索で 0 件のときは、選択中のタグが効いていることを書く**:
  「「くつ」に合うタグがありません」＋「選んでいるタグ（洋服）は、そのまま効いています。」
  検索で選択中のタグが画面から隠れることがあり、**見えていないものが効いている状態は
  言わないと「外れた」と読まれる**。選んでいるタグが無いときは 2 行目ごと出さない。
  名前は先頭 1 つ ＋「ほか N件」に畳む（青い行の `filterTagPartLabel` と同じ作法）。

#### 4.2.3 空と 0 件（案 `35d` / `35e`）

**タグが 1 件も登録されていないとき**（案 `35d`）

- 見出しは「タグ」（**件数を書かない** ── 「タグ（0件）」は下のカードと同じことを 2 度言う）。
- 検索欄は出さない（探す対象が無い）。
- カードの中に「タグがありません」＋
  「タグは記録するときに、品名の下から作れます。付けたタグはここに並びます。」
- **設定への導線は置かない。** この画面に来た用は「今ある記録を絞ること」で、設定へ飛ぶと
  用が中断し、**戻り道が記録タブではなく設定になる**。§3.2 の記録フォーム側の選択シートには
  「設定で編集する ▸」があるが、あちらは**タグを作る・直す場所**で用が違うので揃えない。

**条件に合う記録が 0 件のとき**（案 `35e`）

- 下部の帯を 2 行にし、「0件」の下に
  「2026年8月には、この3つが揃った記録がありません。」を出す。
- 月名は表示中の期間から入れる（月バーと同じ書式 `formatMonthTitle`）。
  **全期間を選んでいるときは月名を出さない**（入れる月が無いので、期間に触れない形に落とす）。
- 「この3つ」の数は**効いている条件の本数**（`activeFilterCount`）。
- 理由: **数字だけだと原因（月・条件・不具合）の区別がつかず、月のせいだと思われやすい。**
  文に月名を入れて、**期間もこの結果に効いている**ことを示す。
- **条件の名前は出さない。** §4.8 が「条件ごとの文言を作らない」と決めたのは組み合わせで
  文言が爆発するためで、**月名と本数だけなら、その決定を破らずに原因を示せる**（§4.8 も参照）。
- **帯に解除ボタンは足さない**（解除の口はヘッダの 1 つに限る）。**警告色も使わない** ──
  間違いではなく事実なので。

### 4.3 絞り込み中の青い行（案 `21d` → 案 `34a-C` で改訂）

> **案 `34a-C` で改訂（実装済み）。** 当初は合計行の下に**独立した 1 段**として出していた
> （案 `21d` の解除バー）。案 `34a` では**集計段の中に生える 1 行**にする。
> リストとは一緒に流れない固定段の中である点は変わらないが、**段数としては増えない扱い**になる。

絞り込みが 1 つでも効いているとき、集計段の下に 1 行足す。

```
▽ 仕入品・タグ「洋服」の14件だけ                          | 解除
```

| 位置 | 中身 | 押すと |
|---|---|---|
| 左（▽ ＋ 条件文） | 効いている条件と、いま出ている件数 | **絞り込みの面へ**（§4.2） |
| 右端 | 「解除」 | 3 条件を初期値へ（「すべて解除」と同じ） |

- **押せる場所が 1 行に 2 つある。** 当たり判定は右端に十分な余白を取って明確に分け、
  読み上げでも**2 つのボタン**として扱う。
- 左を押して絞り込みの面へ行けるのは、**絞り込み中はこの行が最も目に入る**から ──
  そこから直せると往復が減る。
- 文言は純粋関数で組み立てる（画面で文字列を連結しない）:

```ts
/**
 * 効いている条件を「仕入品・タグ「洋服」の14件だけ」のように連ねる。
 * 0 件なら null（行ごと出さない）。matchCount は**いま一覧に出ている件数**。
 */
export function filterSummaryText(
  filter: RecordFilter,
  tags: Tag[],
  matchCount: number,
): string | null;
```

- **末尾の語を「〜で絞り込み中」→「〜の N件だけ」に変えた**（案 `34a-C`）。件数を文に含めるのは、
  リスト上の「N 件」の行と**交代制**にしたため（§4.1 の段の図 / 案 `34a-D`）:

| 状況 | リスト上の「N 件」 | 青い行 |
|---|---|---|
| 絞り込みなし | 出す | 出ない |
| 絞り込み中 | **出さない** | 「…の N件だけ」が件数を担う |

  同じ数を 2 か所に出さないため。条件の並べ方（`・` 連結・タグの畳み込み）は変えていない。
- `matchCount` に渡すのは**いま一覧に出ている件数**（＝検索も効いた後）。
  この文のすぐ下に並ぶのがその一覧だから。シート下部の「この条件に合う記録 N 件」（§4.6）は
  検索語を含めない数なので、検索中は両者が食い違うが、**それぞれの数がそれぞれの真下にあるものを
  説明している**ので取り違えない。
- タグが 2 つ以上のときは「タグ「洋服」ほか 1 件」と畳む（全部並べると 1 行に収まらない）。
  この「ほか N 件」は**タグの数**で、末尾の「N件だけ」は**記録の数**。別物。
- 0 件に絞られても行は出す（条件が効いている事実は消えない）。空表示は §4.8。
- **条件の数と文言の対象は一致させる**（`activeFilterCount` が 2 なら、行にも条件が 2 つ並ぶ）。

### 4.4 クエリ設計 — `EXISTS` を使い、`DISTINCT` は使わない

**決定: 複数タグの OR は相関サブクエリ（`EXISTS`）で書く。`JOIN` ＋ `DISTINCT` は採らない。**

```sql
-- buildWhere に足す 1 条件（tagIds が 1 件以上のときだけ）
EXISTS (
  SELECT 1 FROM record_tags
  WHERE record_tags.record_id = sale_records.id
    AND record_tags.tag_id IN (?, ?, ...)
)
```

| 案 | 内容 | 判断 |
|---|---|---|
| **A（採用）** | `EXISTS` の相関サブクエリ | **行が増えないので `DISTINCT` が要らない。** 既存の `buildWhere` に条件を 1 本足すだけで、`filteredRecords` / `careerSummary` / `earliestMonthKey` / `filteredAndGrouped` の**4 経路すべてに同時に効く**。`idx_record_tags_tag` が効く |
| B（不採用） | `JOIN record_tags` ＋ `SELECT DISTINCT` | **集計が壊れる。** `careerSummary` / `analyticsSummary` は `sum(netProfit)` を引いており、2 つのタグが付いた記録は 2 行に増える。`DISTINCT` は行の重複を消すだけで**集計の重複計上は消せない**（`sum(DISTINCT x)` は別の意味になる）。一覧だけ直しても合計行が静かに倍になる |
| C（不採用） | `id IN (SELECT record_id FROM record_tags WHERE tag_id IN (...))` | 動作は A と同じだが、相関がないぶん SQLite が中間結果を作りやすい。A の方が既存の書き方（`sql` テンプレート）にも素直に乗る |

**質問への回答**: 「複数タグの OR 検索には `DISTINCT` が必要になる」は **JOIN で書いた場合に限って正しく、
そしてその `DISTINCT` は集計クエリを直せない**。`EXISTS` にすれば `DISTINCT` は最初から不要になる。
これが本書で `EXISTS` を採る決定的な理由。

**AND 検索（選んだタグをすべて持つ）は V4 では持たない**（設計で OR 固定と確定済み）。
必要になったら `EXISTS` をタグの数だけ `AND` で並べるだけで足りる（構造を変えずに拡張できる）。

### 4.5 既存の `buildWhere` との関係

`RecordListFilter` に 2 つ足す。**型の追加だけで、既存の 3 条件（`isSold` / `monthKey` / `searchText` / `kind`）は
一切変更しない。**

```ts
export type RecordListFilter = {
  isSoldMode: boolean;
  searchText?: string;
  monthKey?: string | null;
  kind?: RecordKind | null;
  /** 販売サイト名の完全一致（§4.2）。null/undefined = すべて。isSoldMode=false のときは無視される */
  siteName?: string | null;
  /** タグの OR 条件（§4.4）。空配列・undefined = すべて */
  tagIds?: string[];
};
```

```ts
function buildWhere(filter: RecordListFilter): SQL {
  const conditions: SQL[] = [eq(saleRecords.isSold, filter.isSoldMode)];
  // …既存の monthKey / searchText / kind はそのまま…
  if (filter.isSoldMode && filter.siteName) {
    conditions.push(eq(saleRecords.siteName, filter.siteName));
  }
  if (filter.tagIds && filter.tagIds.length > 0) {
    conditions.push(sql`EXISTS (…)`);
  }
  return sql.join(conditions, sql` AND `);
}
```

**5 つの条件の組み合わせ**

| 条件 | 出所 | リスト本体 | 合計行（`summaryFilter`） |
|---|---|---|---|
| 状態（`isSold`） | 合計行のセグメント | ○ | ○ |
| 期間（`monthKey`） | 月バー・期間シート | ○ | ○ |
| 検索（`searchText`） | ヘッダの ⌕ | ○ | **×** |
| 種別（`kind`） | 絞り込みシート | ○ | ○ |
| **販売サイト（`siteName`）** | 絞り込みシート | ○ | **○** |
| **タグ（`tagIds`）** | 絞り込みシート | ○ | **○** |

- 検索だけが合計行に効かないのは既存の決定（「検索は探す操作で、見る対象そのものの限定ではない」。
  `RecordListScreen` のコメント / SPEC-V2 §4.2）。**販売サイトとタグは種別と同じ「限定」なので合計行にも効く。**
  これは「タグ『洋服』で絞ったときの収支合計」を見たいという機能の目的そのもの。
- **期間シートの月グリッド（`monthsWithRecords`）は絞り込みを一切受け取らない方針を維持する**
  （UI-SPEC §1.2 の派生決定）。タグでも変えない ── 絞り込むたびにグリッドの濃淡が変わると
  期間選びの手がかりとして当てにならなくなる、という理由はタグでもそのまま成り立つ。

### 4.6 シート下部の「この条件に合う記録 N 件」

repository に件数だけを返す 1 本を足す。

```ts
/** buildWhere と同じ条件での件数（§4.2 の下部表示）。集計はしない */
countRecords(filter: RecordListFilter): number;
```

- ページは**下書きの条件**を持ち、変わるたびにこれを引く。同期クエリで数千件規模
  （SPEC-V2 §8-6）なので、タップごとに引いて問題にならない。一覧そのものは引かない
  （要るのは数だけ。`useFilteredRecordCount`）。
- 検索語は含めない（合計行と同じ扱い）。
- **ページにはタグの検索欄があるが、これもこの件数には効かない**（§4.2.2）──
  あれが変えるのは**タグ一覧の見え方だけ**で、絞り込みの条件ではない。
  効かせると「条件は 3 つ」という決めごとが崩れ、この件数の意味も変わる。
- 見出しは状態で変わる（出品中では「この条件に合う**出品中の**記録」。§4.2 / 案 `35c`）。
- 0 件のときは帯が 2 行になる（§4.2.3 / 案 `35e`）。

### 4.7 タグが消えたときの絞り込み

別画面（設定タブ）でタグを消すと、`tagIds` に存在しない id が残り得る。

- **画面復帰時（`useFocusEffect`）に、生きているタグの id へ絞り直す。**
  `EXISTS` は存在しない id を単に無視するので SQL は壊れないが、
  **解除バーの文言と N の数が実体と合わなくなる**（消えたタグの名前が引けない）ので、state 側で落とす。
- すべて落ちて 0 件になったら、その条件は解除された扱いになる（バーも消える）。

### 4.8 0 件のときの空表示（記録タブの一覧）

**ここで決めるのは記録タブの一覧の空表示**であって、絞り込みページの下部（§4.2.3）とは**別物**:

| 場所 | 何を出すか | なぜ違うか |
|---|---|---|
| 記録タブの一覧（本節） | 「条件に合う記録がありません」＋「絞り込みを解除」リンク | 一覧が空なので、**次にできること**を示す場所がここしかない |
| 絞り込みページの下部（§4.2.3） | 「0件」＋「2026年8月には、この3つが揃った記録がありません。」 | 条件を触っている最中なので、**いま出している条件の結果**を説明する。解除の口はヘッダにあるのでリンクは足さない |

**§4.2.3 の文が本節の決定を破っていない理由**: 本節が「条件ごとの文言を作らない」と決めたのは、
効き得る条件が 6 つあり**組み合わせごとに書くと爆発する**ため。§4.2.3 が出すのは
**月名と条件の本数だけ**で、条件の名前は 1 つも出さない ── 文言の数は組み合わせで増えず、
それでも「月も効いている」という原因の切り分けは示せる。

**決定（§9-13）: 文言を 1 つに統一し、条件の名前は出さない。**

| # | 要素 | 内容 |
|---|---|---|
| 1 | 見出し | 「条件に合う記録がありません」 |
| 2 | リンク | 「絞り込みを解除」（種別・販売サイト・タグを初期値へ。「すべて解除」と同じ） |

- **条件ごとの文言を作らない。** 効き得る条件は 6 つ（状態・期間・検索・種別・販売サイト・タグ）で、
  組み合わせごとに文言を書くと爆発する。SPEC-V2 の段階では検索と種別の 2 つしかなかったので
  出し分けられていたが、本書でその前提が崩れる。
- **既存の `ListEmpty` の 2 通りの出し分け（検索中 / 種別で絞り込み中）も、この 1 文言に統合する。**
  「ほかの月にはあるかもしれません」のような推測の文も落とす ── 期間も条件の 1 つになったので、
  特定の条件だけを名指しして示唆する根拠がなくなる。
- **1 件も記録がないとき**（絞り込みが 0 件で、かつ記録が 0 件）は従来どおり別の空表示を出す
  （「まだ記録がありません」＋ 追加への導線）。**絞り込みの有無で 2 通り**に整理する。
- 検索中の 0 件もこの文言にする。検索欄はヘッダに出たままなので、
  何で絞れているかは画面から読める。

### 5.1 前提 — CSV はまだ実装されていない

> **タグの列が入るのは「データ保存用」だけ**である（§5.3 の追記を参照）。

SPEC-V3 §5 の CSV は **Step 5・6 が未着手**（設定タブの行は「準備中」のまま）。
したがって本書は **SPEC-V3 §5.3 の 17 列の表を 18 列に改訂する**。
実装がまだなので「後から列を足す」のではなく、**最初から 18 列で作る**。

### 5.2 決定 — 1 列に「・」で並べる

**決定: タグは 1 列。1 件の記録に付いた複数のタグを「洋服・春夏物」と 1 セルに並べる。**

| 案 | 内容 | 判断 |
|---|---|---|
| **A（採用）** | 1 列に区切り文字で並べる | **1 行 = 1 記録**が保てる。列数がデータの中身で変わらない。表計算では `COUNTIF(範囲,"*洋服*")` で扱える |
| B（不採用） | タグ 1 / タグ 2 / タグ 3 … と列を展開 | **列数がその時の最大タグ数で変わる**。ヘッダが書き出しごとに変わると、取込側の設定を毎回やり直すことになる。SPEC-V3 §5.2 が「出力は 1 種」に統一した趣旨にも反する |
| C（不採用） | タグごとに行を複製（1 行 = 1 記録 × 1 タグ） | **金額が重複計上される。** 2 つタグが付いた記録は販売価格も収支も 2 回足される。SPEC-V3 §5.4 が「CSV の中で足し算が合う方を採る」と決めた原則を真っ向から壊す |
| D（不採用） | タグごとに 0/1 の列を立てる（ダミー変数） | 列数がタグの登録数で変わる（B と同じ問題がより強く出る） |

**区切り文字は「・」1 文字。タグ名に「・」を使えなくする**（§1.3 の検証で禁じる）。

- エスケープを設計するより、**入力の側で 1 文字を予約する方が説明も実装も短い**。
  設定画面で「・」を打った瞬間に理由が出る（「「・」は使えません」）ので、
  書き出してから気付く経路にならない。
- 「,」を使わないのは CSV の区切りと衝突するため（引用で回避できるが、
  表計算の「区切り位置」でセル内を分割したいときに使えない）。
- **並び順は `tags.sortOrder` 昇順**（画面の表示と同じ。§1.5）。
  書き出すたびに並びが変わらないので、差分を取れる。
- タグなしの記録は**空文字**（SPEC-V3 §5.4「空値は空文字」に従う）。

### 5.3 改訂後の列（18 列）

SPEC-V3 §5.3 の 17 列に**14 列目として「タグ」を挿入**する。以降の列は 1 つずつ後ろへずれる。

| # | 列名 | 出所 | 備考 |
|---|---|---|---|
| 1–12 | （SPEC-V3 §5.3 のまま） | | **先頭 3 列の固定は変わらない**（販売日 / 商品名 / 販売価格） |
| 13 | 種別 | `kind` | |
| **14** | **タグ** | `record_tags` → `tags.name` | **新設。「洋服・春夏物」。なしは空** |
| 15 | 状態 | `isSold` | 旧 14 |
| 16 | 出品日 | `saleStartDate` | 旧 15 |
| 17 | メモ | `memo` | 旧 16 |
| 18 | 記録ID | `id` | 旧 17。**末尾のまま** |

- **12（販売サイト）と 13（種別）の隣に置く**のは、この 3 つが「属性の群」だから
  （SPEC-V3 §5.2 の並び「内訳 → 計算値 → 属性 → メモ → 記録ID」に従う）。
- 「メモ」より前に置くのは、メモが改行を含み得る（引用が必要な）列で、
  その後ろに読みたい列を置くと表計算で目視しづらいため。

**2026-08-12 追記: タグの列が入るのは「データ保存用」だけ**（SPEC-V3 §5.2 の改訂で
書き出しが 2 種類になった）。上の 18 列はデータ保存用の表である。

| 種類 | タグの列 | 理由 |
|---|---|---|
| **データ保存用**（18 列） | **あり**（14 列目） | 主用途がバックアップ（SPEC-V3 §0.1）。記録した内容がすべて残る必要がある |
| **確定申告用**（11 列。SPEC-V3 §5.3.1） | **なし** | 帳簿に関係がなく、**個人的な記述が混ざる**（メモを外したのと同じ理由）。タグ名は利用者が自由に付ける語なので、税務の書類に持ち込む前提で書かれていない |

- 帰結として、**確定申告用ではタグを引くクエリ自体を投げない**（`tagNamesByRecord` は
  データ保存用のときだけ呼ぶ。`src/db/useExport.ts`）。
- 「日ごとにまとめる」（SPEC-V3 §5.2.2）が確定申告用にしか無いのも、この列の有無と同じ根拠 ──
  **タグとメモは合算できない**ので、18 列のままではまとめられない。

### 5.4 書き出しクエリへの影響

- `listForExport()`（SPEC-V3 §6.1）は `SaleRecord[]` を返す設計だった。
  **タグは 1 対多なので同じ行に載らない。** よって書き出し用に 1 本足す:

```ts
/** 対象の記録に付いたタグを 1 本のクエリでまとめて引く（記録ごとに引かない） */
tagNamesByRecord(recordIds: string[]): Map<string, string[]>;
```

- `csv.ts` は**純粋関数のまま**にする（SPEC-V3 §6.1 の方針）。
  引数を `(records, tagsByRecord)` の 2 つにして、DB は呼び出し側が引く。
- **書き出しの絞り込みにタグは使わない**（決定 §9-14）。`ExportSheet` が持つのは期間と対象だけ
  （SPEC-V3 §5.5）。CSV の主用途はバックアップ（SPEC-V3 §0.1）で、
  絞り込んだ書き出しは「一部しか保存されていないファイル」を作る事故の方が大きい。
  タグごとの集計は書き出した後に表計算側で行う（§5.2 の `COUNTIF`）。

## 6. データタブへの影響

**決定: 適用する。** ただし記録タブと同じ形にするのではなく、**同じシートを状態の節なしで使う**。

| 項目 | 記録タブ | データタブ |
|---|---|---|
| 状態 | セグメント（売れた記録 / 出品中） | **なし**（`isSold = true` 固定。SPEC §6.2） |
| 期間 | 月バー | 月バー（共用） |
| 絞り込みシート | 種別 / 販売サイト / タグ | **同じ 3 節**（販売サイトの節は常に出る） |
| 現状の種別チップ（巡回） | 廃止 | **廃止**（記録タブと揃える） |
| 絞り込みの state | 画面ローカル | **画面ローカル。記録タブとは共有しない**（決定 §9-9） |

- データタブは元から売れた記録だけを見る面なので、**販売サイトの節を消す分岐が要らない**
  （§4.2 の分岐は記録タブ側だけの話）。
- `AnalyticsFilter` に `siteName` / `tagIds` を足し、`buildAnalyticsWhere` に
  `buildWhere` と**同じ `EXISTS` の式**を足す。式は共通の関数に切り出して 1 か所で持つ:

```ts
/** タグの OR 条件（§4.4）。buildWhere / buildAnalyticsWhere の両方が使う */
function tagExistsSql(tagIds: string[]): SQL;
```

- **チャート（`aggregatedPoints`）にも同じ条件が効く**。集計式（`netProfitSql` 等）は変更しない ──
  `EXISTS` は行を増やさないので、SUM はそのまま正しい（§4.4 の A を採った帰結）。
- これで IMPROVEMENTS が挙げていた「『洋服だけの売上』が見えると仕入れの判断材料になる」が
  データタブのグラフとして満たされる。**タグ機能の主目的はここにある**ので、
  データタブへの適用は「余力があれば」ではなく**必須の範囲**として扱う。

#### 実装（Step 5。案 `36b` で上部も作り替えた）

**上部の割り付けは案 `36b`**（UI-SPEC §1.5 に全面反映）:

```
[ ヘッダ                                    データ   ？ ]
[ 月バー           ◀  2026年8月 ▾  ▶   │  ▽        ]  ← 右端が絞り込みの入口
[ ▽ タグ「洋服」の14件だけ                     解除 ]  ← 絞り込み中だけ
[ この月の収支                        売上  ¥15,145 ]  ← 集計段（収支が主役）
[ ¥12,686                            経費   ¥2,460 ]
```

- **種別セグメントは廃止。** 種別は絞り込みページの中の 1 節に一本化した（表の「現状の種別チップ」の行）。
  集計段から操作が消え、値を読む場所になる。
- **集計段は収支が主役**（3 値を対等に並べない）。理由は UI-SPEC §1.5。
  **記録タブの `SummaryBar` とは共用しない** ── あちらは 2 値で対等、こちらは 3 値で収支が主役で、
  骨格が違う。共用するのは青い行（`FilterNoticeRow`）だけ。
- **青い行は月バーの直下**（記録タブは集計段の中。§4.3）── 集計段とグラフカードの間に挟むと
  絞り込みの有無で集計とグラフの距離が変わるが、月バーの下なら
  「期間 → 絞り込み → その結果」の順に読め、集計とグラフは常に隣り合ったまま。
- **絞り込みを変えたら選択中の棒（`selectedKey`）を外す。** 集計対象が変わるので、
  期間を変えたときと同じ扱い。条件は選んだ瞬間から効くので、変えるたびに外れる。

**絞り込みページは 1 つの画面を両タブで共用する**（§7.1 の `RecordFilterScreen`）。
ルートだけをタブごとに置く（`app/(tabs)/data/filter.tsx`）── レコード詳細と同じ形で、
記録タブのルートへ push すると戻ったときにグラフではなく記録の一覧に着いてしまう
（UI-SPEC §6-9）。**画面を 2 つに分けてコピーしない**（片方だけ直る事故を作らないため）。
違いは Stack の state から読む 2 つだけで、画面には分岐を書かない:

| 読む値 | 記録タブ | データタブ | 効果 |
|---|---|---|---|
| `isSoldMode` | セグメントで変わる | **常に true**（`isSold = true` 固定。SPEC §6.2） | **販売サイトの節が常に出る。** §4.2 の「出品中では節を消す」分岐は記録タブ側だけの話。下部の見出しも `matchingRecordLabel(true)` =「この条件に合う記録」で自然に決まる（出品中の分岐が起きない） |
| `scope`（`'records'` / `'data'`） | `'records'` | `'data'` | **件数を数える集合**（下記） |

**決定 §9-9（両タブで絞り込みを共有しない）は Provider の置き場所で守る。**
`RecordFilterProvider` を**各タブの `_layout.tsx` に 1 つずつ**置く ── 2 つは React の木の上で
兄弟なので、同じ Context を使っていても値は混ざらない。タブ全体（`(tabs)/_layout.tsx`）へ上げると
1 つになって共有されてしまうので、**絶対に上げないこと**。

**件数の数え方は記録タブと違う**（§4.6 / §4.2.1 の数字を、データタブの集合で数え直す）:

| 何の数 | 記録タブ | データタブ |
|---|---|---|
| ページ下部の「この条件に合う記録 N 件」 | `countRecords`（`buildWhere`） | **`analyticsSummary(filter).recordCount`**（`buildAnalyticsWhere`） |
| タグの行の使用件数 | `countsByTagForFilter` | **`analyticsCountsByTagForFilter`** |

- データタブは **`isSold = true` かつ `saleDate` 非 null が固定条件**（SPEC §6.2）で、
  記録タブの `buildWhere` は後者を持たない。そのまま使うと、下部の数もタグの行の数字も
  **グラフが集計している集合と食い違う**。
- 下部の件数に `analyticsSummary.recordCount` を使うのは、**合計行とまったく同じ 1 本から取る**ため
  （記録タブが `summaryFilter` の `recordCount` を使っているのと同じ形）。
  別々に条件を組み立てると、片方だけ直したときに食い違う。
- タグの行の数字は記録タブと**同じ考え方**（選択中のタグ*以外*のすべての条件で絞る。
  タグは OR なので、選択中のタグを織り込むと逆向きの嘘になる）。**集合だけが違う。**
- 青い行の「〜の N件だけ」に渡すのも `summary.recordCount`。記録タブでは「いま一覧に出ている件数」だが、
  データタブに一覧はなく、行の下にあるのはグラフ ── **グラフが何件を集計した結果か**を言うのが
  「文のすぐ下にあるものを説明する」という §4.3 の趣旨に合う。データタブには検索欄がないので、
  記録タブのような「下部の件数との食い違い」も起きない。
- **`monthsWithRecords`（期間シートの月グリッド）は絞り込みを受け取らないまま**（§4.5 / UI-SPEC §1.2）。

**§4.7（消えたタグを絞り込みから落とす）はデータタブでも必要。** 記録タブと同じく
画面復帰時（`useFocusEffect`）に `pruneMissingTags` を通す ── 通さないと青い行の文言と
条件の本数が実体と合わなくなる。

    CSV はバックアップを兼ねる（SPEC-V3 §0.1）ので、絞った書き出しは
    「一部しか保存されていないファイル」を作る事故の方が大きい。（§5.4 に反映）
