## 0. 前提と方針

- 3 種のプリセット（販売サイト / 送料 / 梱包材）は「名前・色・頭文字・数値」を持つ点で完全に同じ構造なので、
  **1 つのテーブル・1 つの編集画面・1 つの部品**で扱う。種別ごとに 3 セット作らない。
  差分は「数値の単位（% か 円）」「単一選択か複数選択か」「初期値の中身」の 3 点に閉じる（§2）。
- **販売サービス名・配送サービスの商標をアプリ側に持たない。** 初期値は
  「手数料 10%」「A4・厚さ3cm以内」のような汎用的な名前にする。理由は 2 つ:
  法的リスクの回避と、**料率・送料の改定への追従を利用者に委ねる**こと。
  名前は自由に編集できるので、利用者が「メ」「ラ」等と付け直せる（§2.5）。
- **プリセットは記録に紐付けない。** 選ぶと数値が欄に入るだけで、レコードはプリセットの id を持たない
  （§1.5）。プリセットを直したり消したりしても、過去の記録の金額は動かない。
  ただし**販売サイトの名前だけは記録に写す**（`site_name` 列。§1.5.1。決定 §8-1）── 参照ではなく
  「そのとき何と書いてあったか」の写しなので、この方針と矛盾しない。
- 計算式（`src/logic/profit.ts`）と `sale_records` の**既存の列は一切変更しない**。
  追加するのは新テーブル 1 本（`presets`）と新しい列 1 本（`sale_records.site_name`）だけ。
- CSV は**用途ごとにパターンを分けず、明細 1 種に統一する**（§5.2 で理由）。

### 0.1 データ管理の方針

**このアプリはサーバーを持たず、データはユーザーの端末にのみ保存する。**（`profit-calculator.db` と
設定の kv-store。どちらも端末内）

| 面 | 内容 |
|---|---|
| 利点 | **個人情報を預からない**ためプライバシーポリシーが簡潔になる。運用コストがゼロで、サーバー障害が起きない。ネットワークを持たないので通信の失敗経路も存在しない |
| 帰結 | **バックアップはユーザー自身の責任**になる。アプリを削除すれば記録も消える |
| だから CSV | **CSV 書き出し（§5）がそのバックアップ手段を兼ねる。** §5.1 の 3 つ目の用途「汎用的な記録保存」はここに直結する |

- この方針は `docs/IMPROVEMENTS.md`「商品写真」の項で外部通信を退けた判断（オフラインで動作しているので
  外部通信を足すとプライバシーポリシーと審査の対応が要る）と同じもので、本書はそれを前提として置く。
- ヘタに「バックアップ機能」を名乗る別機能を作らない。**書き出したファイルの保管先はユーザーが選ぶ**
  （共有シートから iCloud Drive・メール等。§5.6）。
- 端末のバックアップ（iCloud / Google）に DB ファイルが含まれるかは**未調査**。§8-14 で扱う
  （含まれるか否かでヘルプに書くこと自体が変わる）。

## 1. プリセットの共通データモデル

### 1.1 型

```ts
/** プリセットの種類。列の意味（value の単位）と選択の作法がここで決まる */
export type PresetType = 'site' | 'shipping' | 'packaging';

export type Preset = {
  id: string;
  type: PresetType;
  /** 自由入力。1〜20 文字（§1.4） */
  name: string;
  /** 色パレットのキー（§1.3）。hex ではなくキーを持つ */
  colorKey: PresetColorKey;
  /** 1〜2 文字の頭文字。空文字なら name から導出する（§1.2） */
  initial: string;
  /** site = 手数料率(%) / shipping・packaging = 金額(円)（§2） */
  value: number;
  /** 一覧・選択シートでの並び順（§3.4） */
  sortOrder: number;
};
```

| 項目 | 決定 | 理由 |
|---|---|---|
| テーブル | **1 本（`presets`）に `type` 列で 3 種を同居** | 構造が同じで、編集 UI も検証規則もほぼ共通。3 テーブルにすると同じコードを 3 回書き、画面も 3 つになる |
| `type` | 文字列 enum（`RecordKind` と同じ方針。SPEC-V2 §1.1） | DB を直接見て意味が読める。第 4 の種類（例: その他の経費）が要るとき列追加でなく値追加で済む |
| `value` | **1 列で兼用**（単位は `type` が決める） | `rate` と `amount` を別列にすると、必ず片方が NULL の行になり、検証も表示も「どちらを見るか」の分岐が全経路に増える |
| 色 | ~~**hex ではなくパレットのキー**を保存~~ → **SPEC-V7 §2.1 で hex 保存に変更**（固定色は hex を識別子として対応表を引くので、明暗の出し分けは残る） | 明暗の外観で色を出し分けるため（`theme.ts` は明暗で別の hex を持つ）。hex を保存すると暗色で沈む色が固定されてしまう |
| `initial` | 空を許し、空なら表示時に `name` から導出 | 追加のたびに 2 つの欄を埋めさせない。凝りたい人だけ上書きする |
| 削除 | **物理削除**（論理削除しない） | レコードが id を参照しない（§1.5）ので、消えても壊れる先がない |

### 1.2 頭文字（`initial`）

- **1〜2 文字。** 2 文字を超えたぶんは落とす（判定は書記素単位で行う。
  `Array.from(name)` で数えるのは、絵文字・サロゲートペアで 2 文字判定が壊れるため）。
- **切り詰めるのは「変換が確定したあと」だけ**（2026-08-11 改訂。当初は「入力欄は 2 文字で打ち止め」だった）。
  日本語入力は「ふうとう」と打ってから「封筒」に変換するので、
  **1 文字ごとに切ると変換前のひらがなが入り切らず、漢字にできない**。
  `maxLength` を使っても同じ（変換中の文字も数えられる）。
  React Native は変換中かどうかを JS に出さない ── iOS の `markedTextRange` も
  Android の composing span もネイティブ内部で完結していて、対応するイベント（`onCompositionEnd` 相当）がない。
  したがって**確定を確実に言える合図 = 欄を離れたとき（`onBlur`）**で数える。
  欄を離れずに保存を押した場合は `validatePreset` が同じ関数を通す（安全網）。
  入力中もバッジのプレビューは 2 文字ぶんしか描かない（`presetInitial` を通るため）ので、
  離れたときに縮んでも結果は見えている。
- **他の文字数制限のある欄（名前 20 文字・タグ名 12 文字。SPEC-V4 §1.3）は打ち止めない。**
  上限を超えたら**保存を止めて理由を出す**だけで、入力そのものは切らない（§1.4）。
  変換途中で一時的に上限を超えても、確定して縮めば有効に戻る。
  **文字数制限を入力の切り詰めで実装しないこと**を、以後この 3 欄の共通の規則とする。
- **空のときは `name` の先頭 1 文字を表示に使う**（保存値は空のまま）。
  導出は純粋関数 `presetInitial(preset): string` に閉じ、画面で文字列を切らない。
- 導出時に落とす文字: 先頭が半角・全角スペースなら次の文字へ進む。それ以外の加工はしない。
- 名前が空で保存されることはない（§1.4）ので、導出結果が空文字になる経路はない。

### 1.3 色

**決定（§8-3）: 8 色の固定パレットから選ぶ。カラーピッカー（自由な色指定）は持たない。**

> **SPEC-V7 で改訂。** パレットは **11 色**（8 → 10 → 11。丸を 6 × 2 に並べるため gray を追加）になり、
> **12 個目の口として自由色（カラーピッカー）を持つ**。保存形式も hex に変わった（SPEC-V7 §2.1）。
> 以下の 8 色を前提とした記述は、色数と保存形式を除いてそのまま有効。

理由: 明暗どちらの外観でも白文字が読める色に限定できること、選択肢が 8 個なら 1 行に収まる横並びで選べること。

`src/theme.ts` に `presetTones: Record<PresetColorKey, string>` を明暗それぞれ追加する。

```ts
export type PresetColorKey =
  | 'red' | 'orange' | 'yellow' | 'green' | 'teal' | 'blue' | 'indigo' | 'purple';
```

- **既存のセマンティック色（`green` = 収支プラス / `red` = 経費・マイナス / `orange` = 販売手数料）とは
  別の定義にする。** 同じ色相を使ってもよいが、`presetTones` を経由することで
  「セマンティック色を変えたらバッジの色も変わる」事故を防ぐ。
- `yellow` は白文字が乗らないので、**バッジの文字色はパレットごとに持つ**
  （`presetTones` の値を `{ background, foreground }` の対にする）。
- プリセットのバッジは**設定画面と選択シート、電卓の品名列にだけ**出る。
  金額の行（伝票カード・レシートカード）には出さないので、手数料のオレンジ等と隣接しない。

### 1.4 検証規則

`src/logic/preset.ts`（新規・純粋関数）に置き、編集シートの保存ボタンの活性・無効を決める。

| 項目 | 規則 | 無効時の文言（`labels.ts`） |
|---|---|---|
| `name` | 前後の空白を落として 1〜20 文字 | 「名前を入れてください」 |
| `initial` | 0〜2 文字（書記素単位）。空は許可 | （超えたぶんは確定後に落とすので出ない。§1.2） |
| `value`（`site`） | 0〜100。**小数第 1 位まで許す**（決定 §8-12） | 「手数料率は 0〜100 の範囲で入れてください」 |
| `value`（`shipping`） | 0〜999,999 の整数 | 「金額は 0 以上で入れてください」 |
| `value`（`packaging`） | 0〜999,999。**小数第 1 位まで許す**（§2.6.3 の単価。当初は整数のみだった） | 同上 |
| 入数 / 購入価格（`packaging` のまとめ買い） | §2.6.6 | §2.6.6 |
| 名前の重複 | **許可する**（弾かない） | — |

- 名前の重複を弾かないのは、「箱（小）」を 2 つ作って片方を直す途中の状態を禁止すると
  編集の手が止まるため。見分けは色と頭文字が担う（それがこの機能の趣旨）。
- **タグ（SPEC-V4 §1.3）では逆に重複を弾く。** 同じ「名前 ＋ 色」の仕組みに見えて扱いが違うのは、
  タグが**絞り込みの意味そのもの**を担うため ── 同名のタグが 2 つあると、
  解除バーに「タグ「洋服」で絞り込み中」と出したときにどちらのことか言えなくなる。
  プリセットは選んだ瞬間に数値が入って終わりなので、同名でも後から困らない。
- 数値の入力は既存の `sanitizeNumericInput`（`src/logic/input.ts`）をそのまま使う。
  **`input.ts` は変更しない**（UI-SPEC §7.4 の方針を踏襲）。
  同関数は許容形式 `/^\d*\.?\d*$/`（SPEC §5.1 / 決定 §7-9）なので**小数点は既に通る** ──
  `site` の小数第 1 位はフィルタを触らずに実現でき、金額側（整数のみ）の桁の切り落としは
  プリセット側の検証（§1.4）で行う。

### 1.5 レコードとの関係 — id は持たず、販売サイト名だけを写す

**決定: `sale_records` はプリセットの id を持たない（案 A）。ただし販売サイトの名前だけは
スナップショットとして 1 列持つ（案 C。決定 §8-1）。**

| 案 | 内容 | 判断 |
|---|---|---|
| **A（採用）** | 選んだ値を欄に入れるだけ。記録はプリセットを参照しない | プリセットの編集・削除が過去の記録の金額を書き換えない。外部キーも移行も要らない。金額列がこれまでどおり唯一の真実 |
| B（不採用） | `sale_records` に `siteId` 等の外部キーを持たせる | 料率を改定した瞬間に過去の記録の手数料額が変わる。プリセット削除時の後始末（NULL 化 or 参照禁止）が全経路に増える |
| **C（採用・販売サイトのみ）** | **名前だけをスナップショットで持つ**（`site_name text` 1 列） | 参照ではなく「そのとき何と書いてあったか」の写し。過去は動かないまま、CSV に「販売サイト」列を出せる |

- 案 C を採ったのは、**CSV に「どこで売ったか」が残らないと §5.1 の用途（確定申告・記録の保存）を満たさない**
  ため（決定 §8-1）。手数料率だけでは、10% のサイトが 2 つあれば区別できない。
- 送料・梱包材には同じ列を持たせない。送料は金額そのものが配送方法を表しており、
  梱包材は複数選択で 1 つの名前に落ちない（電卓の品名列に残る。§4.5）。

#### 1.5.1 `site_name` の仕様

| 項目 | 決定 |
|---|---|
| 列 | `site_name text NOT NULL DEFAULT ''`（空文字 = 未設定。NULL は使わない。既存列と同じ方針） |
| 書き込む契機 | **販売サイトのプリセットを選んだときだけ**（§4.3）。そのとき率（`commission`）と名前を同時に入れる |
| 手で率を変えたとき | **消さない。** 名前は利用者が付けた札で、率の微調整で無効になるものではない。ステッパーで 10% → 8% にしても札は残る。ただし**タグボタンのバッジは薄くし、▾ を外す**（下記「バッジの見た目」） |
| 消し方 | 手数料行の下に出る名前のチップの「✕」で消す（下記） |
| 既存レコード | 空文字（プリセットがなかったので写しようがない）。バックフィルは行わない |
| 計算・集計への影響 | **なし。** 計算式にも `buildWhere` にも入らない。当面は表示と CSV だけが読む |
| 絞り込み | V3 では**行わない**（種別フィルタのような UI は足さない）。サイトごとの集計は CSV 側で行う。**→ SPEC-V4 §4.2 で実装済み**: 絞り込みシートの中の単一選択として足す。候補は「記録に実在する `site_name`」から作るので、プリセットを消しても選べる。出品中モードでは節ごと出さない（サイトが決まっていないため） |

**表示する場所**

| 画面 | 表示 |
|---|---|
| 記録フォーム 伝票カード | 手数料行の**直下**に 1 行「{バッジ}{名前} ✕」（未設定なら行を出さない） |
| レコード詳細 レシートカード | 「− 販売手数料 (N%)」の行の下に薄く名前（✕ なし。編集はフォーム経由） |
| 計算タブ | 伝票カードと同じ形。**画面ローカルの state** に持ち、「この内容で記録する」でフォームへ引き継ぐ（`kind` と同じ。SPEC-V2 §1.4） |
| 記録一覧・データタブ | **出さない**（行の情報量を増やさない。UI-SPEC §6-1 / §6-2 の方針） |

- チップを 1 行の独立した行にするのは、手数料行（ラベル・率・タグボタン・ステッパー・額）が既に詰まっており、
  同じ行に名前を足すと収まらないため。未設定のときは行ごと出ないので、通常の高さは変わらない。

**バッジの見た目**（実装は `logic/preset.ts` の `resolvePresetTag`）

`site_name` が残ったまま率だけ変わった状態を、選択直後と同じ見た目で出すと
「プリセットの率がそのまま入っている」と読めてしまう。名前と率の**両方**を照合して 3 つに分ける。

| 状態 | 判定 | 見た目 |
|---|---|---|
| 未選択 | `site_name` が空文字 | タグアイコン ＋ ▾ |
| 選択どおり | 名前で引けたプリセットの率 == 今の率 | バッジ ＋ ▾ |
| 率だけ変更 | 名前で引けたプリセットの率 != 今の率 | **薄いバッジ（不透明度 0.4）・▾ なし** |

- ▾ を外すのは、▾ が「今ここに入っている値の出どころ」を指す印だから。
  率が既にプリセットのものでない以上、同じ印は出さない。
- **押したときの挙動は 3 つとも同じ**（選択シートが開く）。読み上げには
  状態を `accessibilityValue`（「{名前}（率は変更ずみ）」）で乗せる ── 濃さと ▾ は音にならない。
- **送料の選択シートだけは、行の中に 2 択（専用資材を使うか）が入る**
  （SPEC-V6 §3 / 採用案 `45b`）。押した時点で選択と資材の有無が同時に決まる。
- 名前で引けたプリセットの率と比べるので、**たまたま他のプリセットと同じ率になっても
  札はそのサイトのまま薄い**（10% のメルカリを 6% に下げてもラクマの札にはならない）。
- **プリセットが削除・改名されて名前で引けないときは「未選択」と同じ見た目**（タグアイコン ＋ ▾）。
  バッジの色と頭文字はプリセットの保存値そのもので、消えた行の札は描けないため
  （名前から色を作ると、同じ記録が編集のたびに違う色で出る）。
  どこで売ったかは欄の下の名前の行（`SiteNameRow`）に残るので読める。
- 薄さを色ではなく不透明度で出すのは、10 色 × 明暗 2 テーマぶんの「薄い版」を
  定義し直さずに、どの色でも同じだけ引っ込ませるため。

## 2. 3 種それぞれの固有仕様と初期値

### 2.1 種類ごとの差分

| 項目 | 販売サイト（`site`） | 送料（`shipping`） | 梱包材（`packaging`） |
|---|---|---|---|
| 設定画面の見出し | 販売サイト | 送料 | 梱包材 |
| `value` の単位 | **%**（手数料率） | 円 | 円 |
| `value` の表示 | 「10%」 | 「210円」 | 「15円」 |
| 選択の作法 | **単一選択** | **単一選択** | **複数選択** |
| 入る先 | 手数料の率（`commission`） | 送料欄（`postage`） | 梱包材欄（`envelopeCost`）※電卓経由 |
| 置き場所 | 手数料行 | 送料行 | 電卓シートの中（§4.3） |
| 初期値の件数 | 4 | 7 | 6 |
| 金額の入れ方の 2 択（§2.6） | 出さない | 出さない | **出す**（1 個ずつ / まとめ買い） |
| `value` の小数 | 第 1 位まで | 整数のみ | **第 1 位まで**（§2.6.3） |

### 2.2 初期値 — 販売サイト（手数料率）

**サービス名を持たない。**「手数料 N%」の形にし、頭文字は率の数字をそのまま入れる。

| # | 名前 | 率 | 色 | 頭文字 |
|---|---|---|---|---|
| 1 | 手数料 10% | 10 | `red` | 10 |
| 2 | 手数料 6% | 6 | `orange` | 6 |
| 3 | 手数料 5% | 5 | `blue` | 5 |
| 4 | 手数料なし（直接取引） | 0 | `green` | 0 |

- 4 件に絞ったのは、**利用者が自分の使うサイトの名前に付け替える**前提だから（§2.5）。
  網羅した一覧を作っても、名前が汎用語のままでは選ぶときに読み取れない。
- 「手数料なし」を入れておくのは、手渡し・直接取引で 0% に戻す操作が
  ステッパーの連打（既定 10% から −1 を 10 回）になるのを避けるため。

### 2.3 初期値 — 送料（配送方法ごとの金額）

**配送サービスの商標を使わず、サイズと形状で表す。**
**名前に金額を含めない**（金額は独立した列として持ち、一覧・選択シートでは名前の右に出す）。
理由は「A4・厚さ3cm以内 210円」を 250 円に改定したとき、名前の中の数字が取り残されるため
── サービス名を持たない理由（改定への追従）と同じ。

| # | 名前 | 金額 | 色 | 頭文字 |
|---|---|---|---|---|
| 1 | A4・厚さ3cm以内 | 210 | `blue` | A4 |
| 2 | A4・厚さ2cm以内 | 185 | `teal` | A4 |
| 3 | 専用箱（小） | 450 | `indigo` | 小 |
| 4 | 宅配 60サイズ | 750 | `green` | 60 |
| 5 | 宅配 80サイズ | 850 | `orange` | 80 |
| 6 | 宅配 100サイズ | 1050 | `red` | 100 |
| 7 | 送料込み・手渡し | 0 | `purple` | 0 |

- 「100」は 3 文字なので頭文字の上限（2 文字）を超える。**この行の頭文字は空にして
  名前の先頭 1 文字（「宅」）を出す**か、`10` にする。**採用: 空（「宅」）**
  ── 「10」は 1 の「A4」より 4 の「60」と混ざりやすく、意味を取り違える。
- **決定（§8-2）: 初期値は代表的な水準で置く。地域差は考えない。**
  調査の結果、フリマの匿名配送は**送料が全国一律**で、配送サービスとサイズだけで決まることを確認した。
  したがって「サイズ・形状の名前 ＋ 1 つの金額」という上表の形で足りる（地域を選ばせる列は要らない）。
- 金額は 2026 年時点の代表的な水準で、**アプリが正しさを保証しない**方針は変えない。
  ヘルプに「実際の料金は各サービスの案内で確認してください」の 1 行を置く（§6.1.1）。

### 2.4 初期値 — 梱包材（資材ごとの金額）

| # | 名前 | 金額 | 色 | 頭文字 |
|---|---|---|---|---|
| 1 | 封筒（A4） | 15 | `blue` | 封 |
| 2 | クッション封筒 | 40 | `teal` | ク |
| 3 | 宅配ビニール袋 | 20 | `indigo` | 袋 |
| 4 | 段ボール（小） | 60 | `orange` | 小 |
| 5 | 段ボール（中） | 100 | `red` | 中 |
| 6 | 緩衝材・テープ | 10 | `green` | 緩 |

- 梱包材は 1 回の発送で複数使う（箱 ＋ 緩衝材 ＋ テープ）ので、複数選択にする（§4.3）。
- **決定（§8-11）: 個数の入力欄は持たない。** 電卓の中で選ぶので、`× 2` と打てば済む。

**初期値の ID**: `seed-site-10`, `seed-shipping-a4-3cm`, `seed-packaging-box-s` のように
**内容が読める固定 ID** を振る。UUID にしない理由は、マイグレーション SQL に直接書くため
（生成器を通せない）と、テストで対象行を名指しできるため。
`sortOrder` は上表の # をそのまま入れる（10 刻みにはしない。手動並べ替えを持たないため。§3.4）。

### 2.5 名前を編集できることの位置づけ

- **初期値は「入力の型」であって「正解の一覧」ではない。** 利用者は
  「手数料 10%」→「メ」、「A4・厚さ3cm以内」→「ネコポス」のように、自分の言葉に付け替えて使う。
  アプリ側がサービス名を持たない代わりに、付け替えを 1 タップで始められるようにするのがこの設計。
- したがって**初期値を消せる**必要もある。削除は自由（§1.1）。
- 全部消した状態も正常な状態として扱う（選択シートは空表示になる。§4.5）。
- **決定（§8-5）: 消した初期値を戻すボタンは置かない。** 自分で作り直せるし、
  置くと「もう一度押したら重複して増えるのか」の説明が要る。

### 2.6 梱包材の単価計算（まとめ買い）— 設計案 28c

**2026-08-11 追加。実装済み。** 梱包材だけに適用する（販売サイト・送料には出さない）。

#### 2.6.1 何を解くか

梱包材は「封筒 100 枚で 800 円」のように箱で買うので、
プリセットに登録したい**1 個あたりの単価は利用者が自分で割る**必要がある。
いまも金額欄の電卓で `800 ÷ 100` と打てる（§3.3-4 の電卓はそのために残してある）が、
**買ったときの情報をそのまま入れられる**ほうが分かりやすい、というのがこの案の判断。

| 案 | 内容 | 判断 |
|---|---|---|
| 現状 | 金額欄の電卓で `800 ÷ 100` と打つ | 割り算を自分で組み立てる必要がある。**入数と購入価格が残らない**ので、買い足しで値段が変わったときに割り直しになる |
| **28c（採用）** | 「1 個ずつ / まとめ買い」の 2 択を金額欄の上に置き、まとめ買いなら入数と購入価格を入れて単価を計算・表示する | レシートの数字（100 枚・800 円）をそのまま写せる。**入数と購入価格を保存する**ので、買い足しのときは購入価格だけ直せば単価が更新される |

#### 2.6.2 画面（プリセット編集画面 §3.3。実装は `PresetFormScreen`）

**金額欄の上に「金額の入れ方」の 2 択を置く**（`SegmentedControl`。既定は「1 個ずつ」）。

```
金額の入れ方   [ 1個ずつ | まとめ買い ]

入数            100 個
購入価格        800 円          🖩
1個あたり       8円
```

| モード | 出る欄 | 電卓 |
|---|---|---|
| **1 個ずつ**（既定） | 金額（従来どおり 1 欄） | **出す**（従来どおり） |
| **まとめ買い** | 入数 ／ 購入価格 ／ 1 個あたり（計算結果） | **購入価格の欄にだけ出す** |

| 項目 | 決定 | 理由 |
|---|---|---|
| 2 択を出す種類 | **梱包材（`packaging`）だけ。** 販売サイト・送料では 2 択ごと出さず、従来の 1 欄のまま | 送料は「1 回いくら」で箱買いの概念がない。販売サイトは率（%）で、そもそも個数の単位がない |
| 2 択の位置 | 金額欄の**上** | 下に置くと、欄の形が変わる原因が欄の後ろにあることになり、読み順と操作順が食い違う |
| 「1 個あたり」 | **計算結果の表示**（青字）。入力欄ではない。**電卓ボタンも付けない** | 入力欄に見えると「ここを直せば単価が変わる」と読める。入数と購入価格から一意に決まる値なので、直せる口は 1 つでよい |
| 購入価格の電卓 | **残す** | 「3 袋で 2,400 円」を `800 × 3` や `2400` と打ち分けられる。まとめ買いでいちばん割り算が要るのはこの欄 |
| 入数の電卓 | **付けない** | 入数は数えた個数で、式にならない |
| 電卓の「梱包材から選ぶ」 | **出さない**（`canPickPackaging={false}` のまま。§4.2） | 梱包材を登録する画面で既存の梱包材を呼べる経路は作らない |
| 既定モード | **1 個ずつ** | 既存 6 件（§2.4）と、送料・販売サイトと同じ形。まとめ買いは足す側の選択肢 |

#### 2.6.3 計算と端数

```ts
/**
 * まとめ買いの単価（§2.6）。入数が 0 以下なら計算できないので null。
 * 小数第 1 位まで四捨五入し、0 に落ちたときだけ 0.1 に上げる（購入価格が 0 のときを除く）。
 */
export function presetUnitPrice(packPrice: number, packQuantity: number): number | null;
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 式 | `購入価格 ÷ 入数` | |
| 端数 | **小数第 1 位まで残す。四捨五入**（決定 §2.6.8-2）。`980 ÷ 100 = 9.8` / `800 ÷ 30 = 26.7` | 1 円未満を切り捨てると、100 枚 980 円の封筒が 9 円になって 80 円ぶん消える。梱包材は単価が小さいので、整数に丸めると誤差の割合が大きい。切り上げ（原価を多めに見る）に寄せないのは、**単価が概算でどちらかに寄せる根拠がなく**、既存の `roundForDisplay`（四捨五入）と揃うため |
| 丸めて 0 円になるとき | **0.1 円として扱う**（決定 §2.6.8-4）。`10,000 枚 500 円` → `0.05` → **`0.1`**。警告は出さない | 0 円だと経費に計上されず、登録した意味がなくなる。ただし**購入価格が 0 のときは 0 円のまま**（もらい物・在庫の使い回しを 0.1 円に押し上げない） |
| 実装 | 丸めは**浮動小数のまま `Math.round(x * 10) / 10` にしない**。`validatePreset` の `decimalPlaces` と同じく桁を文字列で扱うか、`Math.round((x + Number.EPSILON) * 10) / 10` の形で誤差を持ち込まない | `0.1` の和が `0.30000000000000004` になる類の値を DB に入れない |
| 記録での扱い | **四捨五入せずそのまま足す。** 選択シートの合計・電卓の行・梱包材欄（`envelope_cost` は `real`）に小数のまま入る | 丸めは表示時のみ（SPEC §2.6）。整数化するのは `roundForDisplay` を通る表示と CSV（§5.4）だけ |
| 表示 | 「1 個あたり **8円**」「1 個あたり **9.8円**」── **末尾の `.0` は出さない**（`10.0` → `10円`） | 整数で割り切れる場合がふつうなので、常に小数を出すと落ち着かない |

- `envelope_cost` は既に `real`（`src/db/schema.ts`）で、計算式（`src/logic/profit.ts`）も加算しかしないので、
  **小数が入っても計算側の変更は要らない**。CSV は §5.4 の丸め規則（各列を四捨五入 → 列の和が合う）のまま。
- 電卓の式評価（`src/logic/calculator.ts`）と数値フィルタ（`sanitizeNumericInput`）は
  小数点を通す（`/^\d*\.?\d*$/`）ので、**`input.ts` は変更しない**（§1.4 / UI-SPEC §7.4 を踏襲）。

#### 2.6.4 schema への影響 — `presets` に 2 列

`value`（1 個あたりの金額）は**これまでどおりの意味のまま**で、記録に入るのもこの列。
足す 2 列は「その `value` がどこから来たか」の材料で、買い足しのときの再計算に使う。

```ts
// SPEC-V3 §2.6。梱包材のまとめ買い（「100 枚で 800 円」）の材料。
// value（1 個あたり）が唯一の真実で、この 2 列はそれを作り直すための控え。
packQuantity: integer('pack_quantity').notNull().default(0), // 入数。0 = 1 個ずつ（未設定）
packPrice: real('pack_price').notNull().default(0),          // 購入価格（円）
```

| 項目 | 決定 | 理由 |
|---|---|---|
| モードの持ち方 | **列を足さない。`packQuantity > 0` を「まとめ買い」とみなす**（導出） | `priceMode` を別に持つと、「まとめ買いなのに入数が 0」のような、意味の重なった不整合な行が作れてしまう。判定は `isPackBuy(preset)` 1 本に閉じる |
| `packQuantity` | `integer`・既定 0 | 個数なので整数。0 が「1 個ずつ」を兼ねるので、`NULL` は使わない（既存列と同じ方針） |
| `packPrice` | **`real`**・既定 0（検証では整数のみ許す。§2.6.6） | 列の型は `value` と揃える。あとで「1 円未満の購入価格」を許すことになっても列を作り直さずに済む。`packQuantity` を `integer` にしたのは、個数が小数になる余地がないため |
| `value` との関係 | まとめ買いのとき **`value` = `presetUnitPrice(packPrice, packQuantity)` を保存時に確定して書く**（導出のたびに計算し直さない） | 読み出す側（選択シート・電卓・記録）が `value` だけ見れば済む。3 種のプリセットで読み方が分岐しない |
| 販売サイト・送料の行 | 2 列とも 0 のまま。書き込まない | 2 択自体を出さない（§2.6.2） |

**マイグレーション**: `drizzle/0003_*.sql` を新しく生成する。
**`0002_dusty_blink.sql`（適用済み）は書き換えない。**

```sql
ALTER TABLE `presets` ADD `pack_quantity` integer DEFAULT 0 NOT NULL;
--> statement-breakpoint
ALTER TABLE `presets` ADD `pack_price` real DEFAULT 0 NOT NULL;
```

- **`UPDATE` は書かない**（バックフィルなし。§2.6.5）。既定値付きの `ADD COLUMN` 2 本だけなので、
  SQLite のテーブル再構築も起きない。
- `site_name` を足したとき（§1.6）と同じ扱い ── 既存行は既定値のまま、後から意味を推測して埋めない。

#### 2.6.5 既存の初期値（梱包材 6 件）への影響

**影響なし。6 件とも `pack_quantity = 0` / `pack_price = 0`、つまり「1 個ずつ」のまま。**

| 項目 | 決定 | 理由 |
|---|---|---|
| §2.4 の 6 件の金額 | **変えない**（封筒 15 円・段ボール（小）60 円 …） | 初期値は「入力の型」であって正解の一覧ではない（§2.5）。単価として妥当な水準で置いてある |
| 入数・購入価格の後付け | **入れない。** 「封筒（A4）15 円」を「100 枚 1,500 円」に書き換えたりしない | アプリが知らない事実（何枚入りをいくらで買ったか）を推測で埋めることになる。利用者が自分の買い方に直したときに初めて入る値 |
| マイグレーションでの `UPDATE` | なし（上記） | |
| 既存の利用者が作ったプリセット | 同じく「1 個ずつ」として開く。**開いただけでは何も変わらない** | 保存を押さないかぎり書き込まないのは従来どおり |

#### 2.6.6 検証（§1.4 への追加）

`src/logic/preset.ts` の `PresetDraft` / `validatePreset` を拡張する。

| 項目 | 規則 | 無効時の文言（`labels.ts`） |
|---|---|---|
| `value`（`packaging`・1 個ずつ） | 0〜999,999。**小数第 1 位まで許す**（§2.6.3。従来は整数のみ） | 「金額は 0 以上で入れてください」 |
| `value`（`shipping`） | 0〜999,999 の**整数**（従来どおり。変更しない） | 同上 |
| `packQuantity`（まとめ買いのとき） | **1〜9,999 の整数。0 と空は無効**（上限は決定 §2.6.8-6） | 「入数を入れてください」 |
| `packPrice`（まとめ買いのとき） | 0〜999,999 の整数 | 「購入価格は 0 以上で入れてください」 |
| 1 個あたり | 検証しない（上の 2 つが通れば必ず 0〜999,999 に収まる） | — |

- `validatePreset` の小数許容は現在 `isRatePreset(type) ? 1 : 0` で分岐している。
  これを **`type === 'shipping' ? 0 : 1`**（率も梱包材も小数第 1 位まで、送料は整数）に変える。
- **入数が空（または 0）のときは保存できない**（保存ボタンをグレーにし、理由を 1 行出す。§3.3 の作法）。
  - 「空なら 1 個ずつに倒す」は採らない。まとめ買いを選んでいるのに黙って別の意味で保存されると、
    次に開いたときモードが戻っていて理由が分からない。
  - 「空なら入数 1 とみなす」も採らない。`800 ÷ 1 = 800 円の封筒`が黙って登録される。
  - 0 除算はこの検証で塞ぐ（`presetUnitPrice` は保険として `null` を返す。§2.6.3）。
- **入力途中は「1 個あたり」の行を `—` にする**（入数が空・0 のあいだ）。行ごと消すと高さが動く。
- **モードを「1 個ずつ」に戻して保存すると、`pack_quantity` / `pack_price` は 0 に戻る**（決定 §2.6.8-3）。
  金額欄にはそのときの 1 個あたりが残る（値は変わらない）。
  控えを残すと「1 個ずつなのに入数がある」不整合な行ができ、
  モードを `packQuantity > 0` で判定する決定（§2.6.4）と食い違うため。

#### 2.6.8 決定事項（旧「要確認」6 件）

**2026-08-11 に 6 件とも確定。§2.6 に未確定の項目は残っていない。** 番号は §2.6 内から参照する用。

1. **一覧・選択シートに買い方を出すか**（§2.6.7 の末尾）
   **決定: 出さない。** 一覧は「名前と単価」を見る画面で、買い方（入数・購入価格）が要るのは編集するときだけ。
   名前の右に「100個 800円」を足すと行が 2 段になり、**選ぶための面**に選ぶのに要らない情報が増える。
   （§2.6.7 に反映）
2. **端数を四捨五入でよいか**（§2.6.3）
   **決定: 四捨五入。** 単価は概算で、切り上げ・切り捨てのどちらかに寄せる根拠がない。
   既存の `roundForDisplay`（四捨五入）と揃えて、丸め方をアプリの中で 1 つに保つ。
   （§2.6.3 に反映）
3. **「1 個ずつ」に戻したときに入数・購入価格を捨てる扱いでよいか**（§2.6.6 の末尾）
   **決定: 捨てる**（`pack_quantity` / `pack_price` を 0 に戻す）。
   残すと「1 個ずつなのに入数がある」不整合な行ができ、
   **モードを `packQuantity > 0` で判定する決定（§2.6.4）と食い違う**。
   （§2.6.6 に反映）
4. **1 個あたりが 0.1 円未満になる場合**（例: 10,000 枚 500 円 → `0.05`）
   **決定: 0.1 円として扱う。警告は出さない。**
   0 円だと経費に計上されず、登録した意味がなくなる。小数第 2 位まで持つ案は採らない
   （表示・合計・CSV の桁がすべて増える）。
   ただし**購入価格が 0 のときは 0 円のまま**（もらい物を 0.1 円に押し上げない）。
   （§2.6.3 に反映）
5. **ヘルプに書くか**（§6.1.1「よく使う値を登録する」）
   **決定: 書く。**「よく使う値を登録する」の節に 1 文
   （「箱で買った梱包材は、入数と購入価格を入れると 1 個あたりが計算されます」）。
   Step 6 までに反映する（§6.1.1 / §6.2）。
   （§6.1.1 / §2.6.7 に反映）
6. **入数の上限**（§2.6.6）
   **決定: 9,999。** それ以上の入数は現実的でなく、桁が増えると欄と「1 個あたり」の表示が窮屈になる。
   `PRESET_AMOUNT_MAX`（999,999）には揃えない ── 金額と個数は別の単位で、同じ上限にする理由がない。
   （§2.6.6 に反映）

| 実装 | `NumericField` に `presetType?: PresetType` を足す。渡された行にだけボタンが出る | 行の形・電卓の位置は変えない（UI-SPEC §7.6 の「`NumericField` は行き先を渡すだけ」と同じ拡張の仕方） |

  送料では名前を写さない（金額だけが入る）。
- 書き戻しは電卓と同じ経路（`NumericField` の `onSubmit` → `sanitizeNumericInput`）を通す。
  プリセットの値が範囲外（負など）でも、この経路で必ず正規化される。
- **上書きの確認は挟まない。** 欄に値が入っていても黙って置き換える
  （入れ直しは 1 タップで、`⌫` より手数が少ない）。

### 4.4 手数料行の扱い

手数料行は他の行と違い、入れるのは「率」で、伝票に載るのはそこから出た「額」
（UI-SPEC §1.3-9 / 実装は `Stepper`）。

- **タグボタンはラベル（率を含む）の直後に置く。**行の並びは ラベル → バッジ → ステッパー → 額（§4.1 と同じ考え方）。
- 選ぶと率が置き換わり、額の表示はその場で追従する（既存の計算経路のまま）。
- ステッパーの ± は残す。プリセットにない率（8.8% 等）を作りたくないときに 1 回だけ動かす用。

### 4.5 複数選択（梱包材）— 電卓の中に置く

UI-SPEC §7.5 は「梱包材の登録を実装したら、**選んだ品名がそのまま電卓の左列（品名）に入る**」と
決めている。本書はそれをそのまま実装する。**梱包材の行にタグボタンは置かない**
（同じことをする経路を 2 つ作らない。UI-SPEC §7.3 の派生決定と同じ方針）。

**電卓シート（UI-SPEC §7.1 の構成）への追加**

| 変更 | 内容 |
|---|---|
| 4「＋ 行を足す」の行 | **左に「＋ 行を足す」／中央に「🏷 梱包材から選ぶ」／右に `AC`** の 3 つにする |
| 品名列（§7.2 / §7.5） | プリセットから積んだ行には**名前だけ**が入る（決定 §8-6。バッジは出さない）。手で作った行は従来どおり空 |
| 行の高さ | 変えない（1 行 1 段のまま。§7.5 の決定） |

「🏷 梱包材から選ぶ」を押すと**複数選択シート**が出る。

| # | 要素 | 内容 |
|---|---|---|
| 1 | ヘッダ | 左「キャンセル」／中央「梱包材を選ぶ」／右「入れる」（太字・青。0 件のときグレー） |
| 2 | 一覧 | 1 行 = チェックボックス ＋ バッジ ＋ 名前 ＋ 右端に金額。タップでトグル |
| 3 | 合計行 | 「選択中 N 点」＋合計額 |
| 4 | 末尾 | 「設定で編集する ▸」 |

**「入れる」を押したときの挙動**

- 選んだ**1 件が電卓の 1 行**になる（`sign = '+'`、`name = プリセット名`、`expression = 金額`）。
  積んである行は消さない。追加で積む。
- 編集中の行（`draft`）が空ならそこから使い、値が入っていればその後ろに積む。
- **合計は既に「表示されている行の結果の和」**（`memoTotal`。UI-SPEC §7.6）なので、
  合計の計算に手を入れる必要はない。`＋ 行を足す` と同じ道に乗るだけ。
- そのあと `× 2` を打って個数を掛けられる（§2.4 で個数欄を持たない理由）。
- **書き戻しは従来どおり「入れる」で合計だけ**が梱包材欄に入る。行は渡さない（UI-SPEC §7.4）。

`src/logic/calcMemo.ts` への追加は関数 1 本で足りる:

```ts
/** プリセットから選んだ資材を行として積む（§4.5）。空の draft は使い回す */
export function appendPresetRows(memo: CalcMemo, items: { name: string; value: number }[]): CalcMemo;
```

`CalcMemoRow.name` は**最初から持たせてある**（`calcMemo.ts` のコメント:「将来の梱包材プリセットで
左列に入る想定」）ので、**行モデルは変更しない**。
**決定（§8-6）: 品名列にバッジ（色）は出さず、名前だけを出す。** 電卓は数字を読む面で、
色の情報が要らない。`CalcMemoRow` に `colorKey` を足さずに済むので、行モデルもそのまま使える。

## 5. CSV の列設計

### 5.1 用途の整理

> **2026-08-12 改訂（実装済み）。** 下の 3 用途はそのままだが、**1 ファイルで全部を賄う決定（§5.2）は覆した。**
> 「確定申告」だけは求められる列が他の 2 つと質的に違う（経費を**項目ごとに区分**した帳簿の材料で、
> メモやタグは邪魔になる）ため、**確定申告用を別の書き出しとして分けた**。
> 経緯は §5.2 の改訂欄、列は §5.3.1。

**2026-08-11 改訂（決定 §8-10）: 「家計簿ソフトへの取り込み」を用途から外した。**
調査の結果、**マネーフォワード ME は CSV の取り込みに対応していない**（PayPay 連携のみ）ことが分かった。
主要な家計簿アプリが取込口を持たないため、「家計簿ソフトの列名に寄せる」方針は成り立たない。
代わりに置いたのが 1 行目の「表計算で開いて自分で集計する」。

| 用途 | 何が要るか | 出力への要求 |
|---|---|---|
| **表計算で開いて自分で集計する** | 列がそのまま読めること。ピボット・SUMIF がかけられること | 1 行 = 1 記録の素直な明細。列名が日本語で意味が読めること |
| 確定申告 | 収入と**経費の内訳**（仕入・送料・手数料・梱包材）。年単位 | 内訳が別列。年で期間を切れること |
| 汎用的な記録保存 | 記録した内容がすべて残ること（**端末が唯一の保存先なので、これがバックアップも兼ねる**。§0） | 画面で見える値がすべて列にあること |

**会計ソフト側の取込口は確認できている。** マネーフォワード クラウド会計（確定申告用）には
CSV インポートがあり、**利用日・利用内容・金額の 3 列**があれば取り込める。
これは「特定ソフトに寄せる」のではなく**列の並び**の要求として扱う（§5.2 / §5.3）──
先頭 3 列がその 3 つになっていれば、取込ウィザードで先頭数列だけ選べば済む。

### 5.2 決定 — 2 種類に分ける（2026-08-12 改訂・実装済み）

**決定（改訂後）: 書き出しは 2 種類。設定タブから開くシートでどちらかを選ぶ（§5.7）。**

| 種類 | 列 | 用途 | まとめ方 |
|---|---|---|---|
| **データ保存用** | **18 列**（§5.3 ＋ SPEC-V4 §5.3） | バックアップ（§0.1）／表計算で自分で集計する | 1 件ずつのみ |
| **確定申告用** | **11 列**（§5.3.1） | 帳簿の材料。経費を**項目ごとに区分**した形 | 1 件ずつ / **日ごとにまとめる**（§5.2.2） |

<details>
<summary><b>元の決定（覆した）と、変えた理由</b></summary>

**元の決定:**

> **決定: 用途ごとにパターンを分けず、「1 行 = 1 記録」の明細 1 種だけを出す（案 A）。**
>
> | 案 | 内容 | 判断 |
> |---|---|---|
> | **A（採用）** | 全列入りの明細を 1 種。用途ごとの加工は表計算 / 会計ソフトの取込側で行う | 主要な家計簿アプリに取込口がなく（§5.1）、寄せる相手がいない。申告に要るのは経費の内訳**列**で、明細に列として入れておけば足りる。出力が 1 種なら、選ばせる UI もヘルプも実装もテストも 1 つで済む |

**変えた理由:**

1. **申告用は「列を減らした版」ではなかった。** 案 B を退けた根拠は「寄せる相手がいない以上、
   実質は列を減らした版でしかない」だったが、帳簿には**外せない要求**がある ──
   経費は「項目に区分して」記載することが求められており（合算した 1 列では材料にならない）、
   **不用品は原則非課税**（生活用動産）なので種別で仕分けられる必要がある。
   18 列の明細でも情報としては足りているが、**メモとタグが混ざったファイルを申告に使わせる**のは別の話で、
   帳簿に関係のない個人的な記述を税務の書類に持ち込むことになる。
2. **「日々の合計金額のみ」を出せない。** 国税庁は「一つ一つの取引ごとではなく、日々の合計金額のみを

   メモとタグは合算できないので、18 列のまま日ごとにまとめることができないからである（§5.2.2）。
3. **C を退けた判断は変えていない。** 足したのは「日ごと」までで、**月ごと・経費科目ごとの集計は入れない。**
   「どの範囲を足したか」の説明責任が増えるのは元の判断のとおりで、日ごとは国税庁が名指しで
   認めている単位なので、アプリが範囲を決めているわけではない。
4. **2 種類でも「選んで書き出し、後で足りないと気付く」は起きにくい。** 元の懸念は
   「列が少ない版を選んで書き出す」ことだったが、名前が用途そのもの（データ保存用 / 確定申告用）で、
   シートの中に選んだ方の説明が 1 行出る（§5.7）。**バックアップに使うべき方が既定**でもある。

**決定（§8-10）: 列名は日本語のまま維持し、データ保存用の先頭 3 列を「販売日 → 商品名 → 販売価格」の順に固定する。**

- 会計ソフト（マネーフォワード クラウド会計）の要求「利用日・利用内容・金額」がこの 3 列に対応する。
  **取込ウィザードで先頭 3 列だけ選べば済む**ので、18 列あっても邪魔にならない。
- **確定申告用はこの並びに従わない**（§5.3.1）── あちらは帳簿の並び
  （取引の年月日 → 相手方の名称 → 内容）で、2 列目に販売サイトが入る。
  会計ソフトへの取り込みが要るときは**データ保存用**を使う（先頭 3 列が保たれているのはそちら）。
- 列名を会計ソフトの語（「利用日」「利用内容」）に改めることは**しない**。
  画面の語（`labels.ts`）と食い違うと、書き出した CSV とアプリの対応が読めなくなる。
  取込側は列を選ぶだけなので、列名が一致している必要はない。

### 5.2.2 まとめ方 — 1 件ずつ / 日ごと（確定申告用のみ）

**決定: 確定申告用にだけ「1件ずつ（既定）」「日ごとにまとめる」の 2 択を出す。**
国税庁が「一つ一つの取引ごとではなく、**日々の合計金額のみをまとめて記載する**など、
簡易な方法で記載してもよい」としているため。

**データ保存用にはこの選択肢を出さない**（節ごと出さない）── メモとタグは合算できないので、
まとめた行に何を書いても嘘になる。**絞り込みページで「出品中のときは販売サイトの節が消える」のと同じ扱い。**

日ごとにまとめたときの各列:

| 列 | まとめ方 |
|---|---|
| 販売日 | その日 |
| 販売サイト | 複数あれば「メルカリ ほか1件」。1 つなら名前だけ。**数えるのは名前の種類**（同じサイトが 3 件でも「ほか」は付かない）。1 つも無ければ空 |
| 商品名 | 「えんぴつ ほか2件」（先頭の 1 件 ＋ **残りの件数**）。空の商品名は一覧と同じ「無題」 |
| 種別 | 混在していれば「混在」。同じなら種別名 |
| 金額の各列 | 合算。**丸めは合算後に列ごと 1 回だけ**（決定 §7-2 / §2.6。§5.4 の丸め規則を参照） |

- **グループのキーは「基準日」と「状態」の 2 つ。** 出品中を含めた（§5.5-3）とき、同じ日の
  出品中の記録を売れた記録に混ぜると、**販売日の列に出品日が入ってしまう**。分けておけば
  出品中の行は販売日が空のまま（1 件ずつのときと同じ）で済む。同じ日は売れた行を先に置く。
- 並びは基準日の昇順（§5.4 と同じ）。

データ保存用の並びは**先頭 3 列 → 内訳 → 計算値 → 属性 → メモ → 記録ID**（§5.3）。
内訳を計算値より先に置くのは、レシートカード（UI-SPEC §1.4-4）と同じ「販売価格 − 内訳 = 結果」の読み順にするため。

### 5.3.1 列 — 確定申告用（11 列・2026-08-12 追加）

ヘッダ行あり。**11 列。**列名はデータ保存用と同じ語（`labels.ts`）を使う。

**並びは帳簿の並び**（取引の年月日 → 相手方の名称 → 内容 → 金額）。
データ保存用の「先頭 3 列の固定」（§5.2）は**ここには適用しない** ── あちらは会計ソフトの
取込ウィザードのための並びで、こちらは帳簿に書き写すための並び。会計ソフトへ取り込むときは
データ保存用を使う。

| # | 列名 | 出所 | 根拠 |
|---|---|---|---|
| 1 | 販売日 | `saleDate` | 帳簿の法定要件「取引の年月日」 |
| 2 | 販売サイト | `siteName` | 同「相手方の名称」。**購入者が匿名なのでサイト名で代用する** |
| 3 | 商品名 | `itemName` | 何を売ったかの証跡（帳簿の「内容」） |
| 4 | 種別 | `kind` | **不用品は原則非課税**（生活用動産）なので仕分けに要る。§5.8 の注意書きと対で効く |
| 5 | 販売価格 | `salesPrice` | 売上金額 |
| 6 | 仕入価格 | `purchasePrice` | 売上原価 |
| 7 | 送料 | `postage` | 経費 |
| 8 | 梱包材 | `envelopeCost` | 経費 |
| 9 | その他 | `othersCost` | 経費 |
| 10 | 販売手数料 | `commissionCost` | 経費（**計算値**。`salesPrice × commission / 100`） |
| 11 | 収支 | `netProfit` | 検算用 |

- **経費を合算せず項目ごとに分けるのが要点。** 国税庁は経費を「項目に区分して、それぞれ
  その取引の年月日、事由、支払先および金額を記載する」と定めており、合算した 1 列では帳簿の材料にならない。
  **「経費合計」の列は置かない**（項目の和なので表計算で作れるうえ、置くと「合計だけ写す」経路を勧めてしまう）。
- **メモとタグは出さない。** 帳簿に関係がなく、個人的な記述が混ざるため。
- **記録 ID・状態・出品日・手数料率も出さない。** 帳簿に書く欄がない。
  出品中を含めて書き出した場合（§5.5-3）、その行は販売日が空になる ──
  申告に使うときは既定（売れた記録のみ）のままにする。
- **11 列目の名前は「純利益」ではなく「収支」。** SPEC-V2 §5.3 のラベル規則
  （1 件を指すときは種別語 = 純利益 / 利益、2 件以上の合計は中立語 = 収支）に従うと、
  ヘッダは**1 語に決められない** ── 行ごとに種別が違い得るうえ、日ごとにまとめた行（§5.2.2）は
  そもそも合計である。中立語の「収支」なら両方の行で正しい。

### 5.4 書式の決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 文字コード | **UTF-8（BOM 付き）** | BOM がないと Windows 版 Excel が Shift_JIS と誤認して日本語が化ける。BOM 付き UTF-8 は主要な表計算・会計ソフトが読める |
| 改行 | **CRLF** | RFC 4180。Excel の互換が最も広い |
| 引用 | **RFC 4180**。`,` `"` 改行を含む値は `"` で囲み、内部の `"` は `""` に | 商品名・メモにカンマと改行が入り得る |
| 数値 | **桁区切りなし・通貨記号なし**（`1050`） | 取込側で数値として読める形。`¥1,050` は文字列になる |
| 日付 | **`YYYY-MM-DD`** | 端末ローカルの暦の日付（`src/db/dates.ts` の保存値の先頭 10 文字）。時刻は出さない ── 記録は日単位で扱っており、時刻に意味がない |
| 金額の丸め | **決定（§8-7）: 各列を先に整数へ丸め（`roundForDisplay` = 四捨五入）、経費合計は丸めた列の和、収支は 販売価格 − 経費合計** | **CSV の中で足し算が合う方を採る。** 画面の合計（丸めなしで足してから丸める）と最大 1 円ずれ得るが、取込先や表計算で検算されるのは CSV 内の列同士なので、そちらの整合を優先する（UI-SPEC §7.6 が「見えているものと一致する方を採る」と決めたのと同じ形の判断）。ずれることはヘルプに 1 行置く（§6.1.1） |
| 空値 | **空文字**（`NULL` や `-` は書かない） | 出品中の販売日のみ該当 |
| 並び順 | **基準日の昇順**（売れた記録 = 販売日 / 出品中 = 出品日）。同日は `id` | 申告・表計算はどちらも時系列で読む。画面の並び（降順）とは逆にする |
| ファイル名 | **`売上記録_2026-08.csv` / `売上記録_2025.csv` / `売上記録_全期間.csv`**（データ保存用）／**`確定申告_…`**（確定申告用）。**2026-08-12 改訂**（下記） | 共有シートに出る名前がそのまま保存名になるので、後から見て何のファイルか読める形にする。期間キーをそのまま入れる（「2026年8月」だと名前で並べたときに 10 月が 1 月の隣に来る） |

**手数料率だけは丸めない**（データ保存用の 11 列目）。10.5% を 11 にしたら率ではなくなる。

**日ごとにまとめたとき（§5.2.2）も丸めの規則は同じ。** 合算は丸めなしの生の値で行い、
丸めるのは**列ごとに 1 回だけ**。1 件ずつ丸めてから足すと、行の中で
「販売価格 − 経費の各列 = 収支」が合わなくなる。

- 既定を「売れた記録のみ」にするのは、申告も集計も**確定した金額**しか扱わないため。

  なお出品中を含めると**1 列目（販売日）が空の行が混ざる**ので、会計ソフトへ取り込むときは既定のままにする。

  **アプリは入金日を持たず、会計上の帰属（いつの売上として計上するか）も決めない。**
  この注記をヘルプに置く（§6.1.1）── 現金主義で入金日基準にしたい場合、この CSV だけでは足りない。
- 対象が 0 件のときは**「書き出す」を非活性**にし、下端に 1 行出す（§5.7）:
  「この期間に対象の記録がありません。**出品中の記録は3件あります。**」
  2 文目を足すのは、**切り替えれば書き出せる**ことを示すため ── 「0件」だけでは、
  期間の選び直しと対象の切り替えのどちらで直るのかが読めない。
  出品中が 1 件も無いときは 2 文目ごと出さない（言うことがない）。
- **記録タブ・データタブの絞り込み（種別・販売サイト・タグ）は効かせない**（SPEC-V4 §5.4 / 決定 §9-9）。
  CSV は設定タブから開くもので、絞り込みは別タブの**画面ローカルな状態**である。
  効かせると「なぜ一部しか出ないのか」が分からないまま一部だけ書き出す事故が起きる ──
  主用途がバックアップ（§0.1）なので、その事故の方が大きい。
  タグごとの集計は書き出した後に表計算側で行う（SPEC-V4 §5.2 の `COUNTIF`）。

### 5.6 書き出しの経路

設定タブ「データ」群の「書き出し（CSV）▸」を押す → `ExportSheet`（種類・期間・まとめ方・対象を選ぶ）→
「書き出す」→ 共有シート。

| 項目 | 決定 | 理由 |
|---|---|---|
| 実装 | **決定（§8-13）: `expo-file-system` でキャッシュ領域に書き、`expo-sharing` で共有シートを出す。出力先はこれだけ** | 「ファイルに保存」「メールで送る」「他アプリへ渡す」が OS 標準の 1 枚で片付く。保存先を自前で選ばせる UI を作らない |
| 新規依存 | `expo-file-system` / `expo-sharing`（Expo SDK 57 の同梱パッケージ） | どちらも Expo 管理下。`react-native` の `Share` はテキスト共有で、CSV 本文を本文に貼る形になり使えない |
| 一時ファイル | キャッシュ領域に置き、消さない（OS 任せ） | 共有シートが閉じるタイミングを待って消す仕組みは、失敗時に消し忘れる方が厄介 |
| 件数の上限 | 設けない | 数千件（SPEC-V2 §8-6）× 18 列で数百 KB。同期で組み立てて問題にならない |
| 進捗表示 | 出さない | 上記の規模で一瞬。ボタンを押している間だけ無効化する |

実装前に **Expo SDK 57 の `expo-file-system` / `expo-sharing` の当該バージョンのドキュメント**
（`app-rn/AGENTS.md` の指示どおり <https://docs.expo.dev/versions/v57.0.0/>）を読むこと。
`expo-file-system` は SDK 54 で API が入れ替わっている（旧 `FileSystem.writeAsStringAsync` /
新 `File` クラス）ので、記憶で書かない。

**実装時に確認した API（SDK 57）:** `new File(Paths.cache, ファイル名)` →
`file.create({ overwrite: true })` → `file.write(文字列)` → `file.uri` を
`Sharing.shareAsync(uri, { mimeType: 'text/csv', UTI: 'public.comma-separated-values-text', dialogTitle })` へ渡す。
`Sharing.isAvailableAsync()` を先に見て、使えなければその旨を出す。
`file.write(string)` は UTF-8 で書くだけで **BOM を付ける口を持たない**ので、BOM は文字列の側に付ける
（`toCsvFileContent`）。
同じ期間を続けて書き出すと前回のファイルが残っているため `overwrite: true` が要る。

### 5.8 確定申告用の注意書き

**シートの中の位置は「対象」の下・下端の上**（§5.7-3 の表では 3 番目に置いてあるが、

#### 5.9.1 シートの中の表（案 `40a`）

- 見出しは「**書き出す表**」（「プレビュー」ではなく**何の表か**を言う）。右に「先頭3行・全18列」。
  **行数が先、列数が後** ── 見えているもの（3 行）を先に言い、見えていないもの（列）を後に置く。
  出す行が 3 行に満たないときは実際の数を出す。
- **横スクロールする。右端をぼかして続きがあることを示す**（グラデーション）。
  下に「横に動かすと残りの列が見えます」の 1 行を置く ── 横に動かせることは形からは読めない。
- **種類・期間・まとめ方・対象を変えるとその場で中身が変わる。**
- **対象が 0 件のときは出さない**（出す表がない）。
- **値は CSV に書かれるのと同じ文字列**をそのまま出す。`2026-08-10` を `8/10` に、
  `5000` を `¥5,000` に整形し直さない ── この表の用は「ファイルに入るものを確かめる」ことなので、
  **見た目を変えるとその用が消える**。設計案 `40a` の絵は整形した値で描かれていたが、その 1 点だけ採らなかった。
- **日付の列は `2026-08-09` の 10 文字が必ず 1 行に収まる幅**にする（112pt）。
  日付が「2026-08-…」と切れると、まさに確かめたい「どの日の行か」が読めない。

#### 5.9.2 全画面（案 `40c`）

- 見出しの行は左「2026年8月・売れた記録」（シートの下端と同じ語）／右「全18列・8件（4行）」。
- **全行を出す。先頭 N 行で打ち切らない。** 打ち切ると「見えていない行に何が入っているか」という
  元の不安がそのまま残る。**件数が増えても重くならないのは仮想化（`FlatList`）の役目**で、
  画面に見えている行しか描かれない。行の高さを固定（38pt）にしてあるので `getItemLayout` も渡せ、
  スクロール位置の計算に実測を待たせない。
  実機（1000 件）で速く弾いても行が欠けず、引っかかりも出ないことを確認した。
- **ヘッダ行は縦スクロールに追随して固定する**（`stickyHeaderIndices`）。
  縦に流れても列名が読めないと、右へ動かした後にどの列を見ているのか分からなくなる。
  地の色は**不透明な色**にすること ── 半透明だと固定したときに下を流れる行が透けて数字が重なる（実機で見つけた）。
- **1 列目（販売日）は固定しない。** 固定するには「左の 1 列」と「残りの列」を別々の仮想化リストにして
  縦スクロールを同期させることになり、リストが 2 本になる（行の高さの計算も 2 通りになり、
  速い指の動きで縦位置がずれる）。**ヘッダが固定されていれば「いま何の列か」は読める**ので、
  そこまでの作りは持たない。
- **横向きには対応しない**（アプリ全体が縦固定）。列が多いときの逃げ道はこの画面そのもので、
  横向きを足すと画面の作りが 2 通りになる。
- 閉じる手段は 2 つ: ヘッダの「‹ 書き出し（CSV）」（push なので自動で付く）と、
  下端の「シートに戻る」（表を最後まで見た指がそのまま届く場所）。
- **条件はルートの引数から受け取り、DB は自分で引き直す。** シートから props で渡す形にすると、
  リロードやディープリンクで引数が欠けたときに空の表になる。知らない値は既定へ倒す。

#### 5.9.3 プレビューと書き出しが同じデータを見る

**決定: `csv.ts` の入口を「行の配列」（`buildCsvTable`）にし、CSV の文字列（`buildCsv`）は
それを繋ぐだけにする。**

**CSV の文字列を作ってから分割し直す形にはしない。** 引用（§5.4）を解く処理をプレビュー側が
持つことになり、片方だけ直したときに「画面で見た値とファイルの値が違う」が起きる。
行の配列から両方が出ていれば、構造として食い違わない（単体テストでも固定してある）。

- 先頭 3 行の打ち切りは `buildCsvTable` の `limit`（**データ行だけに効く**）。
  **日ごとにまとめる場合はまとめた後の行に効く** ── 先頭 3 件で記録を切ってから合算すると、
  1 行目の金額が本物と食い違う。
- タグを引くのは**データ保存用のときだけ**（SPEC-V4 §5.3）。
  1 件ずつのときは行と記録が 1 対 1 なので、シートの表では先頭 3 件ぶんしか引かない。

#### 5.9.4 シートの高さ

プレビューのぶん、シートの中身は約 120pt 伸びた。書き出しシートは**モーダルの 1 画面**
（下から出る `SheetModal` ではない。UI-SPEC §3.5 の器は使っていない）ので、
**中身が画面を超えたぶんはそのまま中でスクロールする**。
開いた直後に見えているのは上（種類・期間）で、プレビューは下へ動かすと出る ──
最初に決めるのは種類と期間で、プレビューはそれを決めた**結果**を確かめるものなので、この順で正しい。

## 8. 決定事項（旧「要確認」）

2026-08-11 に 1〜13 を確定。番号は本書内から参照する用。**14 は実装時の調査項目**（決定ではなく作業）。

1. **記録に「販売サイト名」を持たせるか**
   **決定: 採用。`sale_records` に `site_name` を 1 列追加する。**
   CSV に「どこで売ったか」が残らないと §5.1 の用途を満たさないため。外部キーではなく**名前の写し**にして、
   プリセットを直しても過去の記録が動かないようにする。（§0 / §1.5 / §1.5.1 / §1.6 / §5.3-12 に反映）
2. **送料の初期値の金額（§2.3）**
   **決定: 代表的な水準で置く。地域差は考えない。**
   調査の結果、フリマの匿名配送は**送料が全国一律**で、配送サービスとサイズだけで決まることを確認した。
   金額はアプリが正しさを保証しない方針のままとし、注記をヘルプに置く。（§2.3 / §6.1.1 に反映）
3. **色パレット（§1.3）**
   **決定: 8 色をそのまま採用。**（§1.3 に反映）
4. **手動並べ替え（§3.4）**
   **決定: 入れない。** 並び順は `sortOrder` の昇順固定、追加は末尾。（§3.4 に反映）
5. **削除した初期値を戻すボタン（§2.5）**
   **決定: 置かない。**（§2.5 に反映）
6. **電卓の品名列のバッジ（§4.5）**
   **決定: 名前だけを出す。** バッジ（色）は出さないので `CalcMemoRow` に `colorKey` を足す必要もない。
   （§4.5 に反映）
7. **CSV の丸め（§5.4）**
   **決定: 列の和が合う方を優先する。** 画面の合計と最大 1 円ずれることを許し、ヘルプに 1 行置く。
   （§5.4 / §6.1.1 に反映）
8. **CSV の期間の基準日（§5.5）**
   **決定: 販売日基準で確定。** アプリは入金日を持たず、**会計上の帰属も決めない**。
   §5.5 の注記どおりヘルプに明記する。（§5.5 / §6.1.1 に反映）

   **決定: 「売れた記録のみ」。**（§5.5 に反映）
10. **家計簿ソフトのフォーマット（§5.1 / §5.2）**
    **決定: 家計簿ソフトの列名に寄せる方針は破棄する。前提が変わった。**
    調査の結果、**マネーフォワード ME は CSV の取り込みに対応していない**（PayPay のみ）。
    そのため「家計簿ソフトへの取り込み」を用途から外し、「表計算で開いて自分で集計する」に置き換えた。
