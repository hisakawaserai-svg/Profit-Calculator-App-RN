# バックアップと復元 仕様 — SPEC-V8

書き出したデータを**アプリに戻せる**ようにする。機種変更でデータを持ち越せることが目的。

**本書は既存の CSV 書き出し（SPEC-V3 §5 / SPEC-V4 §5）を一切変更しない。**
18 列も 11 列も、期間の指定も、シートの構成もそのまま。これは**別の機能**として並立する。

| | 書き出し（CSV）— SPEC-V3 §5 | バックアップと復元 — 本書 |
|---|---|---|
| 目的 | 表計算で読む・確定申告の材料 | **端末を移る・元に戻す** |
| 形式 | CSV 1 枚 | **ZIP 1 つ（中に CSV 5 枚）** |
| 期間 | 選べる（全期間 / 年 / 月） | **選べない。常に全件**（§1.3） |
| 中身 | 記録だけ（計算値を含む 18 列 / 11 列） | **記録・プリセット・タグ・タグ付けの 4 表**（§2.1） |
| 読み込み | **無い** | **ある**（§3） |
| 写真 | 入らない | **含めるか選べる**（既定は含める。§4） |

---

## 0. なぜ分けたか

### 0.1 「書き出し」の主用途はバックアップだったが、片道だった

SPEC-V3 §0.1 は「端末が唯一の保存先」と置き、CSV 書き出しの主用途をバックアップとしていた。
だが**読み込む手段が無い**ので、書き出したファイルはあってもアプリに戻せない
（`docs/IMPROVEMENTS.md` の「CSV の読み込み」）。機種変更でデータが失われる状態が残っていた。

### 0.2 既存の CSV に読み込みを足さなかった理由

**18 列 CSV は DB の上位集合ではない。** 計算値（販売手数料額・経費合計・収支）が入る一方で、
`photo_file_name` / `shipping_material_cost` / `excludes_shipping_material` の 3 列が無く、
日付は先頭 10 文字だけなので**時刻が落ちている**。プリセットもタグの色も入っていない。
つまり 18 列を読み戻しても元には戻らない。

かといって 18 列に列を足すと、**表計算で開く人に意味のない列が増える**（IMPROVEMENTS.md の
「ZIP でのバックアップ」で指摘済み）。人が読む形と機械が読み戻す形は要求が違う、という結論で
**2 つの口に分けた**。

### 0.3 それでも CSV にした理由（JSON にしない）

読めない形式にすると「中身が確かめられない」不安がそのまま残る。CSV なら
解凍して表計算で開けば全部見える。**利用者が中身を確認したあとでも復元できる**ように、
解凍したフォルダも受け付ける（§3.1）のはこの決定の帰結。

## 1. 形式

### 1.1 ZIP 1 つ、中にフォルダ 1 つ

```
profit-calculator-backup_2026-08-14.zip
└── profit-calculator-backup_2026-08-14/
    ├── backup-info.csv
    ├── records.csv
    ├── presets.csv
    ├── tags.csv
    ├── record_tags.csv
    └── photos/<uuid>.jpg     ← 写真を含めたときだけ（§4）
```

**中にフォルダを 1 段作る。** 解凍したときに中身がダウンロードフォルダへ
散らばらないようにするため。

**アプリ名を頭に付ける**（決定 §8-6）。保存先（ファイルアプリ・クラウド・PC）には
他のアプリのバックアップも並ぶので、`backup_2026-08-14.zip` だけでは何のバックアップか
分からず、機種変更のときに正しいファイルを選べない。

**名前は ASCII だけ**（決定 §8-1）。書き出しの CSV は日本語名にしてある
（`logic/exportPeriod.ts`）が、こちらは ZIP のエントリ名になるので事情が違う ──
ZIP のファイル名の文字コードは規格上あいまいで、日本語だと解凍ツールによって化ける。
**化けた名前は復元時に引けなくなる**ので、アプリ名も日本語の表示名ではなく
バンドル ID と同じ綴り（`profit-calculator`）を使う。

**読み込み側はこの名前に一切依存しない**（§3.1）。名前は「保存先で見分けるため」だけのもので、
利用者がリネームしても、フォルダ名が違っても、旧名（`backup_2026-08-13/`）のままでも読める。

### 1.2 `backup-info.csv`（1 行だけ）

| 列 | 内容 |
|---|---|
| `format_version` | 形式のバージョン（§1.2.1） |
| `created_at` | 作成日時（DB と同じ `YYYY-MM-DDTHH:mm:ss.SSS`） |
| `record_count` / `preset_count` / `tag_count` / `record_tag_count` | 各表の件数 |
| `photo_count` | 写真の枚数（**版 2 で追加**。§4.1） |

**バージョンは ZIP 全体で 1 つ。** ファイルごとには持たない ── 5 枚は同時に書かれ、
片方だけ古いことが起こらない。

**件数は読み込み側で数え直す**（§3.2）。ここに書いてある数は信じない ──
信じると、手で行を削られたファイルでも気付けない。書いてあるのは人が見るためのもの。

#### 1.2.1 バージョンの上げ方

`BACKUP_FORMAT_VERSION`（現在 **2**）を上げるのは**列の増減・意味の変更**があったときだけ。

**版 2 は写真を含められるようにした版**（§4）── `backup-info.csv` に `photo_count` が
増え、`photos/` が入り得る。**版 1 も読める**（`BACKUP_MIN_SUPPORTED_VERSION` = 1）──
版が上がったからといって、利用者が既に持っているバックアップを読めなくする理由がない。
`photo_count` を**末尾に足した**のはこのためで、途中に挿すと同じ列名でも位置がずれる。

**DB のマイグレーション番号（drizzle の 0008…）とは別の数にしてある。**
マイグレーションは内部の都合で何度でも増えるもので、そのたびに古いバックアップを
読めなくする理由がない。

読み込みは `BACKUP_MIN_SUPPORTED_VERSION` 以上 `BACKUP_FORMAT_VERSION` 以下だけを受ける。
**未来の版は弾く** ── 知らない列を黙って捨てると、復元できたつもりでデータが減る。

### 1.3 期間を選ばせない

書き出し（CSV）には期間があるが、こちらには**無い。常に全件**。

一部だけ入ったファイルは「バックアップ」として意味を成さない ── 戻したときに
何が欠けているか利用者には分からない。選択肢そのものを作らないことで、
「先月だけバックアップしたつもり」の事故を消す。

## 2. CSV の中身

### 2.1 各表は DB の全カラムをそのまま出す

列名は**DB のカラム名そのまま**（`item_name` のようなスネークケース）。画面の日本語ラベルは
使わない ── これは機械が読み戻す形で、列名は DB との対応が一目で分かる方がよい。
（エラー文言では日本語のラベルに直して出す。§3.3）

| ファイル | 列数 | 中身 |
|---|---|---|
| `records.csv` | **17** | `sale_records` の全カラム |
| `presets.csv` | **10** | `presets` の全カラム |
| `tags.csv` | **4** | `tags` の全カラム |
| `record_tags.csv` | **2** | 複合 PK の 2 列 |

**計算値の列は入れない**（販売手数料額・経費合計・収支）。保存されているのは率で、
額は計算で出る（SPEC §2.2）── 書いても読み戻さないので、読み手に嘘の選択肢を見せるだけ。

### 2.2 数値は素の形

**桁区切りを入れない**（`1500` であって `1,500` ではない）。通貨記号も付けない。
`toLocaleString()` を使うと端末の地域設定で桁区切りが入り、読み戻せなくなる。

読み込み側も**桁区切りを受け付けない** ── 表計算で開いて書式を付けて保存し直された
ファイルは、そこで弾いてエラーにする（黙って解釈すると、何が入ったのか分からなくなる）。

### 2.3 日付は時刻まで

`YYYY-MM-DDTHH:mm:ss.SSS`。**既存の 18 列 CSV と違い、先頭 10 文字で切らない**
（§0.2 の「時刻が落ちている」への答え）。

`sale_date` の null は**空欄**。読み込み時は `is_sold` で判定する ──
出品中の記録は販売日を持たない（SPEC §1）。

引用は RFC 4180（`logic/csv.ts` の `escapeCsvField` を借りる）。改行は CRLF。
**引用の規則を 2 通り持たない**のが借りている理由で、書いた側と読む側で食い違うと原因が追えない。

## 3. 読み込み

### 3.1 受け付ける形

**ZIP と、解凍したフォルダの両方**（決定 §8-2）。§0.3 のとおり「中身を確認してから戻す」を
成立させるため ── 解凍して確かめた人が、そのまま復元できなければ確認する意味がない。

**引くのは中身の基底名（`records.csv` など）だけで、ZIP の名前もフォルダの名前も見ない。**
だから次はすべて読める:

- `profit-calculator-backup_2026-08-14/records.csv`（自分で作った形）
- `backup_2026-08-13/records.csv`（**アプリ名を付ける前に作った古いバックアップ**）
- `きろく 2026年8月 (1)/records.csv`（利用者がリネームしたもの）
- `records.csv`（他のツールが直下に置いた形）

名前で引く実装にしなかったのはこのため ── 名前は §1.1 のとおり「見分けるため」のもので、
**それを変えたら読めなくなる**のでは、利用者に名前を触るなと強いることになる。

**次のエントリは黙って無視する**（決定 §8-3）:

| 無視するもの | なぜ入るか |
|---|---|
| `__MACOSX/` 配下 | macOS の Finder で再圧縮すると必ず入る |
| `.DS_Store` | 同上 |
| `._` 始まり | リソースフォーク（`__MACOSX/` の外にも出る） |
| 末尾が `/` のエントリ | ディレクトリ自身 |

これらを「知らないファイルがある」で弾くと、**中身を確認しようと解凍しただけの人が
復元できなくなる。** 実機で `ditto -c -k --sequesterRsrc`（Finder の「圧縮」と同じ構造）を
通して確認済み。

フォルダを選んだ場合は**深さ 1 まで**探す（選んだフォルダ自身と、その直下のフォルダ 1 段）。
読みに行くのは要る 5 枚だけ ── 解凍先が雑然としたフォルダでも、無関係なファイルを開かない。

### 3.2 検証（1 件でもエラーがあれば一切読み込まない）

**順序が意味を持つ**:

1. **5 つのファイルが揃っているか**
2. **`backup-info.csv` の版が読める範囲か** ← 列の検証より先。知らない版のファイルに
   「列が違う」と言っても、利用者には直しようがない
3. **各ファイルの列数と列名が一致するか**（並べ替え・改名・過不足はすべてエラー）
4. **各行の項目数がヘッダと一致するか**
5. **各値が列の型として読めるか**（数値 / 0・1 / 日付 / 決まった語）
6. **必須列が空でないか**
7. **`record_tags` の参照先が実在するか** ← 全ファイルを読み終わってからでないと確かめられない

**7 が要るのは外部キーが効いていないから。** `references()` は宣言してあるが
`PRAGMA foreign_keys` の既定は OFF（SPEC-V4 §1.4）。孤児行が入ると絞り込みの件数が
静かに狂う。復元は既存データを全部消してから入れるので、**ここで見逃すと戻す先も無い。**

日付は形だけでなく**実在するか**まで見る（`2026-02-31` を弾く）── `Date` は 2 月 31 日を
3 月 3 日に繰り上げるので、書き戻して一致を確かめる。

### 3.3 エラーの出し方

**題名 ＋ 本文の 3 行で固定する**:

```
バックアップを読み込めませんでした。          ← 題名（Alert のタイトル）
records.csv 501行目：「仕入価格」が正しい数値ではありません。
現在のデータは変更されていません。
```

- **どこが**（ファイル名と行番号）**なぜ**（列名と理由）を必ず出す。「読めませんでした」だけでは、
  500 行のファイルのどこが悪いのか調べようがない
- 列名は**日本語のラベル**に直して出す（CSV の列名は `purchase_price` だが、
  利用者が画面で見ている語は「仕入価格」）
- **3 行目を必ず付ける。** 失敗したときに一番知りたいのは「壊れていないか」だから ──
  全置換の機能なので、途中まで入った可能性を疑わせない
- 行番号は**ヘッダ行を 1 行目として数える**（テキストエディタで開いたときの行番号と合わせる）

**列の食い違いは列名を全部並べない。** 17 列を 2 回並べると画面が文字で埋まり、
肝心の「どこが違うか」が読めなくなる（実機で確認して直した）。出すのは
**最初に食い違った 1 か所**だけ:

```
records.csv の列の数が違います。必要な列は 17 ですが、ファイルには 16 あります。
records.csv の列名が違います。3 列目は「sales_price」のはずですが「price」になっています。
```

### 3.4 全置換（部分復元・マージ・追加は作らない）

`IMPROVEMENTS.md` が挙げていた 3 択（A: 常に新規 / B: ID 一致で上書き / C: 新 ID で追加）は、
**どれも採らない。** 4 テーブルを空にしてから、読んだ行をそのまま入れる。

理由は目的が「復元」だから ── 「取り込み」の口を兼ねると、どちらの場面でも半端になる
（IMPROVEMENTS.md の指摘）。全置換なら「バックアップの中身がそのまま端末の中身になる」の
一文で説明が終わり、ID 衝突という概念そのものが消える。

**すべてが 1 つのトランザクションの中で起きる。**

> **重要**: drizzle の expo-sqlite 実装は `begin` を素で流すだけで、better-sqlite3 のように
> savepoint へ切り替えてはくれない（SPEC-V4 §9-15）。`repository.create()` などは
> 1 件ごとに自分でトランザクションを張るので、**外側で張ってその中でループすると必ず失敗する。**
> よって復元は `db/backup.ts` に**専用の低レベル経路**を持ち、`db.transaction((tx) => ...)` の中で
> `tx.delete` / `tx.insert` を直接呼ぶ。

**既存の入口を使わないもう 1 つの理由は正規化。** `repository.toRow()` は不用品の仕入価格を
0 に落とし（SPEC-V2 §2.4）、売却済みの `saleDate` を現在時刻で埋める（SPEC §5.2）。
それは「人が入力したものを整える」規則で、復元には害になる ── バックアップの値は
既に正規化済みなので、もう一度かけると**書き出したものと違うものが入る**。ここは素通しで書く。

**id も採番し直さない。** 同じ id を書き戻すのが復元で、新しい id を振ったら
`record_tags` の参照先が全部ずれる。

INSERT は **50 行ずつ**に分ける。SQLite の変数上限（既定 999）に対して records は 17 列なので、
全件を 1 文にすると 59 行目で `too many SQL variables` になる。1 件ずつだと 1000 件で
1000 往復して目に見えて遅くなる。

## 4. 写真

> **2026-08-14 改訂。** 当初は「写真を含めない」と決めていたが覆した ──
> **「バックアップ」を名乗る以上、写真も戻せるべき**という判断。
> 覆せた根拠は §6.2 の実測で、破綻の原因が fflate ではなく**圧縮レベル**だったこと。

### 4.1 ZIP に `photos/` を作る

```
profit-calculator-backup_2026-08-14/
├── backup-info.csv     ← photo_count が増えた（版 2）
├── records.csv         ← photo_file_name に**実名が入る**
├── … 他 3 枚
└── photos/<uuid>.jpg
```

写真の実体はドキュメントディレクトリ配下の `photos/` にあり、DB はファイル名しか
持たない（SPEC-V5 §1.2）。ZIP の中でも同じ形にして、`records.csv` の
`photo_file_name` がそのまま `photos/` の中のファイル名を指す。

**写真かどうかは `photos/` の下にあるかで決める**（基底名では見ない）── 基底名だけで
判断すると `photos/records.csv` のような入れ子を CSV と取り違えるし、`photos/` の外の
`.jpg` を写真として拾ってしまう。

**写真を含めないバックアップでも `photo_file_name` は書く。** 空にしてしまうと
「写真があったこと」自体が消え、復元側で「元から無い」と「入れなかった」の区別が付かない。

### 4.2 圧縮レベルは中身で使い分ける（CSV = 6 / 写真 = 0）

fflate はファイルごとに圧縮レベルを指定できる（`Zippable` の値が `[bytes, options]` を取る）。

| 中身 | level | 理由 |
|---|---|---|
| CSV | **6**（deflate） | テキストはよく縮む（1000 件で 145KB → 59KB）。数十 KB なので時間は無視できる |
| 写真 | **0**（store） | **JPEG は既に圧縮済みで deflate が効かない** |

**写真に level 6 をかけるのは丸ごと無駄だった**（§6.2 の実測）:

| | level 6 | level 0 | 差 |
|---|---|---|---|
| 300 枚（56.2MB）の作成 | 33,700ms | **3,571ms** | **9.4 倍速い** |
| 同・展開 | 9,491ms | **57ms** | **166 倍速い** |
| ZIP のサイズ | 54.7MB | 56.2MB | 2.7% 増えるだけ |

**3% 縮めるために 34 秒 UI を止めていた。** 縮まないものを縮めようとする時間が
そのまま損失になっていた、というのが今回の測定でいちばん大きい発見。

**CSV まで level 0 にはしない。** テキストは実際に 2.5 倍縮み、そのコストは
数十 KB に対する数ミリ秒でしかない。「JPEG だから効かない」のであって
「圧縮そのものが無駄」なのではない。

### 4.3 写真が欠けていても復元は止めない

`records.csv` が指す `photo_file_name` について、`photos/` に同名があるかを照合する。

**無くてもエラーにしない。** その記録の `photo_file_name` だけ null にして続け、
完了時に件数で伝える（「写真3枚が復元できませんでした」）。

> **写真 1 枚のために記録 1000 件が戻せなくなるのは本末転倒。**
> 写真は記録の付随物で、欠けても金額も履歴も壊れない。

**逆方向（ZIP にあるが `records.csv` が指していない写真）は検証しない。**
孤児のファイルは容量を食うだけで DB との整合を壊さない ── 書き出さなければそれで終わる。

### 4.4 写真を含めるかは選べる。上限は 50MB

**バックアップを作る画面で選ぶ。既定は「含める」**（バックアップは全部戻せるのが本来）。

**枚数と合計サイズを常に出す**（「写真を含める（53枚・8.2MB）」）── 「含める」が
どれだけの重さなのかは、数字が無いと分からない。

**合計サイズは実体を読まずに出す**（`File.size` だけを見る）。表示のために全部読んだら、
上限を設けた理由（メモリを使いすぎない）と真っ向から矛盾する。

#### 上限 50MB の根拠

**fflate は同期 API で全体をメモリに載せるので、ピークのメモリ使用量が
アーカイブのおよそ 5 倍になる**（§6.2 の実測。187MB のアーカイブで RSS が +939MB、
ピーク 1,322MB）。内訳は 写真のバイト列 ＋ ZIP の出力 ＋ fflate 内部 ＋ GC 未回収分。

iOS の jetsam（メモリ超過によるアプリの強制終了）の上限は端末により
おおむね 1.4GB（3GB 搭載機）〜3GB。**187MB のバックアップは低メモリ端末で確実に落ちる。**
50MB ならピークが +250MB 程度に収まり、どの端末でも届かない。

> **シミュレータで落ちなかったことは根拠にならない。** シミュレータは Mac の
> メモリ上で動くので、実機の jetsam 上限が効かない。2000 枚（375MB）でも
> 落ちなかったが、これは「実機で落ちない」ことを一切意味しない。
> 上限の根拠にしたのは**メモリの実測値**であって、落ちなかったことではない。

#### 上限の見せ方

**押す前に上限の説明は出さない。** 大半の利用者には無関係な数字で、先に見せると
「50MB とは何枚か」を考えさせることになる。**超えた人にだけ、押した後に出す**:

```
写真が多すぎます。
現在 62MB あります（上限 50MB）。

写真を含めずに作りますか？
        [ キャンセル ]  [ 写真なしで作る ]
```

**否定で終わらせず、その場から進める道を出す**（§3.3 のエラーで行き先を名指しするのと同じ）。

### 4.5 復元の手順と、「全か無か」が及ぶ範囲

> **§3 の「1 件でもエラーがあれば一切読み込まない」は、
> 記録・プリセット・タグに対する約束であり、写真には適用しない。**
>
> ファイルシステムにロールバックが無いため、写真の書き出しはトランザクションに
> 入れられない。「全か無か」を写真まで広げようとすると、書き出しに 1 枚失敗しただけで
> DB を巻き戻すことになり、§4.3 の判断（写真のために記録を捨てない）と矛盾する。

手順は 5 段。**2 までが「全か無か」の範囲**:

| | すること | 失敗したら |
|---|---|---|
| 1 | 検証（メモリ上、DB は無変更） | **何も起きない**（§3.2） |
| 2 | `db.transaction` で 4 テーブルを全置換 | **丸ごと巻き戻る**（§3.4） |
| 3 | `photos/` を空にする | — |
| 4 | 写真を 1 枚ずつ書き出す | **復元の失敗とは見なさない** |
| 5 | 書き出せなかった写真の `photo_file_name` を null にする | — |

**手順 2 で既に、欠けている写真を指す記録は `photo_file_name` が null になっている**
（書き戻せる写真の名前を渡すため）。手順 5 が受け持つのは「入れるつもりだったが
書けなかった」ぶんだけ。

**DB が先、写真が後**（`repository.remove` が実体の削除をトランザクションの外でやるのと
同じ理由。SPEC-V5 §1.5）。逆にすると、DB の書き込みが巻き戻ったときに
「記録は残っているのに写真だけ消えた」状態になる。

#### 整合の不変条件

**`photo_file_name` が非 null なら、その実体が `photos/` にある。**

これを崩すと `PhotoThumbnail` が「写真なし」の薄い枠ではなく**壊れた `expo-image`** を出す
（`photoStore.uri()` が null を返さなくなるため）。手順 5 はこの不変条件を守るためにある。

### 4.6 写真がどうなるかは、状況に応じて言い分ける

写真の扱いは**選択と中身で変わる**ので、文言も変える。黙っていると
「これで全部戻る」と思ったまま機種変更する事故になる。

| どこ | いつ | 文言 |
|---|---|---|
| 作る画面 | 写真を含める | 写真も含めて、まるごと元に戻せます。 |
| 作る画面 | 含めない / 写真が 0 枚 | このバックアップに写真は含まれません。 |
| 確認ダイアログ | 写真が入っている | 写真は、いまの写真がすべて消えたうえで、このバックアップの N 枚に置き換わります。 |
| 確認ダイアログ | 入っていない | このバックアップに写真は入っていません。今ある写真は削除され、戻りません。 |

**どちらでも「今ある写真は残らない」ことは共通なので、そこは必ず言う。**
復元は全置換で、`photos/` は必ず一度空になる（手順 3）。

### 4.7 SPEC-V5 の「1 枚 100〜300KB」は実態と合っていない

SPEC-V5 §1.4 の見積もりを実測で検証したところ、**上振れ側に寄りすぎていた**
（長辺 1000px・JPEG 0.7 に縮小した後の実測）:

| 被写体 | 実測 |
|---|---|
| 白背景に商品 1 つ（**フリマの典型**） | **18KB** |
| グラデーション＋質感（一般的な写真） | **61KB** |
| 細かい柄（チェック・プリント。衣類） | **317KB** |
| ランダムノイズ（理論上の最悪） | **371KB** |

**下は見積もりの 1/5、上は見積もり超え。20 倍の開きがある。**
このアプリの主用途である「白背景に商品」は 18〜61KB に収まるので、
50MB の上限は**典型的な使い方なら 800 枚以上**に相当する。
柄物中心（300KB 級）なら 160 枚程度。

**合計サイズは「件数 × 定数」では予測できない**（何を売る人かで 3〜5 倍変わる）ので、
画面には常に実測の合計を出す（§4.4）。

## 5. 画面

### 5.1 導線

設定タブ「データ」群の**3 行目**（書き出し（CSV）の下）。

**書き出しと同じ行にまとめない。** あちらは期間を選んで表計算で読む形を出すもので、
こちらは全件を戻すためのもの。1 つにすると「どちらを押せば機種変更で困らないか」が読めなくなる。

### 5.2 画面の形（設計案 53 系・2026-08-14 改訂）

設定の下への **push**（モーダルにしない）。書き出しシートは「押したらすることが 1 つ」なので
モーダルにしたが（SPEC-V3 §5.7）、こちらは作る／復元するの 2 つがあり、
復元は選ぶ → 確かめる → 実行の 3 段になる。

> **`_layout.tsx` に `Stack.Screen` を宣言していない。** 見出しは画面の中の
> `<Stack.Screen options>` が出すので足す理由がなく、宣言を足すと `index` を先頭に
> 書き直す制約（`settings/_layout.tsx` の冒頭）だけが増える。

**1 つのルートの中に 4 つの状態を持つ**（`src/screens/BackupScreen.tsx`）:

| 状態 | 見出し | 案 |
|---|---|---|
| `create` | バックアップと復元 | 53a / 53b |
| `preview` | 読み込む中身 | 53f / 53g |
| `error` | 読み込む中身（プレビューのまま） | 53h |
| `result` | 読み込みの結果 | 53k |

**ルートを分けない。** 分けると読み込んだ中身（写真のバイト列を含む Map）を
ルートの引数で渡せず、モジュールの外に置き場を作ることになる ──
「選んだファイルは画面を離れたら消える」という今の性質を、置き場の寿命の話に変えたくない。

**4 つの状態はどれも「下端に大きなボタン 1 つ ＋ その下に小さな 2 つ目」で終わる**
（`components/BottomActionBar`）。行き先は違っても、次の一手は常に親指の下の同じ場所にある。

### 5.3 バックアップを作る（案 53a / 53b）

カード 2 枚 ＋ 下端のボタン 1 つ:

1. **バックアップを作る** … 説明（何のために作るか）＋ 件数の帯（記録・タグ・プリセット）
2. **商品の写真** … **2 択のセグメント**（含める / 含めない。§4.4）

**トグルではなく 2 択にする。** トグルは「いま入っているのか」を色と位置だけで示すもので、
選択肢の中に枚数とサイズを書けない ── 写真を含めるかは量の判断なので、
数字が選ぶ瞬間に目に入っている必要がある（`components/ChoiceCardPair`）。

**「含めない」を選んだら 2 か所で言う**（§4.6）── 選択カードの直下の警告と、
**下端のボタン名**（「写真なしで作る」）。作ったあとに気付いても遅い。

**写真が 1 枚も無ければカードごと出さない。** 選ばせるものが無く、
「含めない」の警告（新しい端末で写真が出ない）も嘘になる。

押すとキャッシュ領域に ZIP を作り、OS の共有シートを出す（書き出しと同じ経路。SPEC-V3 §5.6）。
**作っている間はボタンそのものが進捗の帯に変わり**（「作っています...」＋「写真 34枚目 / 53枚」）、
**画面全体が触れなくなる**（連打で 2 回走らせない）。進捗は写真を 1 枚読むごとに
描画へ譲って進める ── 止まって見える時間のほとんどが写真の読み出しなので、そこだけが動けば足りる。

下端のボタンの下に **「前回作ったのは 2026年7月2日」**（`settings/lastBackupAt.ts`）。
通知も催促もしないので、間隔が空いたことに気付く手がかりはこの 1 行しかない。

写真が上限（50MB）を超えていれば、**押した後に下からのシートで受け止める**（§4.4 / 案 53e）──
棒グラフで「あと少しなのか、大幅に超えているのか」まで見せる。
**「やめる」で閉じたときは写真の選択を「含めない」に倒す** ── 元の行き止まりに戻さない。

### 5.4 復元するものを選ぶ → プレビュー（案 53f / 53g）

「バックアップのファイルを選ぶ」/「解凍したフォルダを選ぶ」の 2 つ。

**選んだ時点では読んで検証するだけで、DB には触らない。**
壊れたファイルならここで止まるので、プレビューまで進む時点で
「入ることは確かめ済み」になっている。

読めたら**「今の端末 → ファイル」の差の表**を出す（記録 / タグ / プリセット / 写真の 4 行。
`logic/backupView.ts`）:

- **減る行だけを赤くする。** 「ファイルに 53 件ある」だけでは増えるのか減るのかが読めない
- **写真の行は 0 枚でも消さない** ── 差の表では 0 に意味がある（`31枚 → 0枚`）
- **記録が半分未満になり、かつ 5 件以上減るときだけ注意帯を足す**（古いバックアップを
  選んでいる典型がここに出る。全部に出すと帯そのものが読まれなくなる）
- 表の下に**中で一番新しい記録を 1 件だけ名指しする** ── 件数の一致より強い手がかりで、
  「別の人のファイル」に一瞬で気付ける

**写真の入っていないファイルから戻すときは赤枠のカードを 1 枚足し**（案 53g）、
ボタン名も「写真なしで置き換える」に変える ── 損失が二重（入ってこない ＋ 今あるものが消える）。

> 取り消しの扱いが 2 つの口で違う。ファイル選択（`File.pickFileAsync`）は
> `{ canceled: true }` を返すが、**フォルダ選択（`Directory.pickDirectoryAsync`）は
> 例外で返す**（`FilePickingCancelledException`）。型の付いた判別の口が無いので、
> フォルダ側だけは文字列で判定して**何も出さずに閉じる** ── 取り消しのたびに
> 「使えません」と出す方が害が大きい。

### 5.5 確認ダイアログは持たない（2026-08-14 改訂）

**旧: `Alert.alert('今あるデータをすべて置き換えます')` を挟んでいた。**

**プレビューの 1 枚が確認そのもの**にした（案 53f）。ダイアログでは
「今あるものがどうなるか」を数字で並べられず、閉じると理由が残らない。
押す前に読ませたいこと ── 差の表・「元には戻せません」の赤い 1 文・赤いボタン ──
がすべて同じ画面に並んでいるので、そのうえで指を置く場所は下端の 1 か所だけになる。

### 5.6 実行後（案 53k）

**ダイアログではなく画面で受ける。** 押した瞬間に消えるダイアログでは
「本当に入ったか」を確かめ直せない。

緑のチェック ＋「復元しました。」＋ 件数の表（記録 / タグ / プリセット / 写真）。
件数は**DB から数え直して**出す。

**戻せなかった写真があれば、その行だけを赤くする**（`17枚（3枚は復元できず）`。§4.3）──
1 枚でも欠けていたら黙らない。理由と対処は表の下に**警告色を使わずに**置く
（復元そのものは成功していて、金額も日付も入っている）。
どの写真かは言わない（ファイル名は UUID で意味が無い）が、
**どの記録かは「写真がなかった3件を見る」でその場に開く** ── 撮り直す先が分かる。

### 5.7 読み込めなかったとき（案 53h）

**ダイアログではなく画面の中の赤枠のカード。** ダイアログは 3 行が同じ大きさの塊になり、
閉じると行番号が消える（家族に見せながら相談することもできない）。

見出し（赤）→ 理由（どのファイルの何行目の何が悪いか）→ 対処 →
**3 行目だけは緑の帯**（「現在のデータは変更されていません。」）。
赤の中に同じ色で埋めると読み飛ばされるが、失敗したときに一番知りたいのは「壊れていないか」。

下に選んだファイルのカードを**不活性のまま残す**（何を選んだのかを画面から消さない）。
**件数は出さない** ── ファイルが自分で名乗っている数は検証を通っておらず、
並べると「読めたところまでは正しい」と読まれる（決定 §8-4）。

下端は「別のファイルを選ぶ」＋「この内容をコピーする」（**長押しではなく普通のボタン**。
長押しは金額の行（`LongPressCopy`）でだけ使う作法にしている）。

## 6. 性能（実測）

iPhone 17 Pro シミュレータ（iOS 26.0）・デバッグビルドでの実測値。

### 6.1 写真なし（CSV だけ）

| 記録件数 | 作成 | 読み込み ＋ 検証 | 復元（DB 書き込み） | ZIP |
|---|---|---|---|---|
| 53 | **84ms** | 67ms | 32ms | 7.4KB |
| 503 | **143ms** | 121ms | 168ms | 30.8KB |
| 1003 | **237ms** | 180ms | 296ms | 58.8KB |

内訳（1003 件）: `dump` 46ms ／ CSV 組み立て 8ms ／ ZIP ＋ 書き込み 183ms。
読み込みの内訳は展開 131ms ／ 解析と検証 49ms。

`__MACOSX` の入った ZIP（Finder で再圧縮した形）はエントリ数が倍以上になるぶん
展開が遅く、1003 件で 255ms（通常は 131ms）。

### 6.2 写真あり（圧縮レベルの比較 ＋ メモリ）

混合の写真（平均 192KB/枚）で測った。**§4.2 の level 0 と、§4.4 の 50MB 上限の根拠。**

| 枚数 | 写真計 | 作成 L6 | 作成 **L0** | 展開 L6 | 展開 **L0** | 書き出し |
|---|---|---|---|---|---|---|
| 20 | 3.7MB | 2,366ms | **232ms** | 643ms | **5ms** | 35ms |
| 50 | 9.4MB | 5,710ms | **551ms** | 1,602ms | **8ms** | 67ms |
| 100 | 18.7MB | 11,354ms | **1,137ms** | 3,166ms | **28ms** | 92ms |
| 200 | 37.5MB | 22,332ms | **2,196ms** | 6,298ms | **54ms** | 175ms |
| 300 | 56.2MB | 33,700ms | **3,571ms** | 9,491ms | **57ms** | 275ms |

ZIP のサイズは L6 で 54.7MB、L0 で 56.2MB（**2.7% しか縮まない**）。
**3% のために 34 秒 UI を止めていた**、というのが level 0 を選んだ理由（§4.2）。

L0 でさらに伸ばした結果（限界の探索）:

| 枚数 | 写真計 | 作成 | 展開 | 書き出し |
|---|---|---|---|---|
| 500 | 93.7MB | 5,855ms | 107ms | 446ms |
| 800 | 149.9MB | 8,858ms | 160ms | 736ms |
| 1200 | 224.8MB | 13,276ms | 264ms | 1,084ms |
| 2000 | 374.7MB | 22,160ms | 452ms | 1,815ms |

**クラッシュはしなかった。だがそれは根拠にならない**（§4.4 の注記）。
実測したのはメモリの方:

| | RSS |
|---|---|
| 起動直後 | 383MB |
| 1000 枚（187MB）の処理中のピーク | **1,322MB**（**+939MB**） |

**アーカイブのおよそ 5 倍**。これが 50MB 上限の根拠（§4.4）。

### 6.3 実装した経路の実測（写真あり / なし）

§6.2 は計測用の治具での数字。**実装した画面をそのまま操作した実測**は次のとおり
（記録 53 件・iPhone 17 Pro シミュレータ）:

| | 写真 | 作成 | 読み込み ＋ 検証 | 復元（DB / 書き出し） | ZIP |
|---|---|---|---|---|---|
| 写真なし | 0 枚 | **43ms** | — | — | 7.6KB |
| 写真あり | 51 枚 / 15.5MB | **1,027ms** | 40ms | 43ms / **68ms** | 15.5MB |
| 写真あり | 101 枚 / 31.0MB | **2,083ms** | 83ms | — | 31.0MB |

作成の内訳（51 枚）: `dump` ＋ 写真の読み込み 111ms ／ CSV 組み立て 0ms ／ **ZIP 916ms**。
**時間のほとんどは ZIP の組み立て**で、写真の枚数にほぼ比例する（51 枚 916ms → 101 枚 1,849ms）。

**復元は作成よりずっと速い**（15.5MB で 111ms）── 展開が store なので実質コピーで、
書き出しもファイルシステムに任せるだけだから。**遅いのは作る側だけ**。

上限の 50MB ではおよそ **3.5 秒**（§6.2 の 300 枚 3,571ms）になる見込み。

### 6.4 busy 表示

**要る。** 写真なしなら 43ms で終わるが、**写真を含めると 51 枚で 1 秒、上限の
50MB では約 3.5 秒**（§6.3）。その間 fflate の同期 API が JS スレッドを止めるので、
画面はタップに反応しない。印が無いと固まったように見える。

ボタンは実行中は非活性にし、進捗（ActivityIndicator）を出す。
**進捗率は出さない** ── `zipSync` は途中経過を返さないので、出せるのは
「動いている」ことだけ。

> 1 つの器にまとめると `icon?` `dimmedCard?` `table?` と片方でしか使わない props が並び、
> 中身を読まないとどちらの画面が出るのか分からなくなる。

**ZIP は `fflate`（MIT / 依存ゼロ / 純粋 JS）。**
選定の経緯は §7.1。**同期 API（`zipSync` / `unzipSync`）しか使わない** ──
非同期 API は Web Worker で並列化する作りで、React Native には Worker が無い。

### 7.1 なぜ fflate か（`react-native-zip-archive` を採らなかった理由）

`ios/` と `android/` は `.gitignore` されており、このリポジトリは
**prebuild でネイティブを毎回生成する構成**（CNG）。ネイティブ依存を足すと
「クローンした人が必ず再ビルド」がついてくる。

fflate は純粋 JS なので `npm install` だけで済み、**依存パッケージがゼロ**。
`package.json` の `exports` により Metro は Node 用の worker を含まない
ブラウザ向けビルドを解決する（Metro は `unstable_enablePackageExports` が既定で真）。

`react-native-zip-archive` は健全なライブラリ（MIT / New Architecture 対応）だが、
その利点は「巨大ファイルをパス経由でストリーム処理できる」こと。
**写真を含めるようになった今でも、上限 50MB（§4.4）の中では fflate で足りる**
（作成 3 秒 / 展開 0.06 秒。§6.2）。

**上限を上げたくなったら**、まず fflate のストリーミング API
（`Zip` / `ZipPassThrough` / `Unzip` / `UnzipInflate`）を検討する ── これらは
Worker を使わない同期コールバック方式（Worker を使うのは `Async*` 系だけ）で、
expo-file-system 側にも `File.open(mode)` → `FileHandle.writeBytes` があるため、
全体をメモリに載せずに逐次書き出せる見込みがある。**未検証。**

## 8. 決定の記録

### §8-1 ZIP とフォルダの名前を ASCII に限る
ZIP のエントリ名の文字コードは規格上あいまいで、日本語だと解凍ツールによって化ける。
化けた名前は復元時に引けなくなる。書き出しの CSV（日本語名）とは扱いを変える。

### §8-2 解凍したフォルダも受け付ける
§0.3 のとおり「CSV にしたのは中身を確かめられるようにするため」なので、
確かめた（＝解凍した）状態から復元できないと決定と矛盾する。

### §8-3 `__MACOSX` などを黙って無視する
「知らないファイルがあるので読めない」と言うと、Finder で再圧縮しただけの
利用者が復元できなくなる。無視して困る場面が無い（要る 5 枚は名前で引く）。

### §8-4 `backup-info.csv` の件数を信用しない
書いてある数と実データが食い違うのは「手で行を削った」ときで、
それは検出すべき異常。数え直せば食い違いようがない。

### §8-5 復元専用の低レベル経路を新設する
既存の repository は 1 件ごとにトランザクションを張り、入れ子にできない（§3.4）。
加えて保存時の正規化が復元には害になる。2 つとも既存の入口を再利用できない理由。

### §8-6 ファイル名にアプリ名を入れる（2026-08-14 改訂）
当初は `backup_2026-08-14.zip` だったが、保存先には他のアプリのバックアップも並ぶ。
何のバックアップか分からないファイルは、**機種変更という「1 回しかない場面」で
選び間違える**。読み込みは名前を見ない（§3.1）ので、旧名のファイルはそのまま読める。

### §8-7 「書き出し（CSV）」と「バックアップ」の関係を両画面で言う（2026-08-14 追記）
**どちらも CSV が出てくるので、画面の名前だけでは区別が付かない**（§10.1）。
片方だけに注記を出しても、もう片方から入った人には届かない。

なお、この追記に伴い**書き出し画面の既存の注記から「バックアップにも使えます」を外した** ──
SPEC-V3 §5.2 の時点では唯一の書き出しだったので正しかったが、本書で本物の復元が入って
**嘘になった**（§0.2 のとおり読み戻せない）。同じ画面に「復元には使えません」と
並ぶことになるので、残すと真っ向から矛盾する。

---

### §8-8 写真を含める（2026-08-14 改訂）
当初は「含めない」と決めていた（サイズが理由）。覆したのは、**破綻の原因が fflate ではなく
圧縮レベルだった**と実測で分かったため（§4.2 / §6.2）── level 0 にすれば 50MB が
実用範囲に入る。「バックアップ」を名乗る以上、写真も戻せるべきという判断が先にあり、
それを可能にする根拠が測定で得られた形。

### §8-9 「全か無か」を写真に広げない（2026-08-14 追記）
ファイルシステムにロールバックが無いので、写真の書き出しはトランザクションに入れられない。
広げようとすると 1 枚の失敗で DB を巻き戻すことになり、**「写真のために記録を捨てない」
（§4.3）と矛盾する**。約束の範囲を記録・プリセット・タグに明示的に限る（§4.5）。

## 9. 解決した未決着事項（`docs/IMPROVEMENTS.md`）

IMPROVEMENTS.md の「ZIP でのバックアップ」「CSV の読み込み」に残っていた論点のうち、
本書で決まったもの:

| 論点 | 本書の決定 |
|---|---|
| ID が衝突したときの扱い（A / B / C） | **どれも採らない。全置換**（§3.4） |
| 読み込みの目的（復元か取り込みか） | **復元のみ。**取り込みの口は作らない（§3.4） |
| タグが存在しないときの色をどう決めるか | **論点ごと消えた。**タグは実体ごとバックアップに入る（§2.1） |
| 同名タグを同じものとみなすか | 同上（id で入るので名前の一致を見る場面が無い） |
| タグ名の禁則に反する値の扱い | 同上（アプリが書いた値しか入らない。壊れていれば §3.2 で弾く） |
| 確定申告用（11 列）は読み込めない | **読み込みの対象にしない。**別形式にした（§0.2） |
| 列が足りない / 多い CSV の扱い | **列名で対応を取り、過不足はエラー**（§3.2） |
| 金額の桁区切り | **受け付けずエラー**（§2.2） |
| 日付の形式 | **`YYYY-MM-DDTHH:mm:ss.SSS` 固定。**それ以外はエラー（§2.3） |
| 時刻が落ちている | **落とさない**（§2.3） |
| 計算値の列は読まない | **そもそも書かない**（§2.1） |
| 途中で失敗したときの扱い | **1 件でもエラーなら一切読み込まない**（§3.2 / §3.4） |
| 入口をどこに置くか | **設定タブ「データ」群の 3 行目**（§5.1） |
| `expo-document-picker` が要る | **要らない。**`File.pickFileAsync` が SDK 54+ にある（§5.4） |
| 読み込む前に見せる | **件数と作成日をプレビューする**（§5.4） |
| ZIP を書き出しの 3 つ目の選択肢にするか | **しない。別の導線にした**（§0.2 / §5.1） |
| 共有シートに ZIP を渡せるか（未検証だった） | **渡せる。**実機で確認（ZIP Archive として認識される） |
| 写真をどう入れるか | **入れる**（§4）。`photos/` に置き、level 0 で圧縮しない。上限 50MB |

**本節の論点はすべて決着した。** 最後まで残っていた「写真ごと戻せるようにするか」は
2026-08-14 に **入れる**で決着（§4）── 破綻の原因が fflate ではなく圧縮レベルだった、
という実測が根拠（§6.2）。

**残るのは上限だけ。** 写真の合計 50MB を超えるバックアップは作れない（§4.4）。
上げたくなったら fflate のストリーミング API を検討する（§7.1。未検証）。

## 10. 中身の CSV をどう位置づけるか

### 10.1 「書き出し」と紛らわしいことを、両方の画面で言う

設定タブ「データ」群には「書き出し（CSV）」と「バックアップと復元」が並び、
**どちらを押しても CSV が出てくる。** 名前だけでは区別が付かないので、
**両方向に注記を出す**（決定 §8-7）:

| 画面 | 文言 | 置き場所 |
|---|---|---|
| 書き出し（CSV） | このCSVは復元には使えません。機種変更などでデータを移すときは「バックアップと復元」をお使いください。 | 「種類」の節のすぐ下（**種類に関わらず常に出す**） |
| バックアップを作る | 中身はCSVですが、確認用です。編集して読み込むことは想定していません。 | カードの外・ボタンの下 |

書き出し側で**行き先を名指しする**のは、否定だけで終わらせないため。
「使えません」だけでは、では何を使えばいいのかが分からない。

バックアップ側の注記を**カードの外に置く**のは、写真の注記（§4.3-1）と重さが違うから ──
写真は知らないと失う（戻らない）が、こちらは知らなくても損はしない。
カードの中に並べると 2 つが同じ重さに見え、**写真の警告が薄まる**。

### 10.2 編集は想定していない（が、禁止もしない）

**CSV にしたのは「人が中身を確認できるようにするため」**（§0.3）であって、
編集して読み込ませるためではない。検証は列名・列数・型・参照まで見る（§3.2）ので、
手で触ると弾かれる方が普通。

**iOS 単体では、そもそも編集できない。**

- ファイルアプリで ZIP を長押しすれば解凍でき、CSV をタップすればプレビューできる。
  **ここまでは iOS だけでできる。**
- だが**編集して CSV のまま保存し直す標準の手段が無い。** Numbers で開くと
  読み込めはするが、保存すると `.numbers` 形式になる ── **CSV に書き戻せない**ので、
  そのファイルは復元に使えなくなる。書き出しはできるが、その操作を知っている人向け。
- したがって**編集するなら Mac / PC が前提**になる（テキストエディタか、
  CSV のまま保存できる表計算ソフト）。

**それでも禁止する実装は入れない。** チェックサムも署名も持たない ──

- 壊れたファイルは**検証が弾く**（§3.2）ので、守るべきものは既に守られている。
  署名を足しても防げるのは「意図的な改変」だけで、それは事故ではない
- 逆に、**手で直せることが役に立つ場面がある** ── 1 行だけ壊れたバックアップを
  エラーの行番号（§3.3）を頼りに直して読み込む、という道を塞ぐ理由がない
- 文言を「編集できません」ではなく「**想定していません**」にしてあるのはこのため。
  できないことにしていない
