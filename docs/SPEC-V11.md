# 絞り込みの拡張 仕様 — SPEC-V11

絞り込みの条件を **3 本から 9 本へ**増やす。増えるのは
**純利益の範囲・販売価格の範囲・経費の範囲・目標の達成／未達・赤字のみ・メモの有無**の 6 本。

**本書は SPEC-V4 §4 より後発**で、絞り込みに関する記述が衝突する場合は本書が優先する。
改訂するのは SPEC-V4 §4.1（`activeFilterCount` の上限 3）・§4.2（節は 3 つ）・
§4.8（効き得る条件は 6 つ）の 3 か所で、**§4.4（`EXISTS` を使い `DISTINCT` は使わない）・
§4.5（`buildWhere` に条件を足す）・§4.6（下部の件数）・§4.7（消えたタグ）は変えない** ──
どれも「条件を 1 か所に足せば全経路に効く」という形の決めごとで、条件が増えるほど効く。

**触っていないもの**: 期間・検索・並び替え（下書きの外にある。§4.1）、
確定申告用 CSV（SPEC-V3 §5.5：絞り込みを持ち込まない）、`filterNoMatchNote`（§7.3）、
計算式（SPEC §2 の 7 関数）、マイグレーション（**列は 1 つも足さない**）。

| | SPEC-V4（3 本） | 本書（9 本） |
|---|---|---|
| 条件の本数 | 種別・販売サイト・タグ | ＋ 純利益・販売価格・経費・目標・赤字・メモ |
| 画面の構造 | 節が 3 つ、すべて開いたまま | **5 群の折りたたみ**（§2） |
| 解除の口 | ヘッダの「すべて解除」1 つ | ＋ **群ごとの解除**（§3） |
| 青い行 | 条件を全部「・」で連ねる | **先頭 2 つ ＋「ほか N 条件」**（§5） |
| 新しい列 | — | **無い**（既存の列と既存の集計式だけで書ける） |

---

## 0. 背景

### 0.1 3 本は「どの記録か」しか絞れない

いまの 3 条件（種別・販売サイト・タグ）は、どれも**記録に貼られた名札**を見ている。
「不用品の」「フリマ A の」「洋服の」── 記録を**分類**で切る条件しかない。

一方でこのアプリが毎日出している数字は**金額**（純利益・販売価格・経費）で、
記録タブの行にも、データタブのグラフにも、レコード詳細の帯にも金額が出る。
**画面が金額を主役にしているのに、絞り込みだけが金額を持っていない。**

実際に効かせたい場面はどれも金額の側にある:

- 「利益が 1,000 円に届かなかったものだけを見たい」（値付けを直す）
- 「経費が 3,000 円を超えたものだけを見たい」（送料と梱包材を見直す）
- 「赤字になったものだけを見たい」（同じ失敗を繰り返さない）
- 「目標を決めたのに届かなかったものだけを見たい」（SPEC-V9 の目標が記録に残るようになった）
- 「メモを書いたものだけを見たい」（あとで読み返すために書いたのに、探す口がない）

**どれも既存の列と既存の集計式で書ける。** `netProfitSql` / `totalExpensesSql` は
すでに一覧の並び替えと集計に使っている式で（repository.ts）、`target_profit` は SPEC-V9 が、
`memo` は初版が持っている。**足りていなかったのは条件の側だけ**で、データは最初から揃っていた。

### 0.2 「3 条件ちょうどで、これ以上増やさない」を破る

`recordFilter.ts` の型のコメントは「3 条件ちょうどで、これ以上増やさない」と書いていた。
**この歯止めが守っていたのは条件の本数ではなく、次の 2 つ**である:

1. **期間・検索・並び替えを下書きに巻き込まない**こと（§4.1）──
   どれもシートの外に専用の UI があり、効いていることが画面から直接読める。
   下書きに入れると「絞り込みを解除」がそれらまで巻き戻す口になる。
2. **画面が縦に 3 つ並ぶだけで読み切れる**こと ── 節が増えるほど、
   いま何が効いているのかを画面の上から下まで見ないと分からなくなる。

**1 は本書でも守る。** 増える 6 本はすべて記録そのものの値（金額・目標・メモ）で、
**画面の外に専用の UI を持たない** ── だから下書きに入れる以外に置き場所がない。
期間と検索が下書きの外に居続ける理由は、本書によって強まりこそすれ弱まらない
（`EMPTY_RECORD_FILTER` のキーを数えるテストはそのまま残す）。

**2 は形を変えて守る。** 9 つの節を平らに並べると縦に読み切れないので、
**折りたたみの群にして、効いている群だけを開く**（§2）。
画面を開いた瞬間に見えるのは「群の名前と、効いている数」だけで、
読む量は条件の本数ではなく**群の数（5）**で決まる。

つまり歯止めは撤回ではなく**置き換え**である:

> 旧: 条件は 3 本まで。
> 新: **条件は下書きの外に UI を持たないものだけ。読む量は群の数で抑える。**

### 0.3 送料・梱包材での絞り込みは見送る（回 2）

検討したが本書には入れない。`postage` / `envelopeCost` は
**経費の範囲（`totalExpensesSql`）に既に含まれている**ので、内訳ごとの範囲を足すと
「経費 3,000〜」と「送料 500〜」が同時に効いたときの意味が画面から読めない
（前者は後者を含むが、含んでいることは画面のどこにも書けない）。
金額の群が 3 本で止まっているのはそのためで、**合計だけを条件にする**という線を引いている。

## 1. 増える 6 条件

### 1.1 下書きの形

`RecordFilterDraft` に 9 つのキーを足す（条件は 6 本だが、範囲は min / max の 2 欄を持つ）。

| キー | 型 | 条件 | 何本 |
|---|---|---|---|
| `kind` | `KindFilter` | 種別（既存） | 1 |
| `siteName` | `string \| null` | 販売サイト（既存。§4 で `''` = 未設定を足す） | 1 |
| `tagIds` | `string[]` | タグ（既存。OR） | 1 |
| `amounts.netProfit` | `{ min: string; max: string }` | `netProfitSql` の範囲 | **1** |
| `amounts.salesPrice` | 〃 | `sales_price` の範囲 | **1** |
| `amounts.expenses` | 〃 | `totalExpensesSql` の範囲 | **1** |
| `targetStatus` | `'met' \| 'missed' \| null` | 目標の達成／未達 | 1 |
| `lossOnly` | `boolean` | 赤字のみ | 1 |
| `memoState` | `'with' \| 'without' \| null` | メモの有無 | 1 |

**範囲は min / max の両方を入れても 1 本**と数える（§1.4）。
3 本を `amounts` にまとめるのは、**画面が同じ形の欄を 3 つ並べるだけ**になるから
（`AMOUNT_RANGE_KEYS` を `map` する）── 平らに 6 キー置くと、
群の数え方も解除も欄の描画も 3 回ずつ書くことになる。
repository へ渡す形（`RecordFilterConditions`）では平ら（`netProfitMin` …）に開く ──
SQL 側は範囲を 2 本の不等号として受けるので、そちらの都合に合わせる（§1.2）。

**範囲を数値ではなく文字列で持つ。** 入力中の `"1000."` や `""` を数値に畳むと、
打っている途中の状態を下書きが表せない（`0` と「未入力」の区別も付かない）。
**下書きは画面が編集しているものそのもの**なので、入力欄の値をそのまま持ち、
数値化は repository へ渡す直前（`toFilterConditions`）で 1 回だけ行う。
副産物として、**「すべて解除」も群ごとの解除も入力欄を空に戻すだけで済む**
── 下書きと入力欄が別々に state を持つと、片方だけ戻る事故が必ず起きる。

### 1.2 SQL（列は足さない）

`buildWhere` / `buildAnalyticsWhere` の**両方に同じ式**を足す（§4.5 の作法どおり）。
2 か所に別々に書かないよう、共有の条件を組む関数を 1 つ置き、両方がそれを呼ぶ。

| 条件 | 式 |
|---|---|
| 純利益の範囲 | `netProfitSql >= ?` / `netProfitSql <= ?`（片側だけでも効く） |
| 販売価格の範囲 | `sales_price >= ?` / `sales_price <= ?` |
| 経費の範囲 | `totalExpensesSql >= ?` / `totalExpensesSql <= ?` |
| 目標を達成 | `target_profit IS NOT NULL AND netProfitSql >= target_profit` |
| 目標に未達 | `target_profit IS NOT NULL AND netProfitSql < target_profit` |
| 赤字のみ | `netProfitSql < 0` |
| メモあり | `trim(memo) <> ''` |
| メモなし | `trim(memo) = ''` |

- **`BETWEEN` ではなく 2 本の不等号にする。** 片側だけ入れられる（「1,000 円以上」だけ）ので、
  両側が揃ったときだけ使える構文では書けない。両側揃えば同じ結果になる。
- **目標は `IS NOT NULL` を必ず伴う。** `target_profit` は「決めていません」を `null` で表す
  （SPEC-V9 §1.2）ので、これを落とすと**目標を決めていない記録が「未達」に混ざる**
  （SQLite の比較は `null` で `null` を返し、`WHERE` では偽になる ── つまり `<` だけでも
  結果は同じになるが、**式を読んで意味が分かる形にしておく**）。
- **`0` は有効な目標**（SPEC-V9 §1.2）なので、`target_profit > 0` のような防御は入れない。
- **メモは `trim` する。** 空白だけのメモを「あり」と数えると、書いたつもりのないものが混ざる。

### 1.3 赤字は範囲ではなく独立した 1 本

純利益の範囲があるのに「赤字のみ」を別に持つのは、**入力欄に負の数を入れられない**ため。
金額の欄は `sanitizeNumericInput`（`input.ts`）を通す ── 数字と小数点以外を落とすので
`-` が消える（SPEC §5.1 / 決定 §7-9）。アプリ中の金額入力はすべてこの規則で、
**絞り込みだけ負号を通すと、記録フォームと電卓で入る値の形が食い違う。**

負の側を切るのは「いくらの赤字か」ではなく「赤字かどうか」で足りるので、
**境界を 0 に固定した 1 本のスイッチ**に置き換える。
これで負の数を入力させずに赤字を絞れる（そして 0 は黒字側に入る ── `netProfit < 0`）。

### 1.4 `activeFilterCount` は 3 → 9

**範囲は min / max の両方を入れても 1 本**と数える。
タグを何個選んでも OR なので 1 本、というのと同じ規則である ──
**数えるのは「効いている条件の本数」であって、入力欄の数ではない。**

数え方が群ごとの数（§3）と食い違わないよう、
`activeFilterCount` は**群ごとの本数の合計**として実装する（5 群を足すだけ）。
2 か所で別々に数えると、群の見出しの数字と青い行の条件数がずれる。

## 2. 画面 — 折りたたみの 5 群

9 つの節を平らに並べない。**5 つの群に畳む。**

```
種別 △                                          ← 常に開く（§2.2）
  ( すべて | 不用品 | 仕入品 )
販売サイト ▽                      1条件  解除
タグ ▽
金額 △                            2条件  解除
  純利益      [      ] 〜 [      ]
  販売価格    [      ] 〜 [      ]
  経費        [      ] 〜 [      ]
その他 ▽
```

| 群 | 中身 | 条件の本数 |
|---|---|---|
| 種別 | セグメント「すべて / 不用品 / 仕入品」 | 1 |
| 販売サイト | 単一選択の行（§4） | 1 |
| タグ | 複数選択の行 ＋ 検索欄 | 1 |
| 金額 | 純利益・販売価格・経費の範囲（§6） | 3 |
| その他 | 目標を達成 / 目標に未達 / 赤字のみ / メモあり / メモなし | 3 |

### 2.1 群の名前は「種別」であって「種別・状態」ではない

状態（売れた記録 / 出品中）の切替を絞り込みページへ持ってくることは**しない**。
状態は下書きの外にあり（`RecordFilterState.isSoldMode`）、
**この画面の分岐の元になっている値**である ── 販売サイトの節を消すか、
目標の節を消すか、下部の見出しをどちらにするかが、すべてこの値で決まる（§7）。
**分岐の元を、その分岐で描かれている画面の中から動かせるようにすると、
節が自分を消す操作を持つことになる。** 群の名前を「種別」に留めるのはその線引きである。

### 2.2 初期の開閉は**マウント時に一度だけ**決める

```
種別   … 常に開く
それ以外 … その群に効いている条件があれば開く
```

**描画のたびに評価してはいけない。** 「効いていれば開く」を毎描画で計算すると、
**その群の最後の 1 つを外した瞬間に節が閉じ、いま押した行が画面から消える。**
押した結果として自分が消えるのは、操作の取り消し方が分からなくなる最悪の形
（案 `35b`「押した行の位置を動かさない」の延長にある問題で、動かすどころか消える）。

したがって開閉の初期値は `useState` の初期化関数で 1 回だけ決め、
**以降は利用者の開閉操作だけで動く**。絞り込みページは push される 1 枚のページなので、
戻って開き直せば新しい下書きで評価し直される（state ごと作り直される）。

**種別を常に開くのは、9 本のうちいちばん粗い切り方だから。**
何も効いていない状態で開いたとき、5 つの畳まれた見出しだけが並ぶと
「ここで何ができるのか」が読めない ── 1 つ開いておけば、群の中身の形が例で分かる。

### 2.3 群は `Accordion`（使いかたと同じカード）にする

**見出しの時点からカードの中にある形にする** ── 使いかたの画面（HelpScreen）と同じ `Accordion`。

> **当初は `CollapsibleSection`（見出しはカードの外・中身だけがカード）で作り、実機で退けた。**
> 理由は 2 つ:
> - **閉じている群が「押せる行」に見えない。** 地色のない見出しが 5 つ並ぶと、
>   節の名前を書いた注記の列にしか読めず、押して開くものだと分からない。
> - **開いている群と閉じている群で面の作りが変わる。** 開くとカードが生え、閉じると
>   文字だけが残る ── 同じ 5 つが並んでいるのに、開閉で別の部品に見える。
>
> `Accordion` なら開いても閉じても**群 1 つ = カード 1 枚**で、
> 5 つ並んだときに面が読める。使いかたの画面で既に使っている形なので、
> アプリの中で折りたたみの見え方が 2 通りにならない、という利点もそのまま乗る。

**二重カードは、中の `Card` をやめることで避ける**（`Accordion` を避けるのではなく）。
群そのものがカードなので、中身は素の行と欄でよい。そのために `Accordion` へ
`contentStyle` を 1 つ足し、**中身の左右・下の余白を外せる**ようにする:

- **行の一覧（販売サイト・タグ・その他）と金額の欄は、カードの端まで届かせる。**
  選択中の行の青い地が余白の手前で切れると、行ではなく**帯が浮いて**見える。
  行は自分で左右 16 の余白を持っているので、群の側の余白は邪魔になるだけ。
- **余白の要る中身**（種別のセグメント・タグの注記と検索欄・空表示・検索結果の 1 行）は、
  その中身の側が余白を巻く（`Inset`）。
- **見出しと 1 行目の間にも区切り線を 1 本入れる。** 群がカードそのものになったので、
  線が無いと 1 行目が見出しの続きに見える。

**タグの節の右にあった注記**（「どれかが付いた記録が出ます」）は、
右端が群ごとの解除（§3）に取られるので**カードの中の 1 行目へ降ろす**。
選ぶ前に読んで分かる語であることは変わらない（案 `35a` の趣旨）。

## 3. 解除の導線 — 群ごとの解除を置く

**ヘッダの「すべて解除」だけでは足りない。** 条件が 3 本のときは、
外したい 1 本を外すのも全部消してやり直すのも手間が変わらなかった。
9 本になると「金額だけ外したい」に対して**全部消す**しか用意がないことになり、
残したい 7 本を入れ直させることになる。

**群の見出しの trailing に「効いている数 ＋ その群だけ解除」を置く。**

- 効いている数が 0 の群には**何も出さない**（押せない「解除」が並ぶと、
  どの群が効いているのかが数字ではなく色で読む話になる）。
- 数と解除は**同じ 1 つの押せる領域**にする。数だけを見出しの右に置いて
  解除を別に足すと、見出し行に押せるものが 3 つ（開閉・数・解除）並ぶ。
- **押しても群は閉じない**（§2.2 と同じ理由）。解除した結果が
  「空になった群」として見えているほうが、消えるより読める。
- 全部の群を解除すればヘッダの「すべて解除」と同じ状態になる。
  **どちらも `EMPTY_RECORD_FILTER` へ向かう**ので、下書きの初期値は 1 か所のまま。

## 4. 販売サイトの節

3 つ足す。**どれも「選べるはずのものが選べない」を潰すための追加。**

### 4.1 使用件数を行に出す（`countsBySiteForFilter`）

タグの行と同じ形（§4.2.1）。**「押したら何件出るか」の予告**なので、
数え方もタグと同じにする ── **渡された条件から `siteName` だけを外して数える**。
外すのは、いま「フリマ A」を選んでいる状態で「フリマ B」の行に
`フリマA AND フリマB` の数（＝必ず 0）が出るのを避けるため。
単一選択なので押せば置き換わる、その結果を予告する数字でなければならない。

タグと違い `EXISTS` は要らない（記録が持つのは 1 つの名前なので、
`site_name` で `GROUP BY` すれば 1 本のクエリで全候補ぶん数え終わる）。

### 4.2 「未設定」の行を足す

**販売サイトを入れていない記録を絞る口がなかった。** 候補は記録に実在する名前だけなので、
名前が入っていない記録は**どの行を押しても出てこない**（「すべて」に戻すしかない）。

条件としては `site_name = ''` で、下書きでは `siteName: ''` で表す
（`null` = すべて／`''` = 未設定／その他 = その名前）。
`buildWhere` は従来 `siteName !== ''` を無条件扱いにしていたので、**この判定を落とす**
── 空文字を「指定なし」と読む経路が 1 つでも残ると、未設定の行が静かに効かなくなる。

**並びの末尾に置く。** 候補は名前の昇順で、未設定には名前がない ──
並びの中に居場所がないので、揃った並びを崩さない末尾に置く。

### 4.3 未使用の販売サイトも候補に出す（プリセットを合併）

候補が「記録に実在する名前」だけだと、**プリセットに登録したばかりのサイトが出てこない**。
登録した名前は利用者にとって既に存在するもので、
「まだ 1 件も売れていない」ことは候補から消える理由にならない（件数 0 と出せばよい）。

`useSiteNames()`（記録に実在する名前）と `usePresetList('site')` の名前を**合併**し、
重複を除いて昇順に並べる。

**選択中の名前は必ず候補に含める。** プリセットを消しても、記録から名前が消えても、
下書きの条件は残る ── 候補から落ちると**効いているのに画面から選択が消え、外す口もなくなる**
（消えたタグを `pruneMissingTags` で落とすのと同じ問題だが、
販売サイトは名前そのものが条件なので落とす必要がない。**候補に足すほうで解く**）。

---

## 5. 青い行 — 先頭 2 つ ＋「ほか N 条件」

`filterSummaryText` は効いている条件を「・」で全部連ねていた。3 本なら 1 行に入るが、
9 本では入らない（「仕入品・販売サイト「フリマA」・タグ「洋服」ほか2件・
純利益 1000円〜5000円・販売価格 〜3000円・経費 500円〜・目標を達成・赤字のみ・メモあり」）。

**先頭 2 つを出し、残りは「ほか N 条件」に畳む。**

```
仕入品・販売サイト「フリマA」・ほか7条件の14件だけ
```

**「ほか N 条件」は 3 つ目の部分として同じ区切りで連ねる**（末尾にくっつけない）──
タグ自身が「タグ「洋服」ほか1件」と畳んでいるので、くっつけると
「ほか1件ほか5条件」と 2 つの畳みが隣り合って読めなくなる。

- **タグが既にやっている畳み方をそのまま広げる。** タグは「タグ「洋服」ほか2件」と
  畳んでいて（`filterTagPartLabel` / `presetOverflowLabel`）、
  同じ「先頭 ＋ 残りの数」という形を**条件全体**にもう一段かける。
  畳み方が 2 通りにならないので、読み手が覚える規則は 1 つのまま。
- 数える単位は**件ではなく条件**（「ほか 7 条件」）── 末尾の「の14件だけ」が
  記録の件数なので、同じ「件」を使うと 2 つの数が同じものを数えているように読める。
- **畳んでも `activeFilterCount` とは一致し続ける。** 出す前の条件の並びは今までどおり
  全部作り、表示の直前で切るだけ（並びを作る側を変えると数と語がずれる。§4.3）。
- 行を押せば絞り込みページへ行き、そこで 9 本すべてが群ごとに読める ──
  **青い行は「効いている」ことと件数を出す場所で、内訳を読む場所ではない。**

## 6. 金額の範囲入力 — `RangeField` を新設する

`NumericField` は**流用しない**。あれは記録フォームの 1 欄で、
行高 60px 固定・電卓ボタン・`presetType`（プリセットの選択シートへの入口）・
警告の赤枠・まとめ買いの受け皿を持つ ── **使わない口のほうが多い。**
絞り込みに要るのは「数字を 2 つ受け取る」だけで、
電卓もプリセットも警告も**この画面に意味がない**（絞り込みに正解の値はない）。

**`RangeField` を新規で作る**（`src/components/RangeField.tsx`）。

```
純利益
[        ] 〜 [        ]
```

- 値の整形は `input.ts` の `sanitizeNumericInput`（数字と小数点だけ・小数点は 1 個）を通す。
  **アプリ中の金額入力と同じ規則**で、絞り込みだけ別の受け方をしない。
- 数値化は `parseNumericInput`。**空欄はその側の境界なし**（`0` ではない）ので、
  空文字の判定は `parseNumericInput` に渡す前に呼び出し側で行う
  （`parseNumericInput('')` は `0` を返す ── 「0 円以上」と「下限なし」は別物）。
- **大小を直さない**（min > max でも入れ替えない）。入れ替えると打っている途中に
  値が飛ぶ。結果は 0 件になるが、それは条件どおりの正しい結果で、
  下部の「0件」と 2 行目（`filterNoMatchNote`）がそのまま説明になる。
- 単位（円 / ¥）は**欄の中に出さない** ── このアプリの金額はすべて円で、
  記録フォームの数値欄も欄の中に単位を持たない。

## 7. 出品中での扱い

出品中（`isSoldMode = false`）では、**節ごと消すものと、そのまま出すものを分ける。**

| 条件 | 出品中 | なぜ |
|---|---|---|
| 販売サイト | **節ごと消す**（既存。§4.2） | 出品中の記録は `site_name` が空 |
| 目標の達成／未達 | **消す**（本書） | §7.1 |
| 赤字のみ | **出す**（本書） | §7.2 |
| メモの有無 | 出す | 出品中でも書ける |
| 金額の範囲 | 出す | 出品中の純利益は見込み額として一覧にも出ている |

### 7.1 目標は消す

出品中の記録の純利益は**まだ確定していない見込み額**である（販売価格は出品価格）。
その値を目標と比べて「達成」と言うと、**売れてもいないものを達成済みとして数える**ことになる。
SPEC-V9 §9 が帯グラフで出しているのも「この価格で売れたら届く」であって、達成の宣言ではない。

**節ごと消す。** 見た目だけ消して条件を残すと、
売れた記録に戻した瞬間に「見えないのに効いている」状態を作る（§4.2 の教訓）ので、
`effectiveFilter` でも落とし、**状態を切り替えるときに state からも退避する**
（販売サイトと同じ扱い。戻したときに 1 回だけ書き戻す）。

### 7.2 赤字のみは出す

**出品中の「このままだと赤字」は、値下げする前に見たい情報**である。
仕入と送料の見込みが出品価格を上回っている記録は、売れてから気づいても遅い。
出品中の一覧の行も帯グラフも既に赤字を赤で出しているので、
**絞り込みだけがそれを扱えないほうが画面の中で食い違う。**

目標との違いは、比べる相手が**利用者の決めた値ではなく 0** であること ──
0 との比較は見込み額でも意味が変わらない（「この価格で売れても赤字」は今日言える事実）。

## 9. 既存の決定の改訂

### 9.1 SPEC-V4 §4.1「N の数え方」— 最大 3 → **最大 9**

数え方の規則自体は変えない（**条件の本数**を数える。タグを何個選んでも 1 本）。
**範囲は min / max の両方を入れても 1 本。** 期間と検索を数に含めないのも変わらない。

### 9.2 SPEC-V4 §4.2「絞り込みページ」— 節 3 つ → **群 5 つ（折りたたみ）**

表の 2〜4 行目（種別・販売サイト・タグ）はそのまま群になり、**金額**と**その他**が加わる。
「完了」を置かない・条件は選んだ瞬間から効く・「すべて解除」はヘッダ、は変わらない
（**群ごとの解除が増える**。§3）。

### 9.3 SPEC-V4 §4.8「効き得る条件は 6 つ」→ **12 つ**

§4.8 が「条件ごとの文言を作らない」と決めた根拠は
「効き得る条件が 6 つ（状態・期間・検索・種別・販売サイト・タグ）あり、
組み合わせごとに書くと爆発する」だった。**本書で 12 になる**
（＋ 純利益・販売価格・経費・目標・赤字・メモ）。

**決定は変わらない。強まる。** 6 で爆発していたものが 12 で収まる道理はないので、
空表示は 1 文言のまま・条件の名前は出さないまま。
**同じ理由で `filterNoMatchNote` も触らない**（§4.2.3）── あれは月名と**本数**だけを出す設計で、
条件の名前を 1 つも含まない。**条件が 9 本になっても文言は 1 つも増えない**
（「この 9 つが揃った記録がありません」と数が変わるだけ）。
`{{count}}` に入る数が大きくなるだけで済むのは、
§4.8 の決定を守った設計が最初から条件の数に依存していなかったからである。

### 9.4 `recordFilter.ts` の「3 条件ちょうどで、これ以上増やさない」

**この文言を差し替える**（§0.2）。守っていたのは本数ではなく
「下書きの外に UI を持つ条件（期間・検索・並び替え）を入れないこと」なので、
歯止めをその形で書き直す ── 本数の上限は歯止めとして機能していなかった
（増やしたい条件が出た時点で、上限は理由ではなく事実の記述に落ちる）。
