# 移植後にやりたい改善

## 利用モードの切替（実装済み。レコード単位の「種別」として着地）
このアプリには2つの利用者層がある：
- 不用品を売る人：仕入価格の概念がない
- 仕入れて売る人：仕入価格が明確。関心は「利益がいくらか」

計算式は両者で完全に同一（不用品は仕入=0）。データ構造も共通。差分は表示のみ。

当初はここに「設定でアプリ全体のモードを切り替える」案を書いていたが、**採用しなかった**。
実利用者は不用品と仕入品が混在し、比率も時期によって変わるため、
アプリ全体の状態ではなく**レコード1件ごとに種別（`kind`: 不用品 / 仕入品）を持たせる**方式に変更した。
仕様の全文と決定の経緯は `docs/SPEC-V2.md`、確定した差分は `docs/SPEC.md` にある。

| 項目 | 不用品 | 仕入品 |
|---|---|---|
| 仕入価格欄 | 非表示（保存時に0へ正規化） | 常に表示 |
| 1件の結果ラベル | 純利益 | 利益 |
| 複数件の合計ラベル | 収支（種別が混ざるため中立語。合計行・データタブ） | 同左 |
| 逆算ラベル | 目標の純利益 | 目標利益 |
| 出品中タブ | 「出品中」のまま（種別で名前を変えない） | 同左 |

上の表からの変更点（いずれもSPEC-V2での決定）：
- **「手取り」は使わない。** 販売サイトが表示する「手取り」は梱包材費やその他の経費を含まないため、
  本アプリの計算結果（それらを差し引いた額）と食い違う。同じ語を別の意味で使うと金額の不一致が
  誤解を生むので、不用品側も「純利益」と呼ぶ。この食い違いはヘルプに注記を置いて明示している
- **タブ名は種別で変えない。** 種別はレコードの属性で、1つのリストに両種別が混在するため、
  タブ名を「売却待ち / 在庫」のように出し分けることはできない
- 種別ごとの合計を常時2系統で出すことはしない。分離は種別フィルタで行う

設定に残ったのは「新規作成時の種別」（既定種別）のみで、これは新しく作る記録の初期値を決めるだけ。
保存済みの記録の種別は設定変更で書き換わらない。

ストア掲載時は不用品側を主軸に訴求する（対象人数が多く、競合が薄いため）。
既定種別の初期値を「不用品」にしているのもこの方針に合わせたもの。

### 梱包材プリセット
背景：梱包材の費用は「封筒100枚入りのうち1枚」「プチプチ＋ダンボール併用」のように
1件あたりの金額が即座に出せず、結果として入力されず空欄のままになっている。
一方で利用者は梱包材の選択自体にはこだわっている（破損による評価低下を避けるため）ので、
選ぶ行為はすでに日常的に行っている。

仕様案：
- 設定画面で梱包材を登録できる。項目は名前と1個あたりの金額
- 登録時に「入数」と「購入価格」から1個あたりの金額を自動計算できる補助を用意する
  （例：100枚800円 → 8円）
- レコード入力時は登録済みの梱包材を複数選択でき、合計が梱包材費の欄に自動入力される
- 手動での上書きも可能（従来どおり自由入力を維持）

同種で複数メーカーの梱包材を使い分ける場合の識別方法：
- 第1案（採用）：名前とメモ欄で区別する。名前は自由入力なので
  「プチプチ（幅広）」「封筒（茶・大）」のように利用者が分かる形で登録できる。
  メモにはメーカー名や購入先を記載できる
- 第2案（将来）：写真の添付。名前だけで思い出せないほど種類が増えた場合に検討する。
  ただし登録のハードルが上がるため、初期実装では見送る
- 第3案（不採用）：購入先URLの保存。商品ページが消えたり変わったりするため信頼性が低い。
  必要ならメモに記載すれば足りる

登録のハードルを下げることを優先する（現状、梱包材費は入力されず空欄のままになっているため）。

期待効果：
- 入力されないままだった梱包材費が実データとして蓄積される
- 「今月の梱包材費」が集計できるようになる

### プリセットのカラーピッカー
現在は 10 色の固定パレットから選ぶ設計（`docs/SPEC-V3.md` §1.3。
同 §1.3 は 8 色で決めていたが、編集画面が色の丸を折り返して 2 段に並べるため、
実装時に 10 色へ拡張した）。パレットの末尾にカラーピッカーボタン（◎）を置き、
自由な色を選べるようにする案。

実装する場合の方針：
- 文字色は選んだ色の明度から自動で切り替える
  （明るい色なら黒文字、暗い色なら白文字）
- 保存形式が colorKey（パレット）と hex（自由選択）の2種類になるため、
  読み出し側で分岐が必要
- ダークモードでは選んだ色が沈む問題が残る。
  `theme.presetTones` は色ごとに明暗の対（`{ background, foreground }`）を持つ設計だが、
  hex を直接保存するとこの仕組みから外れる

優先度は低い。10 色で運用し、実際に色が足りないと感じてから実装する。

### 商品写真 →**`docs/SPEC-V5.md` へ移動（仕様確定・実装済み）**
記録に写真を添付する案。

**2026-08-12 に `docs/SPEC-V5.md` で仕様を確定し、実装した（案 `41a`）。**
本項が挙げていた「端末のカメラ・アルバムから選ぶ方式」をそのまま採り、
**1 件 1 枚**（SPEC-V5 §0.1）・**画像は DB に入れずファイルで持つ**（§1.2）とした。
本項が「別途必要」としていた 2 点のうち、
**ストレージ管理**は SPEC-V5 §1.4（長辺 1000px・JPEG 0.7 まで縮めてから保存）と
§1.5（記録を消したら実体も消す／差し替えたら古い方を消す）で決着した。
**バックアップは未決着**で、下の「ZIP でのバックアップ」に移した ──
写真は CSV に出さない（SPEC-V5 §5）ので、**CSV だけでは完全に復元できなくなった**。
→ **2026-08-14 に `docs/SPEC-V8.md` で決着。** 記録・プリセット・タグ・**写真**を
ZIP で書き出して読み戻せる。写真は合計 50MB までという上限だけが残る（SPEC-V8 §4）。

リンクから画像を自動取得する案は**不採用**とする。理由：
- ECサイトのHTML構造が変わるたびに壊れる
- 多くのサイトが自動アクセスを規約で禁じている
- 商品ページは売り切れると消えるためリンクが切れる
- 現在アプリは完全にオフラインで動作しており、
  外部通信を追加するとプライバシーポリシーや審査の対応が必要になる

実装するなら端末のカメラ・アルバムから選ぶ方式とする。
ストレージ管理とバックアップの検討が別途必要。
→ **アルバムから選ぶ方式で実装した。カメラは入れていない**（SPEC-V5 決定 §6-2）──
販売サイトにも載せる使い方では写真が先にカメラロールにあるため。

#### 入力の自動化（検討）
フリマサイトのリンクから商品名・価格・出品日を自動取得する案は不採用。
利用規約で自動アクセスを禁じているサービスが多く、
ストア配信するアプリには組み込めない。
サイト側のHTML構造変更で壊れるメンテナンス負荷も高い。

代替案として検討する価値があるもの：
- **共有シート経由の受け取り。** フリマアプリの商品ページから
  「共有」でこのアプリを選ぶ。渡されるのはURLとタイトル程度だが、
  商品名だけでも自動入力できる可能性がある。
  ユーザーが明示的に渡すため規約上の問題がない。
  何が渡されるかはサービスごとに異なるため、実機での検証が必要
- **取引画面のスクリーンショットからのOCR。**
  ユーザー自身の画面を撮るだけなので規約違反にならない。

**OCRは端末内処理で実装すること。写真を外部に送信しない。**
- iOS: Vision フレームワーク（OS標準、通信不要、日本語対応）
- Android: ML Kit の同等機能

Expo から利用できるライブラリの有無を調査し、
なければ Native Module の実装を検討する。
端末内処理であれば、プライバシーポリシーに
「データを外部送信しない」と記載するだけで済み、審査対応も軽くなる。

ただし優先度は低い。プリセット機能（`docs/SPEC-V3.md`）が入れば入力の手間は大幅に減るため、
それを使った上でまだ不足を感じた場合に検討する。

## 絞り込みの拡張

### 販売サイトでの絞り込み →**`docs/SPEC-V4.md` へ移動（仕様確定・未実装）**
sale_records.site_name を使って、記録タブ・データタブで
販売サイトごとに絞り込む案。SPEC-V3 §1.5.1 では V3 のスコープ外とした。

実装は難しくない（種別フィルタと同じ仕組みで絞れる）が、以下の懸念があった：
- 記録タブの合計行には既に状態チップと種別チップが並んでおり、
  3つ目が増えると窮屈になる
- 販売サイトを持つのは売れた記録だけ。出品中はまだ売れていないため
  サイトが決まっておらず、状態によってフィルタの数が変わることになる

**2026-08-11 に `docs/SPEC-V4.md` でタグと合わせて確定した。上の 2 つの懸念は解けた：**
- 「3つ目のチップで窮屈」→ **チップを増やさない。** 状態はセグメント、
  種別・販売サイト・タグは 1 枚の**絞り込みシート**にまとめ、
  合計行に出るのは「絞り込み N」チップ 1 つだけにした（SPEC-V4 §4.1 / §4.2）
- 「出品中はサイトを持たない」→ **出品中を選ぶとシートから販売サイトの節ごと消す**。
  売れた記録に戻すと直前の指定を復元する（SPEC-V4 §4.2）

本項の末尾にあった「タグ機能も同じ性質の要望で、実装するなら絞り込み UI を
まとめて設計する必要がある」という見立てのとおり、SPEC-V4 が両方を 1 つの UI として設計している。

なお**販売サイトの候補一覧には上限も検索欄も置かずに始める**（SPEC-V4 決定 §9-10）。
実際に多くなってから対応する ── 候補として並ぶのは実際に使ったサイトの数だけで、
プリセットを何件登録しても増えない。

### タグの AND 検索（見送り）
複数のタグを選んだときの絞り込みは **OR で確定**した（「洋服 または 春夏物」。SPEC-V4 §4.4）。
「洋服 かつ 春夏物」の AND 検索は今回入れない。

必要になったら**構造を変えずに足せる** ── SPEC-V4 が採った相関サブクエリ（`EXISTS`）を
タグの数だけ `AND` で並べるだけで済む。切り替える UI（OR / AND のトグル）の方が
説明の手間として大きいので、実際に困ってから判断する。

### 電卓の表示部への直接入力（見送り）
電卓の表示部分をタップして OS キーボードから式を直接打てるようにする案。
外付けキーボード利用者や、長い式を一度に入れたい場合に有効。

見送りの理由：
- `decimal-pad` には演算子がなく、`numbers-and-punctuation` はテンキー配列でないため
  数字入力が不便になる
- 自前キーパッドの状態と OS 入力欄の状態を同期する必要があり、
  入力途中の不完全な式（「1500÷」で止まっている等）の扱いが煩雑
- 電卓のキーパッドが画面下半分を占めるため、OS キーボードと場所を取り合う（UI-SPEC §7.1）
- 現在の利用者はモバイル単体での利用を想定しており、外付けキーボードの需要が薄い

将来、式の直接入力の要望が出た場合に再検討する。

## UI全面改訂で見送った項目（2026-08-10・`docs/UI-SPEC.md`）

UI 全面改訂の設計案にはあったが、今回のスコープから外したもの。判断の根拠は UI-SPEC の該当項に置いてある。

### postage を NULL 許容にする（UI-SPEC §5-3）
現状 `postage` は NOT NULL DEFAULT 0 のため、**「送料を入力していない」と「送料 0 円（送料込み・手渡し）」を
区別できない**。設計案は出品中の行に「売れたら 約¥2,520（送料未定）」と出し分ける想定だったが、
`postage === 0` では誤って「送料未定」と表示してしまう。

今回はスキーマを変更せず、出品中の見込み額には**常に「約」を付ける**（未入力かどうかの判定はしない）ことで回避した。
将来やるなら `postage` を nullable にして「未入力」を表現できるようにする。
同じ問題は `envelopeCost` / `othersCost` にもある。

### 設定「送料の既定値」（UI-SPEC §5-6）
設計案 `5b` に「送料 ＝ 前回の値を使う ▸」という項目があったが、挙動が未定義のため今回は実装しない。
決めるべきこと：
- 「前回保存した記録の送料を初期値にする」自動学習なのか、固定値を選ぶ画面へ遷移するのか
- 自動学習なら、SPEC-V2 §7-9 で既定種別について「自動学習は採用しない」と決めた理由
  （挙動が暗黙的になる）が送料にも当てはまるか

送料は配送方法で決まるので、既定値より**梱包材プリセットと同じ「登録して選ぶ」方式**のほうが合う可能性がある。

### データタブに売上の推移を戻す（UI-SPEC §5-4）
指標切替（売上金額 / 収支）を廃止したため、合計行で売上額は分かるが**売上が伸びているか**は見られなくなった。
戻すなら、切替を復活させるのではなく**収支の棒の背後に薄い売上の棒を重ねる**（切替なし・1 つのグラフ）。
実際に「見たい」と感じてから入れる。

### 計算タブの「元に戻す」（UI-SPEC §5-8）
設計案 `2e` は「クリアを押した直後に『元に戻す』を数秒表示する」としていたが、
スナックバー相当の共通部品がないため今回は見送り。「入力が空のときはクリアを無効」だけ実装する。
入れるなら他の破壊的操作（スワイプ削除など）にも使える共通部品として作る。

### CSV 書き出し（UI-SPEC §5-7）
設計案 `5b` では実装済みの体で描かれているが、SPEC-V2 §6.2 でスコープ外とされたまま未実装。
設定タブには行を置き「準備中」（非活性）で出す。実装するときは SPEC-V2 §7-11 のとおり `kind` を 1 列として出す。

**→ 2026-08-12 に実装済み（`docs/SPEC-V3.md` §5。Step 5・6）。** 「準備中」は外れ、
設定タブ「データ」群の行から書き出しシートが開く。`kind` は 2 種類とも 1 列として出している。

### 確定申告用の注意書きを消せるようにする（未着手）
確定申告用を選ぶと、シートの中に固定のバナーが出る（SPEC-V3 §5.8）:
「不用品でも、課税対象になる場合があります。書き出したあとで仕分けてください。」

いまは**消せない**。毎回同じ文が同じ場所に出るので、使い込むほど読み飛ばされる
（読み飛ばされる注意書きは、無い注意書きと同じになる）。

案:
- バナーに「✕」を置き、押すと**ヘッダの ⚠️ アイコンへ吸い込まれる**アニメーションで畳む。
  行き先が見えていれば「消えた」ではなく「そこにある」と読める
- 消した状態を覚える（設定に 1 つ持つ）。⚠️ アイコンを押せばいつでも開き直せる
- **確定申告用を初めて選んだときだけは必ず開いた状態にする**

先に**バナーを押したら詳しい説明が読める**ようにするのが前提（下項）。
消せるようにするのは、詳しい説明への入口ができてからにする ──
入口が無い状態で消せるようにすると、注意書きが本当に消えるだけになる。

### ZIP でのバックアップ（**2026-08-14 に `docs/SPEC-V8.md` で決着。ただし写真は保留**）

> **本節の論点は、写真を除いてすべて SPEC-V8 で決まった。**
> ZIP 1 つ（中に CSV 5 枚）でバックアップを作り、読み戻せるようにした。
> 下の「CSV の読み込み」と対で読むこと。対応は SPEC-V8 §9 に一覧がある。
>
> | 本節の論点 | SPEC-V8 の決定 |
> |---|---|
> | CSV の列を増やすか、ZIP 内の対応表を持つか | **どちらでもない。**既存 18 列 CSV は一切変えず、**別形式**（DB の全カラムをそのまま出す 5 枚）にした（§0.2） |
> | 書き出しの選択肢を増やすか、差し替えるか | **どちらでもない。**設定の**別の行**にした（§5.1）── 3 つ目の選択肢にすると「バックアップのつもりで CSV を選ぶ人が残る」という本節の懸念がそのまま当たるため |
> | 共有シートに渡せるか（未検証） | **渡せる。**実機で確認（ZIP Archive として認識される） |
> | ZIP のライブラリは新規依存になる | **`fflate`**（MIT / 依存ゼロ / 純粋 JS）。ネイティブ不要なので prebuild の構成を変えずに済む（§7.1） |
> | サイズ（500 件で 50〜150MB） | **写真を入れないことで回避した。**1000 件で 59KB（§6） |
> | 読み込みが無いと ZIP だけ作っても戻せない | **読み込みを同時に作った**（§3） |
>
> **写真も 2026-08-14 に決着した（SPEC-V8 §4）。** 本節が挙げたサイズの懸念は
> 正しかったが、原因の見立てが違った ── 破綻していたのは fflate ではなく
> **圧縮レベル**で、JPEG に deflate をかけていたぶんが丸ごと無駄だった
> （level 0 にすると作成 9 倍・展開 166 倍速く、サイズは 3% しか変わらない）。
> いまは `photos/` に入れて復元でき、**写真の合計 50MB** を上限としている
> （ピークメモリがアーカイブの約 5 倍で、低メモリ端末の jetsam に届くため）。
> 本節が試算した「500 件で 50〜150MB」も過大で、**実測は 1 枚 18〜371KB**
> （白背景の商品写真は 18〜61KB。SPEC-V8 §4.7）。

**写真（`docs/SPEC-V5.md`）が入ったことで、CSV だけでは記録を完全に復元できなくなった。**

CSV 書き出しの主用途はバックアップ（SPEC-V3 §0.1「端末が唯一の保存先」）だが、
**写真は CSV に出さない**（SPEC-V5 §5 / 決定 §6-7）── 表計算に画像の置き場がなく、
ファイル名を書いてもそのファイルは端末の中にあって他所では開けない。
結果として、書き出したファイルには**写真だけが入っていない**。

これは「読み込みが無いのでバックアップが片道」（下の「CSV の読み込み」）とは**別の欠け方**である ──
あちらは経路の問題で、こちらは**書き出したものの中身が既に欠けている**。
読み込みを作っても、写真は戻らない。

#### 案: CSV ＋ 画像フォルダを 1 ファイル（ZIP）にまとめる

```
backup-2026-08-12.zip
├── records.csv        ← いまの「データ保存用」（18 列）そのまま
└── photos/
    ├── a1b2c3.jpg
    └── d4e5f6.jpg
```

- **CSV の列は増やさない。** `photo_file_name` は既に `sale_records` の列としてあるので、
  読み込み側は「CSV の記録 ID → その記録の写真の名前」を辿れる。
  **ただし現行の 18 列には写真の列が無い**ので、ZIP を作るなら
  「その 1 列を足すか、ZIP の中だけの対応表を持つか」を決めることになる
  （**列を足すと、いまの CSV を表計算で開いた人には意味のない列が 1 本増える**）。
- **書き出しの選択肢を増やすのか、差し替えるのかを決める必要がある。**
  いまの書き出しシートは「データ保存用 / 確定申告用」の 2 択（SPEC-V3 §5.2）。
  ZIP を 3 つ目に足すと、**バックアップのつもりで CSV を選ぶ人が残る**
  （＝写真が抜けたまま安心してしまう）。「データ保存用」を ZIP に置き換える方が
  事故は少ないが、表計算でそのまま開けなくなる（1 手増える）。
- **共有シートに渡せるかの確認が要る**（`expo-sharing` は ZIP でも動くはずだが未検証）。
  ZIP を作るライブラリは新規依存になる（Expo に同梱のものは無い）。
- **サイズ**。写真は 1 枚 100〜300KB（SPEC-V5 §1.4）なので、
  500 件で 50〜150MB になり得る。共有シート経由で渡せる大きさか、
  期間で分けて出せるようにするか（書き出しには既に期間の指定がある）。
- 読み込み（下の節）が出来たときに、**ZIP を読めば写真ごと戻る**のが最終形。
  逆に読み込みを作らないまま ZIP だけ作っても、**中身を人が手で戻す道はない**
  （写真のファイル名は UUID で、どの記録のものかは CSV を読まないと分からない）。

**優先度**: 読み込み（下の節）と対で考えるべきもので、
単独で ZIP 書き出しだけを作っても復元はできない。ただし
「**写真が消えたら二度と戻らない**」状態は記録が増えるほど重くなるので、
読み込みより先に「出すだけは出せる」を作る価値はある。

### CSV の読み込み（**2026-08-14 に `docs/SPEC-V8.md` で決着**）

> **本節の論点はすべて決まった。** 対応表は SPEC-V8 §9 にある。要点は 3 つ:
>
> 1. **読み込むのは既存の CSV ではない。** 18 列 CSV は DB の上位集合ではなく
>    （計算値が入り、写真・資材費の 3 列が無く、時刻が落ちている）、読み戻しても
>    元に戻らない。列を足すと表計算で開く人に無意味な列が増える ── よって
>    **DB の全カラムをそのまま出す別形式**を作った（§0.2 / §2.1）。
> 2. **目的は「復元」に限る。** 本節が「先に決める必要がある」とした
>    ID 衝突の 3 択（A / B / C）は**どれも採らない**。4 テーブルを全置換するので、
>    ID 衝突という概念そのものが消えた（§3.4）。「取り込み」の口は作らない。
> 3. **タグの論点は丸ごと消えた。** 本節が挙げた「色をどう決めるか」「同名タグを
>    同じとみなすか」「名前の禁則に反する値」は、いずれも**CSV にタグ名しか
>    出ていない**ことから来ていた。SPEC-V8 は `tags` テーブルを id と色ごと
>    バックアップに入れるので、名前で突き合わせる場面が無い（§2.1）。
>
> 本節が挙げた個別の論点（列の過不足・桁区切り・日付形式・時刻の欠落・計算値・
> 途中失敗・入口・事前プレビュー）の決定は SPEC-V8 §9 の表を参照。
> **`expo-document-picker` は要らなかった** ── `File.pickFileAsync` が SDK 54+ にある。
>
> 以下は決定に至る前の検討の記録として残す。

書き出し（`docs/SPEC-V3.md` §5）は実装済みだが、**読み込みは無い**。
いずれ作るときのために、先に決めることになる論点を残しておく。**この節は決定ではない。**

書き出しの主用途はバックアップ（SPEC-V3 §0.1「端末が唯一の保存先」）なので、
読み込みが無いかぎり**バックアップは片道**である ── 書き出したファイルはあっても、
アプリに戻す手段がない。読み込みを作る動機はここにある。

**さらに 2026-08-12 以降は、書き出したファイルの中身そのものが欠けている**
（写真が入っていない。上の「ZIP でのバックアップ」）。
読み込みを作っても写真は戻らないので、2 つは対で考える必要がある。

#### 1. ID が衝突したときの扱い（最初に決めること）

データ保存用（18 列）には**記録 ID** が入っている（SPEC-V3 §5.3-18）。
読み込んだ ID が既存の記録と一致したときにどうするかで、3 つの道がある。

| | 扱い | 向く用途 | 問題 |
|---|---|---|---|
| A | ID を無視して常に新規作成 | 他人のデータの取り込み | **同じファイルを 2 回読むと二重になる** |
| B | ID が一致したら上書き | **バックアップからの復元** | 別端末のデータで、一致した記録が消える |
| C | ID が一致したら新しい ID を振って追加 | 取り込み | 復元にならない（同じ記録が 2 つになる） |

**UUIDv4 が偶然衝突する確率は無視できる**ので、実際に ID が一致するのは
**同じデータを 2 回読む場合＝復元の場面**である。したがって B が自然に見えるが、
**読み込みの目的（復元なのか取り込みなのか）を先に決める必要がある。**
目的が決まらないまま挙動だけ決めると、どちらの場面でも半端になる。

- 目的が**復元**なら B。「書き出したファイルを読み直すと元に戻る」が満たせる。
- 目的が**取り込み**なら A か C。ただしその場合、同じファイルを二度読んだときの
  二重登録をどう防ぐか（読み込み履歴を持つ？）が次の論点になる。
- **両方を 1 つの口で兼ねない**方がよさそうに見える（「復元」と「追加で取り込む」を
  利用者に選ばせる形）。ただし選択肢を増やすことそのものが事故の元でもある。

#### 2. タグの扱い（読み込みで実体を作ることになる）

**読み込んだ CSV にあるタグが、アプリに存在しない場合の扱いを決める必要がある。**

- タグは**実体**（`tags` テーブル）が要るので、無ければ**作る**ことになる。
  ただし **CSV にはタグ名しか出ていない**（SPEC-V4 §5.2 の 1 列に「洋服・春夏物」）ので、
  **色をどう決めるかが問題**:
  適当に振る（`nextTagColor` に任せる）／全部同じ色にする／読み込み後に使う人が直す。
- **同名のタグが既にある場合**、同じタグとみなして紐づけるか、別物として扱うか。
  名前が同じなら同じものとみなすのが自然だが、**別の色で使っていた場合に
  「同じ名前で違う意味のタグ」だった可能性が残る**。
  なお SPEC-V4 §1.3 は**同名のタグを弾く**ので、「別物として 2 つ作る」は
  いまの検証規則とそのまま衝突する（読み込みだけ規則を緩めるのか、という論点になる）。
- **名前の禁則（SPEC-V4 §1.3）に反するタグ名が CSV に入っていた場合の扱い。**
  手で編集した CSV を読み込むことがあり得る。具体的には
  **13 文字以上**／**「・」を含む**（区切り文字なので、そもそも 1 セルの中で
  2 つのタグと区別が付かない）／空文字。
  弾く・切り詰める・その記録だけタグ無しで読む、のどれか。

**プリセット（販売サイト・送料・梱包材）は対照的に、作る必要がない。**
SPEC-V3 §1.5 / 決定 §8-1 が「プリセットを記録に外部キーで紐づけず、
**名前のスナップショットを保存する**」と決めているため、`site_name` は
文字列としてそのまま `sale_records` の列に入る（読み込み先の列がある）。

**この非対称 ── タグは実体が要る／プリセットは要らない ── が、読み込みの設計で効いてくる。**
「CSV に出ている名前」の意味が 2 種類あるということで、
プリセットの名前は**過去の記録の一部**（読んだらそのまま列に入れる）、
タグの名前は**いま生きている分類への参照**（読んだら実体を用意して紐づける）である。

#### 3. その他の論点

- **確定申告用（11 列）は読み込めない。** 記録 ID・状態・出品日・手数料率・メモ・タグが
  無く（SPEC-V3 §5.3.1）、**日ごとにまとめた行は 1 行が複数の記録の合算**（§5.2.2）なので、
  元の記録に戻せない。読み込みの対象は**データ保存用だけ**にするのが素直で、
  そのことを画面で先に言う必要がある（確定申告用のファイルを選んだときのエラー文言）。
- **列が足りない / 多い CSV の扱い。** 列名で対応を取るか、位置で取るか。
  列名で取れば列の並べ替えに強いが、利用者が列名を書き換えていると読めない。
  必須の列（販売日・商品名・販売価格…）が欠けていたらどうするか。
- **金額の列に桁区切りが入っていた場合**（表計算で開いて書式を付けて保存し直すと起こる）。
  `1,050` を読むか弾くか。書き出し側は桁区切りを入れない決定（§5.4）だが、
  **往復の途中で表計算が入る**ことは十分あり得る。
- **日付の形式。** 書き出しは `YYYY-MM-DD` だが、Excel で開いて保存すると
  `2026/8/9` になることがある。
- **時刻が落ちている。** 書き出しは日付の先頭 10 文字だけ（§5.4）なので、
  読み込むと保存値の時刻（`T09:00:00.000`）を作り直すことになる。
  **書き出し → 読み込みで時刻の情報は失われる**（往復が完全に元に戻るわけではない）。
- **計算値の列（販売手数料・経費合計・収支）は読まない。**
  保存するのは率（`commission`）の側で、額は計算で出る（SPEC §2.2）。
  読み込んだ額と計算値が食い違っていても、**アプリの計算式を正とする**。
- **途中で失敗したときの扱い。** 1 行でも壊れていたら全部やめるか、読めた行だけ入れるか。
  トランザクションで全部やめる方が状態が読みやすいが、
  「1 行だけ壊れた 500 行のファイル」が一切読めないのは厳しい。
- **入口をどこに置くか。** 設定タブ「データ」群（書き出しの隣）が自然。
  ファイルの選択には `expo-document-picker`（新規依存）が要る。
- **読み込む前に見せる。** 書き出しにプレビューを付けた（§5.9）のと同じ理由で、
  **読み込みは書き出しよりさらに取り消せない**（既存のデータが動く）。
  「何件読む・何件が上書きになる」を押す前に出す形が要る。

- 月表示をタップすると年月ピッカーが開き、「全期間」も選べる
- これにより一覧からレコード詳細まで1タップになる（現状は2タップ）
- 月の移動も矢印1つで済む（現状は戻って選び直しで2アクション）

アプリ全体の操作感が揃う

### 種別フィルタの発見しにくさ

- 一覧上部にセグメントコントロールとして常設する
  （ただし縦幅を消費するため、月切り替えバーの導入と併せて設計する。
  上記「出品中・実績タブの階層構造」と同じ画面上部を取り合うため）

補足：SPEC-V2 §7-10 の「縦幅を節約するためソートメニューに統合」という決定は、
結果として発見可能性を犠牲にしていた。UI全体の見直し時に再検討する

補足2（2026-08-11）：SPEC-V4 で種別は**再びシートの中**（絞り込みシート）へ入るが、
本項の問題は再発しない。理由は 2 つ：
- シートは**絞り込み専用**で、8択のソートの下に埋もれない（種別は先頭の節）
- 合計行の「**絞り込み N**」チップに**効いている条件の数が出る**ので、
  絞り込みが効いていること自体が閉じた状態でも読める（SPEC-V4 §4.1）。
  さらに絞り込み中は解除バーが常に出る（案 `21d`）

**→ UI-SPEC §1.2 / SPEC-V2 §4.2 で解消。** 対処案の 2 案目（一覧上部に常設）を採った。
月バーの導入で常時表示の合計行ができたため、その右端にチップとして置けば縦幅を追加せずに済む。
SPEC-V2 §7-10 の決定は破棄した。

### 出品中の合計表示
現状、出品中タブでも「収支」「経費」を表示しているが、まだ売れていないため
どちらも確定した値ではなく、見ても意味がない。
出品中で見るべき指標に差し替える。候補：
- 出品点数
- 出品価格の合計（売れた場合に入る見込み額）
- 仕入品に使った金額（まだ回収できていない額）※不用品のみの月は0になる

**→ UI-SPEC §1.2 / §6-3 で解消。** 候補の 1・2 を採用し、合計行を「出品中 N 点」＋「出品価格の合計」にした。
3 つ目（回収できていない額）は今回は入れていない。
「出品価格 / 出品価格の合計」は SPEC-V2 §5.3 のラベル表に追加済み。
なお**滞留日数**（差別化候補の「出品中の滞留日数表示」）も、行のメタ行に「N 日経過」として入った（UI-SPEC §5-2）。
長い順ソートはまだない。

### 出品中→売却済みに変更したときの販売日
現状は自動的に今日の日付が入る。実際には数日前に売れた記録を後からつける場合があるため、
日付を確認・変更できるようにする。案：
- 切り替え時に日付を聞くシートを出す
- 今日を入れた上で、その場で編集できる導線を出す

- **実在するサービスの名前**はアプリ内・アプリ名・説明文のいずれにも含めない。
