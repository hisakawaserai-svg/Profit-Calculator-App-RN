## 0. 前提と方針

- 実利用者は「不用品の販売」と「仕入れての販売」が**混在**し、比率も時期によって変わる。
  したがって IMPROVEMENTS.md にあった**アプリ全体のモード切替は採用しない**。
  **レコード 1 件ごとに種別（kind）を持たせる**方式とする。
- 計算式は両種別で完全に同一（SPEC §2 をそのまま維持）。不用品は仕入価格 = 0 になるだけで、
  `netProfit` / `totalExpenses` / `requiredSalesPrice` の式は変更しない。
- したがって差分は「入力欄の出し分け」「表示ラベル」「集計の絞り込み」の 3 点に閉じる。
  **計算ロジック（`src/logic/profit.ts`）と SQL の計算式（`src/db/repository.ts` の
  `netProfitSql` / `totalExpensesSql`）は一切変更しない。**
- **決定（§8-1）: SwiftUI 版からのデータ移行は行わない。RN 版に守るべき実データもまだ存在しない。**
  よって本書のマイグレーションは「開発中に作られた行」だけを相手にすればよく、
  バックフィルの誤判定リスクは実質ゼロ。

## 1. レコード種別の定義

### 1.1 型と値

**決定（§7-7）: 表示名は「不用品 / 仕入品」で確定。**

| 値 | 表示名 | 意味 |
|---|---|---|
| `'used'` | 不用品 | 自宅にあった物を売る。仕入価格の概念がない（常に 0） |
| `'sourced'` | 仕入品 | 仕入れて売る。仕入価格を入力する |

```ts
export type RecordKind = 'used' | 'sourced';
```

- 種別は**レコードの属性**であり、アプリの状態ではない。同一リスト内に両種別が混在する。
- 2 値だが `boolean`（`isSourced` 等）ではなく**文字列 enum** とする。理由:
  DB を直接見たときに意味が読めること、将来 `'gift'`（貰い物）等の第 3 の値が要るとき
  マイグレーションが列追加でなく値追加で済むこと。
- CSV エクスポート（IMPROVEMENTS.md）でもこの値を列として出す（§7-11）。

### 1.2 計算への影響

**なし。** 種別は計算式に一切入らない。不用品は `purchasePrice = 0`（§2.4 の正規化で保証）なので、
結果として `netProfit = salesPrice − (送料 + 梱包材 + その他 + 手数料額)` になるだけ。
「不用品の純利益」と「仕入品の利益」は、同じ式の同じ値を別の言葉で呼んでいるにすぎない
（用語は §5）。

**決定（§7-8）: 不用品の結果を「手取り」とは呼ばない。** 販売サイトが表示する「手取り」は
梱包材費やその他経費を含まないため、本アプリの計算結果（それらを差し引いた額）と食い違う。
同じ語を別の意味で使うと金額の不一致が誤解を生むので、不用品も「純利益」と呼ぶ。
この食い違いはヘルプで明示する（§6.1）。

### 1.5 フォーム上で種別を切り替えたときの挙動

**決定（§7-3）: 確認ダイアログは出さず、即クリアする。**
**決定（§8-5）: レコードの種別が後から変わることは想定するが頻度は低いため、この仕様のままとする。**

- **仕入品 → 不用品**: 仕入価格の入力欄が消える。入力済みの値は
  **その場で 0 にクリアし、欄が消える前にユーザーが変化を目視できる**ようにする。
  保存時に黙って 0 にする方式（値を保持したまま非表示）は採らない。理由:
  見えない金額が経費に効き続ける／効かなくなる状態は、後から原因を追えないため。
- **不用品 → 仕入品**: 仕入価格の入力欄が空欄で現れる。他の値は変えない。
- 既存レコードの編集で種別を変えて保存した場合も同じ規則に従う（過去の集計値は当然変わる）。
- 詳細画面には種別の切替 UI を置かない（編集フォーム経由のみ）。売却トグルのような
  1 タップでの誤操作を避けるため。

## 2. schema への影響

### 2.1 列設計

`src/db/schema.ts` の `saleRecords` に 1 列追加する。

```ts
kind: text('kind', { enum: ['used', 'sourced'] }).notNull().default('used'),
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 列名 | `kind` | 「モード」ではなくレコードの属性であることを名前で示す |
| 型 | `text`（drizzle の `enum` 指定で型安全に） | §1.1 のとおり可読性と拡張性のため |
| NULL | **NOT NULL** | 「種別なし」の第 3 状態を作ると、表示・集計・フィルタの全分岐に `null` の場合が増える。移行時に一度だけ決め切る方が総コストが低い |
| DEFAULT | `'used'` | 列追加時に既存行を埋めるため必須（§2.2）。アプリ側は常に明示指定するので実行時には効かない |

### 2.2 マイグレーションと既存レコードの扱い

**決定（§7-1）: バックフィル規則は `purchasePrice > 0` → `'sourced'`、それ以外 → `'used'` で確定。**

`npm run db:generate` で `drizzle/0001_*.sql` が生成される（`ALTER TABLE ... ADD COLUMN`）。
drizzle-kit はデータ移行 SQL を生成しないので、**生成された SQL に以下の UPDATE を手で追記する**。

```sql
ALTER TABLE `sale_records` ADD `kind` text DEFAULT 'used' NOT NULL;
--> statement-breakpoint
UPDATE `sale_records` SET `kind` = 'sourced' WHERE `purchase_price` > 0;
```

- 根拠: 不用品は定義上 `purchasePrice = 0`（IMPROVEMENTS.md）。したがって
  `purchasePrice > 0` の行を不用品と見なすことはあり得ない。
- 誤判定が起きるのは「仕入れたが仕入価格 0」のケースのみ。この行は不用品に倒れるが、
  表示ラベルが変わるだけで金額はどの画面でも一切変わらない。ユーザーが編集画面で直せる。
- **決定（§8-1）: SwiftUI 版からのデータ移行は行わず、RN 版に守るべき実データも存在しない。**
  よって対象は開発中に作られた行のみで、移行処理側に同じ規則を実装する必要もない。
- 一律 `'used'` にする案は採らない。仕入価格が入っている行の詳細画面で仕入価格行が消え、
  金額の内訳が合わなくなるため。

`src/db/analytics.test.ts` と `scripts/db-smoke-test.ts` は `drizzle/meta/_journal.json` を読んで
マイグレーション SQL をそのまま流す作りなので、上記 UPDATE はテスト側でも自動的に適用される。

### 2.3 インデックス

**決定（§7 補足 / §8-6）: 種別フィルタ用のインデックスは追加しない。**

既存の 2 本（`(is_sold, sale_date)` / `(is_sold, sale_start_date)`）は変更しない。
レコード件数の見込みは数百〜数千件（§8-6）で、`kind` は 2 値とカーディナリティが低く、
既存インデックスで `is_sold` を絞った後の追加スキャンで十分なため。
将来件数が桁で増えて体感が出たら `(is_sold, kind, sale_date)` を検討する。

### 2.4 保存時の正規化ルール（追加）

**決定（§7-2）: 不用品の `purchasePrice` は 0 に強制する。値を保持したまま非表示にはしない。**

SPEC §5.2 の正規化（出品中なら `saleDate = null`）と同じ場所、
`src/db/repository.ts` の `toRow()` に以下を追加する。

```
kind === 'used' のとき purchasePrice = 0 を強制する
```

- フォーム側（§1.5）でもクリアするが、**DB に入る値の保証は repository の責務**とする
  （`saleDate` の正規化と同じ方針。二重実装ではなく、UI は見た目、repository は不変条件）。
- これにより「不用品なのに仕入価格が入っている行」はアプリ経由では作られない。
  §2.2 の移行後も同様。

## 3. 新規作成時の既定種別（設定）

### 3.1 設定項目

**決定（§7-9）: 既定種別は設定画面で明示的に選ぶ。「最後に保存した種別を次回の既定にする」自動学習は採用しない。**
挙動が暗黙的になり、意図しない種別で保存される事故のほうが害が大きいため。

| キー | 型 | 既定値 | 用途 |
|---|---|---|---|
| `defaultRecordKind` | `'used' \| 'sourced'` | `'used'` | 新規レコード・計算タブの初期種別（§1.4） |

初期値を `'used'` にするのは、IMPROVEMENTS.md の「ストア掲載時は不用品側を主軸に訴求する」方針
（対象人数が多い側を既定にする）に合わせるため。

### 3.2 保存先

**決定: `expo-sqlite/kv-store` を使う。**

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **A. `expo-sqlite/kv-store`（採用）** | `expo-sqlite` に同梱の KV ストア。`getItemSync` / `setItemSync` の**同期 API** を持つ | 依存追加ゼロ（`expo-sqlite` は導入済み）。同期読み出しなので初期表示のちらつきや loading state が不要。設定 DB がレコード DB と分離されるので、レコード側のマイグレーションに巻き込まれない | 文字列 KV なので値の妥当性検証を自前で書く必要がある（不正値は既定値にフォールバック） |
| B. レコードと同じ DB に `settings` テーブル | drizzle のスキーマ・マイグレーションで管理 | 型と DDL が一元管理される。将来の設定増加に強い | 設定 1 個のためにテーブルとマイグレーションを増やすのは過剰。設定変更のたびにレコード DB を書くことになる |
| C. `@react-native-async-storage/async-storage` | 定番の KV | 情報が多い | **新規依存の追加**。A と機能が重複し、しかも非同期のみ |

読み出しが同期なので、`src/db/client.ts` の repository と同じく「起動時に読める値」として扱え、
既存の `useRecordListData` 系（同期クエリ + `useFocusEffect` で再取得）の構成と揃う。

実装の置き場所は `src/settings/` を新設し、`getDefaultRecordKind()` / `setDefaultRecordKind()` と

## 4. 集計への影響

### 4.1 種別ごとに分けた集計は必要か

**決定（§7-5 / §8-2）: 合計は 1 系統のまま表示し、種別ごとの分離は Step 4 の絞り込みフィルタで代替する。
常時 2 系統の内訳表示は行わない。実際に使ってみてから内訳表示の要否を判断する。**

- 分離の手段が要る理由: 不用品の売却と仕入れての販売は金額の意味が異なり、
  「仕入れて売った分でいくら儲かったか」を見たい場面がある。
  確定申告での利用も可能性が高い（§8-3）。
- 常時 2 系統にしない理由: 月次カードは現在「収支 / 経費」の 2 値で既に情報密度が高く、
  4 値に増やすと一覧の可読性が落ちる。多くの月は片方の種別に偏るため、
  常時 2 系統は「片方が 0 のカード」を量産する。
- フィルタで「不用品だけ / 仕入品だけ」の合計は取れるので、必要な情報は失われない。

## 5. 用語の扱い

### 5.1 論点

1 レコードでは種別ごとに呼び分けたい。しかし集計は両者が混ざるため、合計を何と呼ぶかが問題になる。
加えて、不用品側に販売サイト由来の語（「手取り」）を使うと、サイト表示額との食い違いが誤解を生む。

### 5.2 案の比較

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A. 完全統一（現状維持） | すべて「純利益」 | 実装ゼロ。用語が 1 つで揺れない | 仕入れて売っている側の実感（利益）と語が合わない |
| B. 完全分離 | レコードも合計も種別ごとに呼び分け、混在時は合計を出さない | 用語が常に正確 | 混在が前提のこのアプリでは「合計が出せない」ことが致命的。月次カードが成立しない |
| **C. レコード＝種別語 / 合計＝中立語（採用）** | 1 件を指すときは「純利益」「利益」、2 件以上の合計は「収支」 | 合計を出しつつ、レコード単位では種別に合った語が使える。**「収支」は既に画面タイトル（「全期間の収支」「YYYY年M月の収支」）で使っている語**なので、新語を増やさない | 画面によって語が変わることを一度覚える必要がある。ヘルプでの説明が要る |
| D. 動的ラベル | 月内が不用品だけなら月カードも種別語で表示 | 語感が常に最適 | データが 1 件増えただけでラベルが変わる。**採用しない** |

**採用: 案 C。ただし不用品側の語は「手取り」ではなく「純利益」とする（§7-8）。**

### 5.3 確定ラベル表

**決定（§7-4 / §7-8。2026-08-10 に出品中の語とセグメント名を追加）**

| 対象 | ラベル |
|---|---|
| 不用品レコード 1 件の `netProfit` | **純利益** |
| 仕入品レコード 1 件の `netProfit` | **利益** |
| 複数レコードの `Σ netProfit`（合計行 / グラフ / 並び替え名） | **収支** |
| `totalExpenses`（1 件・合計とも） | **経費**（現状のまま。種別で変えない） |
| `salesPrice` | **販売価格** / データタブの集計は **売上** |
| `commissionCost` | **販売手数料**（現状のまま） |
| 計算タブの逆算入力 | 不用品「目標の純利益」/ 仕入品「目標利益」 |
| 計算タブの逆算結果 | **必要な販売価格**（現状のまま） |
| 計算タブのセグメント（結果側） | 不用品「**純利益を出す**」/ 仕入品「**利益を出す**」 |
| 計算タブのセグメント（逆算側） | **目標から逆算**（種別で変えない） |
| 出品中レコード 1 件の `salesPrice`（行の主金額） | **出品価格** |
| 出品中の `Σ salesPrice`（合計行） | **出品価格の合計** |
| 出品中の件数（合計行） | **出品中**（値は「N 点」） |
| 出品中レコード 1 件の見込み `netProfit`（行のメタ行） | **売れたら 約¥…**（常に「約」を付ける。UI-SPEC §5-3） |

- 「出品価格 / 出品価格の合計」は 2026-08-10 に追加した新語（UI-SPEC §6-3）。
  出品中は「まだ確定していない額」で、売れた記録の「販売価格 / 売上」と同じ語では意味が違ってしまうため、
  語を分ける。IMPROVEMENTS.md「出品中の合計表示」で挙げていた指標そのもの。
- **一覧行（`RecordRow`）には金額ラベルを付けない**（金額のみ・色で正負）。UI-SPEC §6-2 の決定。
  上表の「純利益 / 利益」は記録フォーム・レコード詳細・計算タブの結果行で使う。
- データタブの指標セグメント（`metricLabel`）は指標切替の廃止に伴い削除する（UI-SPEC §6-10）。
- 「手取り」は**アプリ内のどこでも使わない**（§1.2 / §7-8）。IMPROVEMENTS.md の表にある
  「結果ラベル: 手取り」は本書で破棄する。

- 内部の識別子（`netProfit`、`totalNetProfit`、`SortTypeMonthly` の `profitDesc` 等）は**改名しない**。
  表示語だけの問題であり、SPEC.md の計算式の名前と一致させておく方が追いやすいため。
- 表示語は 1 箇所に集約する（`src/logic/labels.ts`）。ラベルが画面ごとに散らばると
  用語変更のたびに全画面を触ることになる。

### 5.4 一覧行の種別表示

**決定（2026-08-10・UI-SPEC §6-1 で改訂）: 一覧行のメタ行に種別名を常時表示する。**
表示は「不用品　8/9 販売」のように、種別名と日付を同じ行の左側に並べる（UI-SPEC §1.2）。
記録タブとデータタブの内訳行の両方に効く（`RecordRow` 共用）。

理由: 旧決定「バッジを置かない」の根拠は「行の金額ラベル（純利益 / 利益）が種別表示を兼ねる」ことだった。
**UI-SPEC §6-2 でその金額ラベル自体を廃止したため、前提が崩れた。**
ラベルを消したうえでバッジも置かないと、種別を読む手段が一覧から完全に失われ、
レコード詳細を開くまで分からなくなる。

<details>
<summary>旧決定（2026-08-09）</summary>

**行や一覧に「不用品 / 仕入品」のバッジは置かない。** レコード詳細の商品情報カードにのみ
「種別」行を 1 行置く。一覧で種別を知りたいときはフィルタで絞れる。

補足: 「純利益 / 利益」は 1 文字違いなので、行のラベルは種別の見分けとしては弱い
（「手取り / 利益」案では強かった）。ただしバッジを足すと行の情報量が増えるため、
まずはバッジなしで実装する。実機で見て判別が要ると感じたらこの項だけ再検討する
（実装をブロックしない）。

— この「再検討」を UI 全面改訂で行い、上記のとおり破棄した。

</details>

4. **用語**
   **決定: 「純利益 / 利益 / 収支」とする。** レコード 1 件は不用品 = 純利益・仕入品 = 利益、
   複数件の合計は収支。その他の語（経費・販売価格・売上・販売手数料）は現状のまま。（§5.3 に反映）
5. **集計の分離をどこまでやるか**
   **決定: Step 4（フィルタのみ）で止める。** 種別ごとの内訳表示は、実際に使ってから要否を判断する。
   （§4.1 / §4.3 に反映）
6. **設定画面の入口**
   **決定: 計算タブのヘッダの歯車でよい。**（§3.3 に反映）
   → **2026-08-10 に破棄。設定はタブへ昇格し、歯車は削除する**（§3.3 / UI-SPEC §6-7 / §6-8）
7. **種別の表示名**
   **決定: 「不用品 / 仕入品」で確定。**（§1.1 に反映）
8. **不用品の結果を「手取り」と呼ぶか**
   **決定: 呼ばない。不用品も「純利益」とする。** 販売サイトが表示する「手取り」は梱包材費や
   その他経費を含まず、本アプリの計算結果と食い違うため。仕入品は「利益」のまま。
   食い違いはヘルプに注記を置いて明示する。（§1.2 / §5.3 / §6.1 に反映）
9. **既定種別の決め方**
   **決定: 設定で明示的に選ぶ。自動学習（最後に保存した種別を既定にする）は採用しない。**（§3.1 に反映）
10. **種別フィルタ UI の置き場所**
    **決定: 既存のソートメニュー（`OptionSheet`）に統合する。** 縦幅を節約するため。
    データタブは `OptionSheet` を使っていないので、表示単位・指標の切替と同じ列に並べる。（§4.2 に反映）
    → **2026-08-10 に破棄。合計行の右端の種別チップに変更**（§4.2 / UI-SPEC §1.2）。
    統合案は実装後、ソートの下に埋もれて発見できないことが分かった
11. **CSV エクスポートでの種別の扱い**
    **決定: `kind` を列として出す。ファイル分割はしない。**（§1.1 / §6.2 に反映。実装自体はスコープ外）

## 8. 前提条件への回答（旧「質問」）

1. **SwiftUI 版の実データを RN 版へ移行する予定はあるか**
   **回答: 移行は行わない。RN 版に守るべき実データもまだ存在しない。**
   → §2.2 のバックフィルは開発中データのみが対象。移行処理側の対応は不要。
2. **月次の合計をどちらの目的で見ているか**
   **回答: 月次は合計を 1 系統で表示し、種別ごとの内訳表示は Step 4 のフィルタで代替する。
   実際に使ってから内訳表示の要否を判断する。**
   → §4.1 / §4.3 で案 A のみ採用、`summaryByKind()` は作らない。
3. **確定申告での利用予定はあるか**
   **回答: 未定だが可能性は高い。CSV エクスポート時に `kind` を列として出す。**
   → §7-11。集計側は Step 4 のフィルタで分離できるため、現時点で追加要件はない。
4. **「不用品」「仕入品」という語を実利用者が普段どう呼んでいるか**
   **回答: この語をそのまま使う。**
   → §1.1 で確定。
5. **1 件のレコードで種別が変わることは起こるか**
   **回答: 想定するが頻度は低い。§1.5 の仕様のままでよい。**
   → 確認ダイアログなし・即クリアで確定（§7-3）。
6. **レコード件数の見込み**
   **回答: 数百〜数千件規模。インデックス追加は不要。**
   → §2.3 の判断を維持。
