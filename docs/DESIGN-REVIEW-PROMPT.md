# アプリ内レビュー依頼 設計 — DESIGN-REVIEW-PROMPT

アプリの中から**ストアのレビューを頼む**仕組み。テスターからの
「アプリ内でレビューできる機能を入れたほうがいい」という指摘から起こした。

入るものは 2 つで、**この 2 つはまったく別の経路**である:

| | 自動の依頼 | 設定タブ「レビューを書く」 |
|---|---|---|
| 出すもの | OS のレビュー画面（星を選ぶ小さいシート） | ストアの掲載ページ |
| 使うもの | `expo-store-review` の `requestReview()` | `Linking.openURL()` |
| きっかけ | 条件を満たした保存操作の 5.5 秒後 | 利用者が行を押したとき |
| 出る保証 | **無い**（OS が決める） | ある（ブラウザ／ストアアプリが開く） |

**混ぜてはいけない。** 設定の行から `requestReview()` を呼ぶことは
Google のガイドラインが名指しで禁じている（§5）。

---

## 0. 先に読む 3 つ

この 3 点を取り違えると設計が丸ごとずれるので先に書く。
実装のコメント（`src/logic/reviewPrompt.ts` の冒頭）にも同じことが書いてある。

### 0.1 表示回数はアプリで数えない。OS が管理する

- **iOS**: Apple のドキュメント（*Requesting App Store reviews*）が
  「システムは 365 日あたり**最大 3 回**までレビュー画面を表示する」と明記している。
  出すかどうかを決めるのは**システムであってアプリではない**。
- **Android**: Google Play が時間ベースの割り当てを持つ。
  「割り当ての具体的な値は実装の詳細であり、予告なく変更されうる」と書かれていて、
  **値は公開されていない**。

したがって「年 3 回に収まるようアプリ側で数える」という作りは要らないし、作れない。
数えても、OS が実際に出した回数とは一致しない。

### 0.2 出たかどうかをアプリは知れない

- iOS の `requestReview()` は**成否を返さない**。
- Android の `launchReviewFlow` は、割り当てに引っかかって
  **何も表示されなくても成功で返る**。

**この帰結として、レビューが書かれたことを前提にした後続処理を一切書かない。**
お礼の表示も、状態遷移も、実績も付けない。`src/review/requestReview.ts` が
呼び出し側に何も返さない（`void`）のはそのため ── 返せる意味のある値が無い。

では `reviewRequestCount` / `reviewRequestedAt` は何を数えているのか。
**こちらから「頼んだ」回数と時刻**であって、利用者が見た回数ではない。用途は 2 つだけ:

1. 出ないと分かっている状況で無駄に呼ばない（OS の割り当てより手前に自分の門を置く）
2. 「どういうときに呼ぶか」を純粋関数に閉じ込め、テストできる形にする（§6）

### 0.3 設定の導線では API を呼ばない

Google の In-App Review のガイドライン:

> ユーザーが既に割り当てに達している場合、フローが表示されず壊れた体験になるので、
> API を起動する CTA（ボタンなど）を置くべきではない

押しても**何も起きない行**になりうる、というのが理由である。
Apple も、利用者が自分から書きに行く経路には
`https://apps.apple.com/app/id.../?action=write-review` という URL を案内している。

だから設定タブの行は `Linking.openURL()` でストアのページを開くだけにする（§5）。

## 1. 何を使うか

`expo-store-review@57.0.2`（SDK 57 対応版）。

```
npx expo install expo-store-review
```

- **iOS**: iOS 16 以上は `AppStore.requestReview(in:)`、それ未満は
  `SKStoreReviewController.requestReview(in:)`。前面のシーンが取れないときは例外を投げる。
  podspec の要求は iOS 16.4 で、このプロジェクトの `IPHONEOS_DEPLOYMENT_TARGET` は
  既に 16.4 なので**引き上げは要らない**。
- **Android**: Play の In-App Review API（`com.google.android.play:review`）。
  `isAvailableAsync()` は実際には「Play ストアが端末に入っているか」を見ている。
- **config plugin は無い**。app.json を触らないので **prebuild は要らない**
  （`/ios` `/android` は生成物なので、`pod install` と再ビルドだけ）。

`requestReview()` は **iOS も Android も reject しうる**（前面シーン無し／`RMTaskException`）。
ポジティブな場面で unhandled rejection を出さないよう、必ず catch する。

## 2. いつ出すか

### 2.1 ゲート（全部満たしたときだけ発火を許す）

| 条件 | 値 | 理由 |
|---|---|---|
| 起動回数 | 5 回以上 | 初回起動の直後に出さない。Apple が「起動直後は避けよ」と名指しで書いている |
| 初回起動からの経過 | 7 日以上 | 起動回数だけでは足りない ── 1 日に 5 回起動しただけの人はまだ評価できる段階にいない |
| 売れた記録の件数 | 10 件以上 | このアプリの中心的な成功体験を通った人にだけ頼む。**全件ではなく売れた件数**（記録しただけでは役に立ったか分からない） |
| 前回頼んでからの間隔 | 120 日以上 | OS の割り当てとぶつからない位置に自分の門を置く |
| 通算で頼んだ回数 | 3 回まで | 同上。120 日 × 3 回 = 360 日で、**こちらの上限が先に効く** |

値はすべて `src/logic/reviewPrompt.ts` の定数として名前が付いている。

### 2.2 発火点

**第一候補は「実績を新規に獲得した瞬間」。** 理由が 3 つある:

1. **定義上ポジティブ**である
2. **配線が既にある** ── `saveRecord()` / `setSoldStatus()` が
   「新規に完了した実績」の配列を返し、実績獲得トーストへ流している（`db/useRecords.ts`）
3. **頻度が自然に低い** ── 全 38 種の階段構造なので、条件が揃う機会がそもそも希少

**第二候補は「実績は出なかったが、黒字の記録を保存したとき」。**
実績は希少なので、これが無いとゲートを満たした人でも何年も発火しないことがある。

### 2.3 除外

| 外すもの | どう外しているか |
|---|---|
| 純利益がマイナスの記録 | 判定（`reviewPromptOccasion`）が **実績より優先して**外す（下記） |
| バックアップの復元（成功・失敗とも） | **呼んでいない**。復元の経路から `requestReviewAfterSave` を呼ばない |
| 書き出し・各種の失敗 | 同上 |
| 「売れた → 出品中に戻す」「取り消し」 | 同上。`handleUndoMarkSold` / `handleRevertToListing` からは呼ばない |
| チュートリアル表示中 | `OnboardingOverlay` がモーダルとして数に入る（§3） |
| UMP（広告の同意）が出うる起動 | 起動から 30 秒は出さない（§3） |

**赤字はすべてに優先して外す。実績を獲得していても外す。**
実績には利益を条件にしないもの（「記録を続けよう」「販売デビュー」など、
記録した行為そのものを数えるもの）があり、赤字の記録でも解放されうる。
損を確定させた直後にレビューを頼むのは、「ネガティブな場面で出さない」の中でも
いちばん外したい場面なので、実績のほうを譲る。次の機会まで待てばよい。

出品中（まだ売れていない）は赤字ではないので外さない。実績が出たならそれが発火点になる。
**純利益は 0 と「まだ無い」を分ける** ── 0 は「売れて収支がちょうど合った」で黒字側、
`null` は「売れていないので利益という値がまだ無い」。0 で代用すると、
出品しただけで発火点になってしまう。

## 3. どう出すか（間の取り方）

保存の直後には**既に下端に家具が出ている**:

| 出るもの | 長さ |
|---|---|
| 実績獲得トースト | 4 秒（`react-native-toast-message` の既定 `visibilityTime`） |
| UndoBar（「売れた」の取り消し） | 4 秒（`TRANSIENT_FEEDBACK_MS`） |

その上へ被せると、読み終える前に合図を押し流すことになる。だから:

```
保存 → シートが閉じる → トースト/UndoBar（4 秒） → +1.5 秒 → レビュー画面
```

合計 5.5 秒（`REVIEW_PROMPT_DELAY_MS`）。トーストの長さを直接書かず
`TRANSIENT_FEEDBACK_MS` から作るのは、片方だけ変えられないようにするため。
1.5 秒空けるのは Apple のドキュメントが例示している「割り込まないための待ち」と同じ考え方。

**その 5.5 秒後にもう一度、出してよい状態かを見る**（`canPresentNow`）:

- モーダルが開いていないか（`src/review/modalPresence.ts`）
- アプリが前面にいるか（`AppState.currentState === 'active'`）
- 起動から 30 秒以上経っているか

満たさなければ**見送り、何も記録しない**（`markReviewRequested` を呼ばない）。
出していないのだから、頼んだ回数にもクールダウンにも入れない。
条件は次の保存操作でまた判定されるので、失った機会はすぐ戻ってくる。

### 3.1 モーダルの数え方

`modalPresence.ts` が「マウントされている RN の `Modal` の数」を持つ。
アプリの `Modal` は 5 か所しかなく（`SheetModal` / `RecordFormSheet` /
`AchievementDetailModal` / `PhotoViewer` / `OnboardingOverlay`）、
そのうち `SheetModal` は 18 のシートの共通の器なので、この 5 か所が
`useModalPresence()` を呼べば漏れなく数えられる。
**`Modal` を新しく足すときはここにも足すこと。**

### 3.2 起動から 30 秒を空ける理由

広告の同意フォーム（UMP）は起動直後に出ることがあり、あれは RN の `Modal` ではないので
`isAnyModalOpen()` では見えない。ゲート（起動 5 回以上・7 日以上）を満たした端末では
同意が済んでいるのが普通なので実際にはまず衝突しないが、
**見えないものを避ける手当ては条件ではなく時間で置く**しかない。

「同意フローが終わったか」を見に行かないのは、同意の取得は失敗しうるものだから
（`ads/consent.ts`）── 失敗した端末でレビュー依頼が永久に出なくなるほうが困る。

### 3.3 TestFlight と Play ストアの無い端末を先に外す

`requestReview()` を呼ぶ前に `isAvailableAsync()` を見る。
iOS の TestFlight では false が返り、レビュー画面は出ない。
**ここで先に外さないと、テスターの端末で「見えないまま通算 3 回」を使い切ってしまう。**

### 3.4 記録するのは呼ぶ直前

`markReviewRequested()` は `requestReview()` の**直前**に呼ぶ。
呼んだあとにすると、レビュー画面が出ている最中にプロセスが終わったときに記録が残らず、
次の保存でまた頼んでしまう。ここが数えているのは「頼んだ」であって「見せた」ではない（§0.2）
ので、呼びに行った時点で記録するのが意味とも合う。

## 4. 置き場所

| ファイル | 持つもの |
|---|---|
| `src/logic/reviewPrompt.ts` | **判定だけ**（純粋関数）。ゲート・発火点・除外の全条件と、その定数 |
| `src/logic/reviewPrompt.test.ts` | 上の全条件（§6） |
| `src/settings/reviewRequest.ts` | kv-store のキーと値の検証（純粋関数） |
| `src/settings/reviewRequest.test.ts` | 上の検証 |
| `src/settings/index.ts` | 履歴の読み書き（`countLaunch` / `getReviewPromptHistory` / `markReviewRequested`） |
| `src/review/requestReview.ts` | 実行（`expo-store-review`・タイマー・画面の状態） |
| `src/review/modalPresence.ts` | モーダルが出ているかの申告 |
| `src/review/storeUrl.ts` | 設定タブが開くストアの URL |
| `src/db/repository.ts` | `soldCount()`（売れた記録の件数） |

`ads/` と同じ分け方 ── 手順と条件をテストできる側へ引き剥がし、
native の層には「実機でしか動かないもの」だけを残す。

### 4.1 履歴を kv-store に置く理由

`lastBackupAt` とまったく同じ理屈である（`src/settings/lastBackupAt.ts` の冒頭）:

> 記録の DB に置くと、復元（全置換）でこの値まで書き換わってしまう ──
> 「前回いつ作ったか」は端末の履歴であって、バックアップの中身ではない。

**復元でレビュー依頼の履歴が巻き戻ると、頼み直しが起きる。**
設定 DB は記録 DB と別ファイルなので、置くだけでこれが満たされる。

日時を `lastBackupAt` のような文字列ではなく **epoch ms（数値）**で持つのは、
あちらが**画面に出す**値で、こちらは**引き算にしか使わない**値だから。

### 4.2 起動回数の数え方

`countLaunch()` は `RootLayout` の `useEffect` から 1 回だけ呼ぶ
（`useDeviceLanguageSync()` と同じ「アプリ全体で 1 か所」の規約）。
モジュール内に once ガードを持つ ── effect は開発時の再マウントや将来の `StrictMode` で
2 回走りうるが、**呼ばれた回数がそのまま保存される**ので、二重呼び出しが数字の誤りとして残る。

初回起動の時刻は**まだ無いときだけ**書く。上書きすると
「初回起動から 7 日以上」が毎回リセットされ、永久に満たせなくなる。

DB の準備は待たない。数えるのは kv-store（設定 DB）なので、
待つと初期化に失敗した起動だけが数から漏れる。

## 5. 設定タブ「レビューを書く」

サポート・プライバシーポリシーとは**別のカード**にする ──
あちらは「困ったときに読むもの」で、こちらは書きに行くもの。
同じカードに 3 行目として並べると、下の注記（「どちらも端末のブラウザで開きます」）が
開く先の違う行にも掛かってしまう（こちらはストアアプリが受け取りうる）。

| | URL |
|---|---|
| iOS | `https://apps.apple.com/app/id6804385417?action=write-review` |
| Android | `https://play.google.com/store/apps/details?id=com.sera.profitcalculator` |

iOS の `action=write-review` は App Store をレビュー投稿の画面で開く。
**Android には同等の直リンクが無い**ので掲載ページを開く。
`market://` は使わない ── ストアアプリが無い端末で開けずに終わるだけで、
`https` なら少なくともブラウザで掲載ページに辿り着ける。

ストアの無い経路（web）では `storeReviewUrl()` が null を返し、**行ごと出さない**
── 押しても何も起きない行を残さない。

`expo-store-review` の `storeUrl()` は使わない。あれは app.json の
`ios.appStoreUrl` / `android.playStoreUrl` を読むだけの薄い関数で、経由させても
増えるのは「app.json に書いた値が埋め込み config に載っているか」という心配だけになる。
サポート・プライバシーポリシーの URL と同じく TS の定数で持つほうが揃う。

**繰り返す: この行から `requestReview()` を呼んではいけない**（§0.3）。

## 6. 検証

条件は 9 本ある（発火点 2・赤字の除外 1・ゲート 5・通算上限 1）。
**実機では全部を試し切れない**ので、条件の側を `src/logic/reviewPrompt.ts` へ
引き剥がし、`vitest` で「1 つだけ外して不成立になること」の形で 1 本ずつ固める。

実機で何が見えるかは環境で違う:

| 環境 | どうなるか |
|---|---|
| **iOS TestFlight** | `isAvailableAsync()` が false。レビュー画面は出ない。**確認できない** |
| iOS シミュレータ | 出る。回数制限なし。投稿はできない |
| iOS 開発ビルド（Xcode から実機） | 出る |
| **Android 内部テストトラック** | 出る。**割り当てが無効化される**。そのアカウントで既にレビュー済みだと出ない |
| Android 内部アプリ共有 | カードは出るが**送信ボタンが無効** |

**自動発火をまともに目で見られるのは Android の内部テストトラックだけ。**
iOS 側の担保は上のテストである。

## 7. やらないこと

- **レビューを書いてもらえたかの追跡**（§0.2）。お礼も、状態遷移も、実績も付けない
- **「アプリを評価しますか？」の事前の問いかけ**。Google が明示的に禁じている
  （「評価する前に意見を聞く質問・予測的な質問をしてはならない」）
- **レビュー画面の見た目の変更・上への重ね置き**。同じくガイドラインが禁じている
- **表示回数のアプリ側での計数**（§0.1）
